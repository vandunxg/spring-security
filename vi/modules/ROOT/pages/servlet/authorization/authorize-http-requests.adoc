[[servlet-authorization-authorizationfilter]]
= Ủy quyền HttpServletRequest
:figures: servlet/authorization

Spring Security cho phép bạn xref:servlet/authorization/index.adoc[mô hình hóa authorization] ở cấp request.
Ví dụ, với Spring Security, bạn có thể quy định rằng mọi trang dưới `/admin` yêu cầu một authority, còn mọi trang khác chỉ yêu cầu authentication.

Theo mặc định, Spring Security yêu cầu mọi request phải được authenticated.
Tuy vậy, bất cứ khi nào sử dụng xref:servlet/configuration/java.adoc#jc-httpsecurity[một instance `HttpSecurity`], bạn đều cần khai báo các quy tắc authorization.

[[activate-request-security]]
Khi có một instance `HttpSecurity`, ít nhất bạn nên thực hiện như sau:

.Sử dụng authorizeHttpRequests
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .anyRequest().authenticated()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize(anyRequest, authenticated)
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url pattern="/**" access="authenticated"/>
</http>
----
======

Điều này cho Spring Security biết rằng mọi endpoint trong ứng dụng ít nhất phải có security context được authenticated thì mới được phép truy cập.

Trong nhiều trường hợp, các quy tắc authorization của bạn sẽ phức tạp hơn, vì vậy hãy xem xét các trường hợp sử dụng sau:

* Tôi có một ứng dụng sử dụng `authorizeRequests` và muốn <<migrate-authorize-requests,di chuyển sang `authorizeHttpRequests`>>
* Tôi muốn <<request-authorization-architecture,tìm hiểu cách các component `AuthorizationFilter` hoạt động>>
* Tôi muốn <<match-requests,so khớp request>> dựa trên một pattern, cụ thể là <<match-by-regex,biểu thức chính quy>>
* Tôi muốn so khớp request và ánh xạ Spring MVC tới <<mvc-not-default-servlet,một servlet khác servlet mặc định>>
* Tôi muốn <<authorize-requests,ủy quyền request>>
* Tôi muốn <<match-by-custom,so khớp request bằng chương trình>>
* Tôi muốn <<authorize-requests,ủy quyền request bằng chương trình>>
* Tôi muốn <<remote-authorization-manager,ủy thác authorization của request>> cho một policy agent
* Tôi muốn <<customizing-authorization-managers,tùy chỉnh cách tạo các authorization manager>>

[[request-authorization-architecture]]
== Tìm hiểu cách các component authorization ở cấp request hoạt động

[NOTE]
Phần này dựa trên xref:servlet/architecture.adoc#servlet-architecture[Kiến trúc và triển khai Servlet] để đi sâu hơn vào cách xref:servlet/authorization/index.adoc#servlet-authorization[authorization] hoạt động ở cấp request trong các ứng dụng dựa trên Servlet.

.Ủy quyền HttpServletRequest
[.invert-dark]
image::{figures}/authorizationfilter.png[]

* image:{icondir}/number_1.png[] Đầu tiên, `AuthorizationFilter` tạo một `Supplier` lấy xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[Authentication] từ xref:servlet/authentication/architecture.adoc#servlet-authentication-securitycontextholder[SecurityContextHolder].
* image:{icondir}/number_2.png[] Thứ hai, nó truyền `Supplier<Authentication>` và `HttpServletRequest` tới xref:servlet/architecture.adoc#authz-authorization-manager[`AuthorizationManager`].
`AuthorizationManager` so khớp request với các pattern trong `authorizeHttpRequests` và thực thi quy tắc tương ứng.
** image:{icondir}/number_3.png[] Nếu authorization bị từ chối, xref:servlet/authorization/events.adoc[một `AuthorizationDeniedEvent` được publish] và một `AccessDeniedException` được throw.
Trong trường hợp này, xref:servlet/architecture.adoc#servlet-exceptiontranslationfilter[`ExceptionTranslationFilter`] xử lý `AccessDeniedException`.
** image:{icondir}/number_4.png[] Nếu access được cấp, xref:servlet/authorization/events.adoc[một `AuthorizationGrantedEvent` được publish] và `AuthorizationFilter` tiếp tục với xref:servlet/architecture.adoc#servlet-filters-review[FilterChain], cho phép ứng dụng xử lý bình thường.

=== `AuthorizationFilter` mặc định ở vị trí cuối

Theo mặc định, `AuthorizationFilter` ở vị trí cuối trong xref:servlet/architecture.adoc#servlet-filterchain-figure[filter chain của Spring Security].
Điều này có nghĩa là xref:servlet/authentication/index.adoc[các authentication filter], xref:servlet/exploits/index.adoc[các cơ chế bảo vệ khỏi exploit] và các tích hợp filter khác của Spring Security không yêu cầu authorization.
Nếu thêm filter của riêng bạn trước `AuthorizationFilter`, các filter đó cũng không yêu cầu authorization; nếu không, chúng sẽ yêu cầu authorization.

Điều này thường trở nên quan trọng khi bạn thêm các endpoint {spring-framework-reference-url}web.html#spring-web[Spring MVC].
Vì chúng được thực thi bởi {spring-framework-reference-url}web.html#mvc-servlet[`DispatcherServlet`] và servlet này chạy sau `AuthorizationFilter`, các endpoint của bạn cần được <<authorizing-endpoints,đưa vào `authorizeHttpRequests` để được cho phép>>.

=== Mọi dispatch đều được authorization

`AuthorizationFilter` không chỉ chạy trên mọi request mà còn trên mọi dispatch.
Điều này có nghĩa là dispatch `REQUEST` cần authorization, cũng như các dispatch ``FORWARD``, ``ERROR`` và ``INCLUDE``.

Ví dụ, {spring-framework-reference-url}web.html#spring-web[Spring MVC] có thể `FORWARD` request tới một view resolver render template Thymeleaf như sau:

.Controller Spring MVC chuyển tiếp mẫu
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Controller
public class MyController {
    @GetMapping("/endpoint")
    public String endpoint() {
        return "endpoint";
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Controller
class MyController {
    @GetMapping("/endpoint")
    fun endpoint(): String {
        return "endpoint"
    }
}
----
======

Trong trường hợp này, authorization diễn ra hai lần: một lần để ủy quyền cho `/endpoint` và một lần để chuyển tiếp tới Thymeleaf render template "endpoint".

Vì lý do đó, bạn có thể muốn <<match-by-dispatcher-type,cho phép mọi dispatch `FORWARD`>>.

Một ví dụ khác của nguyên tắc này là {spring-boot-reference-url}reference/web/servlet.html#web.servlet.spring-mvc.error-handling[cách Spring Boot xử lý lỗi].
Nếu container bắt được một exception, chẳng hạn như sau:

.Controller Spring MVC gây lỗi mẫu
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Controller
public class MyController {
    @GetMapping("/endpoint")
    public String endpoint() {
        throw new UnsupportedOperationException("unsupported");
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Controller
class MyController {
    @GetMapping("/endpoint")
    fun endpoint(): String {
        throw UnsupportedOperationException("unsupported")
    }
}
----
======

thì Boot sẽ dispatch request đó tới dispatch `ERROR`.

Trong trường hợp đó, authorization cũng diễn ra hai lần: một lần để ủy quyền cho `/endpoint` và một lần để dispatch lỗi.

Vì lý do đó, bạn có thể muốn <<match-by-dispatcher-type,cho phép mọi dispatch `ERROR`>>.

=== Việc tra cứu `Authentication` được trì hoãn

Hãy nhớ rằng xref:servlet/authorization/architecture.adoc#_the_authorizationmanager[API `AuthorizationManager` sử dụng một `Supplier<Authentication>`].

Điều này quan trọng với `authorizeHttpRequests` khi request <<authorize-requests,luôn được cho phép hoặc luôn bị từ chối>>.
Trong các trường hợp đó, xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Authentication`] không được truy vấn, giúp request nhanh hơn.

[[authorizing-endpoints]]
== Ủy quyền cho một endpoint

Bạn có thể cấu hình Spring Security với các quy tắc khác nhau bằng cách thêm các quy tắc theo thứ tự ưu tiên.

Nếu muốn yêu cầu chỉ end user có authority `USER` mới truy cập được `/endpoint`, bạn có thể thực hiện như sau:

.Ủy quyền cho một endpoint
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
public SecurityFilterChain web(HttpSecurity http) throws Exception {
    http
        .authorizeHttpRequests((authorize) -> authorize
	    .requestMatchers("/endpoint").hasAuthority("USER")
            .anyRequest().authenticated()
        );
        // ...

    return http.build();
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
fun web(http: HttpSecurity): SecurityFilterChain {
    http {
        authorizeHttpRequests {
            authorize("/endpoint", hasAuthority("USER"))
            authorize(anyRequest, authenticated)
        }
    }

    return http.build()
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url pattern="/endpoint" access="hasAuthority('USER')"/>
    <intercept-url pattern="/**" access="authenticated"/>
</http>
----
======

Như bạn có thể thấy, khai báo có thể được chia thành các cặp pattern/rule.

`AuthorizationFilter` xử lý các cặp này theo thứ tự được liệt kê và chỉ áp dụng kết quả so khớp đầu tiên cho request.
Điều này có nghĩa là dù `/**` cũng khớp với `/endpoint`, các quy tắc trên vẫn không có vấn đề.
Có thể đọc các quy tắc trên như sau: "nếu request là `/endpoint` thì yêu cầu authority `USER`; nếu không thì chỉ yêu cầu authentication".

Spring Security hỗ trợ nhiều pattern và nhiều rule; bạn cũng có thể tạo các pattern và rule của riêng mình bằng chương trình.

Sau khi request được authorize, bạn có thể kiểm thử bằng xref:servlet/test/method.adoc#test-method-withmockuser[test support của Security] như sau:

.Kiểm thử authorization của endpoint
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@WithMockUser(authorities="USER")
@Test
void endpointWhenUserAuthorityThenAuthorized() {
    this.mvc.perform(get("/endpoint"))
        .andExpect(status().isOk());
}

@WithMockUser
@Test
void endpointWhenNotUserAuthorityThenForbidden() {
    this.mvc.perform(get("/endpoint"))
        .andExpect(status().isForbidden());
}

@Test
void anyWhenUnauthenticatedThenUnauthorized() {
    this.mvc.perform(get("/any"))
        .andExpect(status().isUnauthorized());
}
----
======

[[match-requests]]
== So khớp request

Ở trên, bạn đã thấy <<authorizing-endpoints,hai cách so khớp request>>.

Cách đầu tiên là đơn giản nhất: so khớp mọi request.

Cách thứ hai là so khớp theo pattern URI.
Spring Security hỗ trợ hai ngôn ngữ để so khớp pattern URI: <<match-by-ant,Ant>> (như ở trên) và <<match-by-regex,biểu thức chính quy>>.

[[match-by-ant]]
=== So khớp bằng Ant
Ant là ngôn ngữ mặc định mà Spring Security sử dụng để so khớp request.

Bạn có thể dùng nó để so khớp một endpoint hoặc một thư mục, thậm chí capture placeholder để sử dụng sau.
Bạn cũng có thể tinh chỉnh nó để so khớp một tập HTTP method cụ thể.

Giả sử thay vì so khớp endpoint `/endpoint`, bạn muốn so khớp mọi endpoint dưới thư mục `/resource`.
Trong trường hợp đó, bạn có thể thực hiện như sau:

.So khớp bằng Ant
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .requestMatchers("/resource/**").hasAuthority("USER")
        .anyRequest().authenticated()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize("/resource/**", hasAuthority("USER"))
        authorize(anyRequest, authenticated)
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url pattern="/resource/**" access="hasAuthority('USER')"/>
    <intercept-url pattern="/**" access="authenticated"/>
</http>
----
======

Có thể đọc quy tắc này như sau: "nếu request là `/resource` hoặc một thư mục con, yêu cầu authority `USER`; nếu không thì chỉ yêu cầu authentication".

Bạn cũng có thể trích xuất giá trị path từ request như dưới đây:

.Ủy quyền và trích xuất
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .requestMatchers("/resource/{name}").access(new WebExpressionAuthorizationManager("#name == authentication.name"))
        .anyRequest().authenticated()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize("/resource/{name}", WebExpressionAuthorizationManager("#name == authentication.name"))
        authorize(anyRequest, authenticated)
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url pattern="/resource/{name}" access="#name == authentication.name"/>
    <intercept-url pattern="/**" access="authenticated"/>
</http>
----
======

Sau khi request được authorize, bạn có thể kiểm thử bằng xref:servlet/test/method.adoc#test-method-withmockuser[test support của Security] như sau:

.Kiểm thử authorization của thư mục
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@WithMockUser(authorities="USER")
@Test
void endpointWhenUserAuthorityThenAuthorized() {
    this.mvc.perform(get("/resource/jon"))
        .andExpect(status().isOk());
}

@WithMockUser
@Test
void endpointWhenNotUserAuthorityThenForbidden() {
    this.mvc.perform(get("/resource/jon"))
        .andExpect(status().isForbidden());
}

@Test
void anyWhenUnauthenticatedThenUnauthorized() {
    this.mvc.perform(get("/any"))
        .andExpect(status().isUnauthorized());
}
----
======

[NOTE]
Spring Security chỉ so khớp path.
Nếu muốn so khớp query parameter, bạn sẽ cần một request matcher tùy chỉnh.

[[match-by-regex]]
=== So khớp bằng biểu thức chính quy
Spring Security hỗ trợ so khớp request với một biểu thức chính quy.
Điều này hữu ích nếu bạn muốn áp dụng tiêu chí so khớp chặt chẽ hơn `**` trên một thư mục con.

Ví dụ, hãy xét một path chứa username và quy tắc rằng mọi username phải là chữ và số.
Bạn có thể sử dụng javadoc:org.springframework.security.web.util.matcher.RegexRequestMatcher[] để tuân thủ quy tắc này như sau:

.So khớp bằng Regex
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .requestMatchers(RegexRequestMatcher.regexMatcher("/resource/[A-Za-z0-9]+")).hasAuthority("USER")
        .anyRequest().denyAll()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize(RegexRequestMatcher.regexMatcher("/resource/[A-Za-z0-9]+"), hasAuthority("USER"))
        authorize(anyRequest, denyAll)
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url request-matcher="regex" pattern="/resource/[A-Za-z0-9]+" access="hasAuthority('USER')"/>
    <intercept-url pattern="/**" access="denyAll"/>
</http>
----
======

[[match-by-httpmethod]]
=== So khớp theo HTTP method

Bạn cũng có thể so khớp rule theo HTTP method.
Điều này hữu ích khi ủy quyền theo permission được cấp, chẳng hạn privilege `read` hoặc `write`.

Để yêu cầu mọi ``GET`` có permission `read` và mọi ``POST`` có permission `write`, bạn có thể thực hiện như sau:

.So khớp theo HTTP Method
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .requestMatchers(HttpMethod.GET).hasAuthority("read")
        .requestMatchers(HttpMethod.POST).hasAuthority("write")
        .anyRequest().denyAll()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize(HttpMethod.GET, hasAuthority("read"))
        authorize(HttpMethod.POST, hasAuthority("write"))
        authorize(anyRequest, denyAll)
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url http-method="GET" pattern="/**" access="hasAuthority('read')"/>
    <intercept-url http-method="POST" pattern="/**" access="hasAuthority('write')"/>
    <intercept-url pattern="/**" access="denyAll"/>
</http>
----
======

Các quy tắc authorization này có thể được đọc như sau: "nếu request là GET thì yêu cầu permission `read`; nếu không, nếu request là POST thì yêu cầu permission `write`; nếu không thì từ chối request".

[TIP]
Từ chối request theo mặc định là một thực hành bảo mật tốt vì nó biến tập rule thành allow list.

Sau khi request được authorize, bạn có thể kiểm thử bằng xref:servlet/test/method.adoc#test-method-withmockuser[test support của Security] như sau:

.Kiểm thử authorization theo HTTP method
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@WithMockUser(authorities="read")
@Test
void getWhenReadAuthorityThenAuthorized() {
    this.mvc.perform(get("/any"))
        .andExpect(status().isOk());
}

@WithMockUser
@Test
void getWhenNoReadAuthorityThenForbidden() {
    this.mvc.perform(get("/any"))
        .andExpect(status().isForbidden());

@WithMockUser(authorities="write")
@Test

    this.mvc.perform(post("/any").with(csrf()))
        .andExpect(status().isOk());
}

@WithMockUser(authorities="read")
@Test

    this.mvc.perform(post("/any").with(csrf()))
        .andExpect(status().isForbidden());
}
----
======

[[match-by-dispatcher-type]]
=== So khớp theo Dispatcher Type

[NOTE]
Tính năng này hiện chưa được hỗ trợ trong XML

Như đã nêu ở trên, theo mặc định Spring Security <<_all_dispatches_are_authorized,ủy quyền cho mọi dispatcher type>>.
Mặc dù xref:servlet/authentication/architecture.adoc#servlet-authentication-securitycontext[security context] được thiết lập trên dispatch `REQUEST` được truyền sang các dispatch tiếp theo, những khác biệt nhỏ trong so khớp đôi khi có thể gây ra `AccessDeniedException` ngoài dự kiến.

Để giải quyết điều đó, bạn có thể cấu hình Spring Security bằng Java để cho phép các dispatcher type như `FORWARD` và `ERROR` như sau:

.So khớp theo Dispatcher Type
[tabs]
======
Java::
+
[source,java,role="secondary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .dispatcherTypeMatchers(DispatcherType.FORWARD, DispatcherType.ERROR).permitAll()
        .requestMatchers("/endpoint").permitAll()
        .anyRequest().denyAll()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize(DispatcherTypeRequestMatcher(DispatcherType.FORWARD), permitAll)
        authorize(DispatcherTypeRequestMatcher(DispatcherType.ERROR), permitAll)
        authorize("/endpoint", permitAll)
        authorize(anyRequest, denyAll)
    }
}
----
======

[[match-by-mvc]]
=== So khớp theo Servlet Path

Nói chung, bạn có thể sử dụng `requestMatchers(String)` như minh họa ở trên.

Tuy nhiên, nếu có các quy tắc authorization từ nhiều servlet, bạn cần chỉ rõ chúng:

.So khớp bằng PathPatternRequestMatcher
[tabs]
======
Java::
+
[source,java,role="primary"]
----
import static org.springframework.security.web.servlet.util.matcher.PathPatternRequestMatcher.withDefaults;

@Bean
SecurityFilterChain appEndpoints(HttpSecurity http) {
	PathPatternRequestMatcher.Builder mvc = withDefaults().basePath("/spring-mvc");
	http
        .authorizeHttpRequests((authorize) -> authorize
            .requestMatchers(mvc.matcher("/admin/**")).hasAuthority("admin")
            .requestMatchers(mvc.matcher("/my/controller/**")).hasAuthority("controller")
            .anyRequest().authenticated()
        );

	return http.build();
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
fun appEndpoints(http: HttpSecurity): SecurityFilterChain {
    http {
        authorizeHttpRequests {
            authorize("/spring-mvc", "/admin/**", hasAuthority("admin"))
            authorize("/spring-mvc", "/my/controller/**", hasAuthority("controller"))
            authorize(anyRequest, authenticated)
        }
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<http>
    <intercept-url servlet-path="/spring-mvc" pattern="/admin/**" access="hasAuthority('admin')"/>
    <intercept-url servlet-path="/spring-mvc" pattern="/my/controller/**" access="hasAuthority('controller')"/>
    <intercept-url pattern="/**" access="authenticated"/>
</http>
----
======

Điều này là do Spring Security yêu cầu mọi URI phải là absolute (không bao gồm context path).

[TIP]
=====
Có một số component khác tạo request matcher cho bạn, chẳng hạn {spring-boot-api-url}org/springframework/boot/security/autoconfigure/web/servlet/PathRequest.html[`PathRequest#toStaticResources#atCommonLocations`]
=====

Nếu phần lớn quy tắc authorization của bạn nằm dưới cùng một servlet path, bạn có thể xref:servlet/integrations/mvc.adoc#mvc-requestmatcher[publish một bean `PathPatternRequestMatcher.Builder`] với base path đó; khi ấy Spring Security áp dụng nó cho các overload nhận string của `authorizeHttpRequests((authorize) -> authorize.requestMatchers(...))`, `HttpSecurity#securityMatcher(...)` / `#securityMatchers(...)` và `WebSecurityCustomizer#ignoring().requestMatchers(...)`.

=== Sử dụng matcher tùy chỉnh

[NOTE]

Trong Java configuration, bạn có thể tạo javadoc:org.springframework.security.web.util.matcher.RequestMatcher[] của riêng mình và cung cấp nó cho DSL như sau:

.Ủy quyền theo Dispatcher Type
[tabs]
======

RequestMatcher printview = (request) -> request.getParameter("print") != null;

[[authorize-requests]]
== Ủy quyền request

Sau khi request được so khớp, bạn có thể ủy quyền theo nhiều cách <<match-requests,đã được đề cập ở trên>>, như `permitAll`, `denyAll` và `hasAuthority`.

Tóm tắt nhanh, dưới đây là các quy tắc authorization được tích hợp trong DSL:

* `permitAll` - Request không yêu cầu authorization và là một public endpoint; lưu ý rằng trong trường hợp này, xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Authentication`] không bao giờ được lấy từ session
* `denyAll` - Request không được phép trong bất kỳ trường hợp nào; lưu ý rằng trong trường hợp này, `Authentication` không bao giờ được lấy từ session
* `hasAuthority` - Request yêu cầu `Authentication` có xref:servlet/authorization/architecture.adoc#authz-authorities[một `GrantedAuthority`] khớp với giá trị đã cho
* `hasRole` - Shortcut cho `hasAuthority`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasAnyAuthority` - Request yêu cầu `Authentication` có một `GrantedAuthority` khớp với bất kỳ giá trị nào đã cho
* `hasAnyRole` - Shortcut cho `hasAnyAuthority`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasAllRoles` - Shortcut cho `hasAllAuthorities`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasAllAuthorities` - Request yêu cầu `Authentication` có một `GrantedAuthority` khớp với tất cả giá trị đã cho
* `access` - Request sử dụng `AuthorizationManager` tùy chỉnh này để quyết định access

Sau khi đã tìm hiểu pattern, rule và cách ghép chúng, bạn có thể hiểu điều gì đang xảy ra trong ví dụ phức tạp hơn sau đây:

.Ủy quyền request
[tabs]
======
Java::
+
[source,java,role="primary"]
----
import static jakarta.servlet.DispatcherType.*;

import static org.springframework.security.authorization.AuthorizationManagers.allOf;
import static org.springframework.security.authorization.AuthorityAuthorizationManager.hasAuthority;
import static org.springframework.security.authorization.AuthorityAuthorizationManager.hasRole;

@Bean
SecurityFilterChain web(HttpSecurity http) throws Exception {
	http
		// ...
		.authorizeHttpRequests((authorize) -> authorize                                  // <1>
            .dispatcherTypeMatchers(FORWARD, ERROR).permitAll() // <2>
			.requestMatchers("/static/**", "/signup", "/about").permitAll()         // <3>
			.requestMatchers("/admin/**").hasRole("ADMIN")                             // <4>
			.requestMatchers("/db/**").hasAllAuthorities("db", "ROLE_ADMIN")   // <5>
			.anyRequest().denyAll()                                                // <6>
		);

	return http.build();
}
----
======
<1> Có nhiều quy tắc authorization được chỉ định.
Mỗi quy tắc được xem xét theo thứ tự khai báo.
<2> Các dispatch `FORWARD` và `ERROR` được cho phép để {spring-framework-reference-url}web.html#spring-web[Spring MVC] render view và Spring Boot render lỗi.
<3> Chúng ta đã chỉ định nhiều pattern URL mà mọi user đều có thể truy cập.
Cụ thể, mọi user có thể truy cập request nếu URL bắt đầu bằng "/static/", bằng "/signup" hoặc bằng "/about".
<4> Mọi URL bắt đầu bằng "/admin/" sẽ bị giới hạn cho user có role "ROLE_ADMIN".
Bạn sẽ thấy rằng vì đang gọi method `hasRole`, chúng ta không cần chỉ định tiền tố "ROLE_".
<5> Mọi URL bắt đầu bằng "/db/" yêu cầu user vừa được cấp permission "db", vừa là một "ROLE_ADMIN".
Bạn sẽ thấy rằng vì đang sử dụng expression `hasAllAuthorities`, chúng ta phải chỉ định tiền tố "ROLE_".
<6> Mọi URL chưa được so khớp trước đó đều bị từ chối access.
Đây là một chiến lược tốt nếu bạn không muốn vô tình quên cập nhật các quy tắc authorization.

[[authorization-expressions]]
== Biểu đạt authorization bằng SpEL

Mặc dù nên sử dụng `AuthorizationManager` cụ thể, có một số trường hợp cần expression, chẳng hạn với `<intercept-url>` hoặc JSP Taglibs.
Vì lý do đó, phần này sẽ tập trung vào các ví dụ trong những lĩnh vực đó.

Vì vậy, hãy cùng tìm hiểu sâu hơn một chút về Web Security Authorization SpEL API của Spring Security.

Spring Security đóng gói tất cả field và method authorization trong một tập các root object.
Root object tổng quát nhất có tên `SecurityExpressionRoot` và là nền tảng của `WebSecurityExpressionRoot`.
Spring Security cung cấp root object này cho `StandardEvaluationContext` khi chuẩn bị đánh giá một expression authorization.

[[using-authorization-expression-fields-and-methods]]
=== Sử dụng field và method của authorization expression

Điều đầu tiên mà cơ chế này cung cấp là một tập field và method authorization nâng cao cho các SpEL expression của bạn.
Dưới đây là tổng quan nhanh về những method phổ biến nhất:

* `permitAll` - Request không yêu cầu authorization để được gọi; lưu ý rằng trong trường hợp này, xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Authentication`] không bao giờ được lấy từ session
* `denyAll` - Request không được phép trong bất kỳ trường hợp nào; lưu ý rằng trong trường hợp này, `Authentication` không bao giờ được lấy từ session
* `hasAuthority` - Request yêu cầu `Authentication` có xref:servlet/authorization/architecture.adoc#authz-authorities[một `GrantedAuthority`] khớp với giá trị đã cho
* `hasRole` - Shortcut cho `hasAuthority`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasAnyAuthority` - Request yêu cầu `Authentication` có một `GrantedAuthority` khớp với bất kỳ giá trị nào đã cho
* `hasAnyRole` - Shortcut cho `hasAnyAuthority`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasPermission` - Hook tới instance `PermissionEvaluator` của bạn để thực hiện authorization ở cấp object

Và dưới đây là cái nhìn khái quát về những field phổ biến nhất:

* `authentication` - Instance `Authentication` liên kết với lần gọi method này
* `principal` - `Authentication#getPrincipal` liên kết với lần gọi method này

Sau khi đã tìm hiểu pattern, rule và cách ghép chúng, bạn có thể hiểu điều gì đang xảy ra trong ví dụ phức tạp hơn sau đây:

.Ủy quyền request bằng SpEL
[tabs]
======
Xml::
+
[source,java,role="primary"]
----
<http>
    <intercept-url pattern="/static/**" access="permitAll"/> <1>
    <intercept-url pattern="/admin/**" access="hasRole('ADMIN')"/> <2>
    <intercept-url pattern="/db/**" access="hasAuthority('db') and hasRole('ADMIN')"/> <3>
    <intercept-url pattern="/**" access="denyAll"/> <4>
</http>
----
======
<1> Chúng ta đã chỉ định một pattern URL mà mọi user đều có thể truy cập.
Cụ thể, mọi user có thể truy cập request nếu URL bắt đầu bằng "/static/".
<2> Mọi URL bắt đầu bằng "/admin/" sẽ bị giới hạn cho user có role "ROLE_ADMIN".
Bạn sẽ thấy rằng vì đang gọi method `hasRole`, chúng ta không cần chỉ định tiền tố "ROLE_".
<3> Mọi URL bắt đầu bằng "/db/" yêu cầu user vừa được cấp permission "db", vừa là một "ROLE_ADMIN".
Bạn sẽ thấy rằng vì đang sử dụng expression `hasRole`, chúng ta không cần chỉ định tiền tố "ROLE_".
<4> Mọi URL chưa được so khớp trước đó đều bị từ chối access.
Đây là một chiến lược tốt nếu bạn không muốn vô tình quên cập nhật các quy tắc authorization.

[[using_path_parameters]]
=== Sử dụng path parameter

Ngoài ra, Spring Security cung cấp một cơ chế phát hiện path parameter để chúng cũng có thể được truy cập trong SpEL expression.

Ví dụ, bạn có thể truy cập path parameter trong SpEL expression như sau:

.Ủy quyền request bằng path variable của SpEL
[tabs]
======
Xml::
+
[source,xml,role="primary"]
----
<http>
    <intercept-url pattern="/resource/{name}" access="#name == authentication.name"/>
    <intercept-url pattern="/**" access="authenticated"/>
</http>
----
======

Expression này tham chiếu tới path variable sau `/resource/` và yêu cầu nó bằng `Authentication#getName`.

[[remote-authorization-manager]]
=== Sử dụng authorization database, policy agent hoặc service khác
Nếu muốn cấu hình Spring Security sử dụng một service riêng cho authorization, bạn có thể tạo `AuthorizationManager` của riêng mình và so khớp nó với `anyRequest`.

Trước tiên, `AuthorizationManager` của bạn có thể trông như sau:

.Authorization Manager của Open Policy Agent
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public final class OpenPolicyAgentAuthorizationManager implements AuthorizationManager<RequestAuthorizationContext> {
    @Override
    public AuthorizationResult authorize(Supplier<Authentication> authentication, RequestAuthorizationContext context) {
        // thực hiện request tới Open Policy Agent
    }
}
----
======

Sau đó, bạn có thể wire nó vào Spring Security như sau:

.Mọi request đều chuyển tới remote service
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
SecurityFilterChain web(HttpSecurity http, AuthorizationManager<RequestAuthorizationContext> authz) throws Exception {
	http
		// ...
		.authorizeHttpRequests((authorize) -> authorize
            .anyRequest().access(authz)
		);

	return http.build();
}
----
======

[[favor-permitall]]
=== Ưu tiên `permitAll` thay vì `ignoring`
Khi có static resource, bạn có thể muốn cấu hình filter chain bỏ qua các resource này.
Cách tiếp cận an toàn hơn là cho phép chúng bằng `permitAll` như sau:

.Cho phép static resource
[tabs]
======
Java::
+
[source,java,role="secondary"]
----
http
    .authorizeHttpRequests((authorize) -> authorize
        .requestMatchers("/css/**").permitAll()
        .anyRequest().authenticated()
    )
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    authorizeHttpRequests {
        authorize("/css/**", permitAll)
        authorize(anyRequest, authenticated)
    }
}
----
======

Điều này an toàn hơn vì ngay cả với static resource, việc ghi secure header vẫn quan trọng, nhưng Spring Security không thể làm vậy nếu request bị bỏ qua.

Trước đây, cách này phải đánh đổi hiệu năng vì Spring Security tham vấn session trên mọi request.
Tuy nhiên, từ Spring Security 6, session không còn bị truy vấn trừ khi quy tắc authorization yêu cầu.
Vì ảnh hưởng hiệu năng hiện đã được giải quyết, Spring Security khuyến nghị sử dụng ít nhất `permitAll` cho mọi request.

[[migrate-authorize-requests]]
== Di chuyển từ `authorizeRequests`

[NOTE]
`AuthorizationFilter` thay thế javadoc:org.springframework.security.web.access.intercept.FilterSecurityInterceptor[].
Để duy trì backward compatibility, `FilterSecurityInterceptor` vẫn là mặc định.
Phần này thảo luận cách `AuthorizationFilter` hoạt động và cách override cấu hình mặc định.

javadoc:org.springframework.security.web.access.intercept.AuthorizationFilter[] cung cấp xref:servlet/authorization/index.adoc#servlet-authorization[authorization] cho các ``HttpServletRequest``.
Nó được chèn vào xref:servlet/architecture.adoc#servlet-filterchainproxy[FilterChainProxy] như một trong các xref:servlet/architecture.adoc#servlet-security-filters[Security Filter].

Bạn có thể override mặc định khi khai báo một `SecurityFilterChain`.
Thay vì sử dụng javadoc:org.springframework.security.config.annotation.web.builders.HttpSecurity#authorizeRequests()[authorizeRequests], hãy dùng `authorizeHttpRequests` như sau:

.Sử dụng authorizeHttpRequests
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
SecurityFilterChain web(HttpSecurity http) throws AuthenticationException {
    http
        .authorizeHttpRequests((authorize) -> authorize
            .anyRequest().authenticated();
        )
        // ...

    return http.build();
}
----
======

Điều này cải thiện `authorizeRequests` theo một số cách:

1. Sử dụng API `AuthorizationManager` đơn giản hóa thay vì metadata sources, config attributes, decision managers và voters.
Điều này đơn giản hóa việc tái sử dụng và tùy chỉnh.
2. Trì hoãn việc tra cứu `Authentication`.
Thay vì phải tra cứu authentication cho mọi request, hệ thống chỉ tra cứu trong những request mà quyết định authorization yêu cầu authentication.
3. Hỗ trợ cấu hình dựa trên bean.

Khi dùng `authorizeHttpRequests` thay cho `authorizeRequests`, javadoc:org.springframework.security.web.access.intercept.AuthorizationFilter[] sẽ được dùng thay cho javadoc:org.springframework.security.web.access.intercept.FilterSecurityInterceptor[].

=== Di chuyển expression

Khi có thể, bạn nên sử dụng các authorization manager type-safe thay vì SpEL.
Với Java configuration, javadoc:org.springframework.security.web.access.expression.WebExpressionAuthorizationManager[] có sẵn để hỗ trợ di chuyển SpEL legacy.

Để sử dụng `WebExpressionAuthorizationManager`, bạn có thể tạo một instance với expression cần di chuyển như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
.requestMatchers("/test/**").access(new WebExpressionAuthorizationManager("hasRole('ADMIN') && hasRole('USER')"))
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
.requestMatchers("/test/**").access(WebExpressionAuthorizationManager("hasRole('ADMIN') && hasRole('USER')"))
----
======

Để di chuyển nhiều expression, bạn có thể dùng `WebExpressionAuthorizationManager#withDefaults`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
WebExpressionAuthorizationManager.Builder authz = WebExpressionAuthorizationManager.withDefaults();
.requestMatchers("/test/**").access(authz.expression("hasRole('ADMIN') && hasRole('USER')"))
.requestMatchers("/test/**").access(authz.expression("permitAll"))
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
var authz = WebExpressionAuthorizationManager.withDefaults()
.requestMatchers("/test/**").access(authz.expression("hasRole('ADMIN') && hasRole('USER')"))
.requestMatchers("/test/**").access(authz.expression("permitAll"))
----
======

Nếu expression của bạn tham chiếu tới một bean như sau: `@webSecurity.check(authentication, request)`, bạn nên gọi trực tiếp bean đó, tương tự như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
.requestMatchers("/test/**").access((authentication, context) ->
    new AuthorizationDecision(webSecurity.check(authentication.get(), context.getRequest())))
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
.requestMatchers("/test/**").access((authentication, context): AuthorizationManager<RequestAuthorizationContext> ->
    AuthorizationDecision(webSecurity.check(authentication.get(), context.getRequest())))
----
======

Với các chỉ dẫn phức tạp bao gồm tham chiếu bean cùng các expression khác, bạn nên thay đổi chúng để triển khai `AuthorizationManager` và tham chiếu bằng cách gọi `.access(AuthorizationManager)`.

Nếu không thể làm vậy, bạn có thể publish javadoc:org.springframework.security.web.access.expression.WebExpressionAuthorizationManager$Builder[] dưới dạng bean:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
WebExpressionAuthorizationManager.Builder authz() {
	return WebExpressionAuthorizationManager.withDefaults();
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
fun authz(): WebExpressionAuthorizationManager.Builder {
	return WebExpressionAuthorizationManager.withDefaults()
}
----
======

Khi đó, các expression truyền vào builder sẽ có thể tham chiếu tới bean.

[[security-matchers]]
== Security Matchers

Interface javadoc:org.springframework.security.web.util.matcher.RequestMatcher[] được sử dụng để xác định request có khớp với một rule nhất định hay không.
Chúng ta sử dụng `securityMatchers` để xác định liệu xref:servlet/configuration/java.adoc#jc-httpsecurity[một `HttpSecurity` nhất định] có nên được áp dụng cho một request nhất định hay không.
Tương tự, chúng ta có thể dùng `requestMatchers` để xác định các quy tắc authorization cần áp dụng cho một request nhất định.
Hãy xem ví dụ sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableWebSecurity
public class SecurityConfig {

	@Bean
	public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
		http
			.securityMatcher("/api/**")                            <1>
			.authorizeHttpRequests((authorize) -> authorize
				.requestMatchers("/api/user/**").hasRole("USER")   <2>
				.requestMatchers("/api/admin/**").hasRole("ADMIN") <3>
				.anyRequest().authenticated()                      <4>
			)
			.formLogin(withDefaults());
		return http.build();
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Configuration
@EnableWebSecurity
open class SecurityConfig {

    @Bean
    open fun web(http: HttpSecurity): SecurityFilterChain {
        http {
            securityMatcher("/api/**")                                           <1>
            authorizeHttpRequests {
                authorize("/api/user/**", hasRole("USER"))                       <2>
                authorize("/api/admin/**", hasRole("ADMIN"))                     <3>
                authorize(anyRequest, authenticated)                             <4>
            }
        }
        return http.build()
    }

}
----
======

<1> Cấu hình `HttpSecurity` chỉ được áp dụng cho các URL bắt đầu bằng `/api/`
<2> Cho phép user có role `USER` truy cập các URL bắt đầu bằng `/api/user/`
<3> Cho phép user có role `ADMIN` truy cập các URL bắt đầu bằng `/api/admin/`
<4> Mọi request khác không khớp với các rule trên sẽ yêu cầu authentication

Các method `securityMatcher(s)` và `requestMatcher(s)` sẽ tạo ``RequestMatcher`` bằng bean javadoc:org.springframework.security.web.servlet.util.matcher.PathPatternRequestMatcher$Builder[], nếu có.
Bạn có thể đọc thêm về tích hợp Spring MVC xref:servlet/integrations/mvc.adoc[tại đây].

Nếu muốn sử dụng một `RequestMatcher` cụ thể, chỉ cần truyền một implementation vào method `securityMatcher` và/hoặc `requestMatcher`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
import static org.springframework.security.web.servlet.util.matcher.PathPatternRequestMatcher.withDefaults; <1>
import static org.springframework.security.web.util.matcher.RegexRequestMatcher.regexMatcher;

@Configuration
@EnableWebSecurity
public class SecurityConfig {

	@Bean
	public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
		http
			.securityMatcher(antMatcher("/api/**"))                              <2>
			.authorizeHttpRequests((authorize) -> authorize
				.requestMatchers(withDefaults().matcher("/api/user/**")).hasRole("USER")     <3>
				.requestMatchers(regexMatcher("/api/admin/.*")).hasRole("ADMIN") <4>
				.requestMatchers(new MyCustomRequestMatcher()).hasRole("SUPERVISOR")     <5>
				.anyRequest().authenticated()
			)
			.formLogin(withDefaults());
		return http.build();
	}
}

public class MyCustomRequestMatcher implements RequestMatcher {

    @Override
    public boolean matches(HttpServletRequest request) {
        // ...
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
import org.springframework.security.web.servlet.util.matcher.PathPatternRequestMatcher.withDefaults <1>
import org.springframework.security.web.util.matcher.RegexRequestMatcher.regexMatcher

@Configuration
@EnableWebSecurity
open class SecurityConfig {

    @Bean
    open fun web(http: HttpSecurity): SecurityFilterChain {
        http {
            securityMatcher(antMatcher("/api/**"))                               <2>
            authorizeHttpRequests {
                authorize(withDefaults().matcher("/api/user/**"), hasRole("USER"))           <3>
                authorize(regexMatcher("/api/admin/**"), hasRole("ADMIN"))       <4>
                authorize(MyCustomRequestMatcher(), hasRole("SUPERVISOR"))       <5>
                authorize(anyRequest, authenticated)
            }
        }
        return http.build()
    }

}
----
======

<1> Import các static factory method từ `PathPatternRequestMatcher` và `RegexRequestMatcher` để tạo instance `RequestMatcher`.
<2> Cấu hình `HttpSecurity` chỉ được áp dụng cho các URL bắt đầu bằng `/api/`, sử dụng `PathPatternRequestMatcher`.
<3> Cho phép user có role `USER` truy cập các URL bắt đầu bằng `/api/user/`, sử dụng `PathPatternRequestMatcher`.
<4> Cho phép user có role `ADMIN` truy cập các URL bắt đầu bằng `/api/admin/`, sử dụng `RegexRequestMatcher`.
<5> Cho phép user có role `SUPERVISOR` truy cập các URL khớp với `MyCustomRequestMatcher`, sử dụng `RequestMatcher` tùy chỉnh.
