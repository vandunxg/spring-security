[[authz-arch]]
= Kiến trúc authorization
:figures: servlet/authorization

Phần này mô tả kiến trúc Spring Security áp dụng cho authorization.

[[authz-authorities]]
== Các authority
xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Authentication`] thảo luận cách mọi triển khai `Authentication` lưu trữ một danh sách các object `GrantedAuthority`.
Các object này đại diện cho những authority đã được cấp cho principal.
Các object `GrantedAuthority` được `AuthenticationManager` đưa vào object `Authentication`, sau đó được các instance `AuthorizationManager` đọc khi đưa ra quyết định authorization.

Interface `GrantedAuthority` chỉ có một method:

[source,java]
----

String getAuthority();

----

Method này được một instance
`AuthorizationManager` sử dụng để lấy biểu diễn `String` chính xác của `GrantedAuthority`.
Bằng cách trả về một biểu diễn dưới dạng `String`, hầu hết các triển khai `AuthorizationManager` có thể dễ dàng "đọc" một `GrantedAuthority`.
Nếu không thể biểu diễn chính xác một `GrantedAuthority` dưới dạng `String`, `GrantedAuthority` được xem là "phức tạp" và `getAuthority()` phải trả về `null`.

Một ví dụ về `GrantedAuthority` phức tạp là một triển khai lưu trữ danh sách các operation và ngưỡng authority áp dụng cho những số tài khoản khách hàng khác nhau.
Việc biểu diễn `GrantedAuthority` phức tạp này dưới dạng `String` sẽ khá khó khăn. Vì vậy, method `getAuthority()` nên trả về `null`.
Điều này cho mọi `AuthorizationManager` biết rằng nó cần hỗ trợ triển khai `GrantedAuthority` cụ thể để hiểu nội dung của nó.

Spring Security bao gồm một triển khai `GrantedAuthority` cụ thể: `SimpleGrantedAuthority`.
Triển khai này cho phép chuyển bất kỳ `String` nào do user chỉ định thành một `GrantedAuthority`.
Mọi instance `AuthenticationProvider` đi kèm kiến trúc security đều sử dụng `SimpleGrantedAuthority` để điền vào object `Authentication`.

[[jc-method-security-custom-granted-authority-defaults]]
Theo mặc định, các rule authorization dựa trên role có `ROLE_` làm prefix.
Điều này có nghĩa là nếu có một rule authorization yêu cầu security context có role là "USER", theo mặc định Spring Security sẽ tìm một `GrantedAuthority#getAuthority` trả về "ROLE_USER".

Bạn có thể tùy chỉnh điều này bằng `GrantedAuthorityDefaults`.
`GrantedAuthorityDefaults` cho phép tùy chỉnh prefix được sử dụng cho các rule authorization dựa trên role.

Bạn có thể cấu hình các rule authorization sử dụng prefix khác bằng cách expose một bean `GrantedAuthorityDefaults`, như sau:

.MethodSecurityExpressionHandler tùy chỉnh
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
static GrantedAuthorityDefaults grantedAuthorityDefaults() {
	return new GrantedAuthorityDefaults("MYPREFIX_");
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
companion object {
	@Bean
	fun grantedAuthorityDefaults() : GrantedAuthorityDefaults {
		return GrantedAuthorityDefaults("MYPREFIX_");
	}
}
----

Xml::
+
[source,xml,role="secondary"]
----
<bean id="grantedAuthorityDefaults" class="org.springframework.security.config.core.GrantedAuthorityDefaults">
	<constructor-arg value="MYPREFIX_"/>
</bean>
----
======

====
Bạn expose `GrantedAuthorityDefaults` bằng một method `static` để đảm bảo Spring publish nó trước khi khởi tạo các class `@Configuration` method security của Spring Security.

[[authz-pre-invocation]]
== Xử lý invocation
Spring Security cung cấp các interceptor kiểm soát quyền truy cập vào các secure object, chẳng hạn như method invocation hoặc web request.
Các instance `AuthorizationManager` đưa ra quyết định trước invocation về việc invocation có được phép tiếp tục hay không.
Các instance `AuthorizationManager` cũng đưa ra quyết định sau invocation về việc có thể trả về một giá trị nhất định hay không.

=== AuthorizationManager
`AuthorizationManager` thay thế cả <<authz-legacy-note,`AccessDecisionManager` và `AccessDecisionVoter`>>.

Các application tùy chỉnh `AccessDecisionManager` hoặc `AccessDecisionVoter` được khuyến khích <<authz-voter-adaptation,chuyển sang sử dụng `AuthorizationManager`>>.

Các ``AuthorizationManager`` được gọi bởi các component authorization xref:servlet/authorization/authorize-http-requests.adoc[dựa trên request], xref:servlet/authorization/method-security.adoc[dựa trên method] và xref:servlet/integrations/websocket.adoc[dựa trên message] của Spring Security, đồng thời chịu trách nhiệm đưa ra quyết định access control cuối cùng.
Interface `AuthorizationManager` chứa hai method:

[source,java]
----
AuthorizationResult authorize(Supplier<Authentication> authentication, Object secureObject);

default void verify(Supplier<Authentication> authentication, Object secureObject)
        throws AccessDeniedException {
    // ...
}
----

Method `authorize` của ``AuthorizationManager`` nhận mọi thông tin liên quan cần thiết để đưa ra quyết định authorization.
Đặc biệt, việc truyền secure `Object` cho phép kiểm tra các argument nằm trong invocation của secure object thực tế.
Ví dụ, giả sử secure object là một `MethodInvocation`.
Bạn có thể dễ dàng truy vấn `MethodInvocation` để tìm bất kỳ argument `Customer` nào, sau đó triển khai một dạng logic security trong `AuthorizationManager` nhằm đảm bảo principal được phép thao tác trên customer đó.
Các triển khai được kỳ vọng trả về một `AuthorizationDecision` dương nếu quyền truy cập được cấp, một `AuthorizationDecision` âm nếu quyền truy cập bị từ chối, và một `AuthorizationDecision` null khi abstain không đưa ra quyết định.

`verify` gọi `authorize` và sau đó ném `AccessDeniedException` nếu `AuthorizationDecision` là âm.

[[authz-delegate-authorization-manager]]
=== Các triển khai AuthorizationManager dựa trên delegate
Mặc dù user có thể tự triển khai `AuthorizationManager` để kiểm soát mọi khía cạnh của authorization, Spring Security cung cấp một `AuthorizationManager` delegating có thể phối hợp với từng ``AuthorizationManager`` riêng lẻ.

`RequestMatcherDelegatingAuthorizationManager` sẽ match request với `AuthorizationManager` delegate phù hợp nhất.
Đối với method security, bạn có thể sử dụng `AuthorizationManagerBeforeMethodInterceptor` và `AuthorizationManagerAfterMethodInterceptor`.

[[authz-authority-authorization-manager]]
==== AuthorityAuthorizationManager
`AuthorizationManager` phổ biến nhất do Spring Security cung cấp là `AuthorityAuthorizationManager`.
Nó được cấu hình với một tập authority cụ thể cần tìm trong `Authentication` hiện tại.
Nó sẽ trả về `AuthorizationDecision` dương nếu `Authentication` chứa bất kỳ authority nào đã cấu hình.
Nếu không, nó sẽ trả về `AuthorizationDecision` âm.

[[authz-authenticated-authorization-manager]]
==== AuthenticatedAuthorizationManager
Một manager khác là `AuthenticatedAuthorizationManager`.
Nó có thể được dùng để phân biệt user anonymous, fully-authenticated và đã xác thực bằng remember-me.
Nhiều site cho phép một số quyền truy cập giới hạn khi authentication bằng remember-me, nhưng yêu cầu user xác nhận danh tính bằng cách đăng nhập để có toàn quyền truy cập.

[[authz-conditional-authorization-manager]]
==== ConditionalAuthorizationManager
javadoc:org.springframework.security.authorization.ConditionalAuthorizationManager[] delegate đến một trong hai ``AuthorizationManager`` dựa trên điều kiện được đánh giá đối với ``Authentication`` hiện tại.
Khi điều kiện trả về true (và authentication khác null), manager ``whenTrue`` được sử dụng; nếu không, manager ``whenFalse`` được sử dụng.
Tạo một instance bằng builder do `ConditionalAuthorizationManager.when(Predicate<Authentication>)` trả về: đặt `whenTrue` (bắt buộc) và tùy chọn `whenFalse` (mặc định là permit-all).
Điều này hữu ích trong các tình huống như chỉ yêu cầu authentication đa yếu tố khi user đã đăng ký factor thứ hai.

[[authz-authorization-manager-factory]]
=== Tạo các instance AuthorizationManager

Interface javadoc:org.springframework.security.authorization.AuthorizationManagerFactory[] (được giới thiệu trong Spring Security 7.0) được sử dụng để tạo các ``AuthorizationManager`` generic trong các component authorization xref:servlet/authorization/authorize-http-requests.adoc[dựa trên request] và xref:servlet/authorization/method-security.adoc[dựa trên method].
Dưới đây là phác thảo của interface `AuthorizationManagerFactory`:

[source,java]
----
public interface AuthorizationManagerFactory<T> {
	AuthorizationManager<T> permitAll();
	AuthorizationManager<T> denyAll();
	AuthorizationManager<T> hasRole(String role);
	AuthorizationManager<T> hasAnyRole(String... roles);
	AuthorizationManager<T> hasAllRoles(String... roles);
	AuthorizationManager<T> hasAuthority(String authority);
	AuthorizationManager<T> hasAnyAuthority(String... authorities);
	AuthorizationManager<T> hasAllAuthorities(String... authorities);
	AuthorizationManager<T> authenticated();
	AuthorizationManager<T> fullyAuthenticated();
	AuthorizationManager<T> rememberMe();
	AuthorizationManager<T> anonymous();
}
----

Triển khai mặc định là javadoc:org.springframework.security.authorization.DefaultAuthorizationManagerFactory[], cho phép tùy chỉnh `rolePrefix` (mặc định là `"ROLE_"`), `RoleHierarchy` và `AuthenticationTrustManager` được cung cấp cho các ``AuthorizationManager`` do factory tạo ra.

Để tùy chỉnh instance mặc định được Spring Security sử dụng, chỉ cần publish một bean như trong ví dụ sau:

[TIP]
Bạn cũng có thể nhắm đến một cách sử dụng cụ thể của factory này trong Spring Security bằng cách cung cấp một kiểu được parameterize cụ thể thay vì kiểu generic.
Xem ví dụ về từng cách trong các phần tài liệu xref:servlet/authorization/authorize-http-requests.adoc#customizing-authorization-managers[dựa trên request] và xref:servlet/authorization/method-security.adoc#customizing-authorization-managers[dựa trên method].

==== AuthorizationManagers
Ngoài ra, javadoc:org.springframework.security.authorization.AuthorizationManagers[] cung cấp các static factory hữu ích để kết hợp từng ``AuthorizationManager`` thành các expression phức tạp hơn.

[[authz-custom-authorization-manager]]
==== AuthorizationManager tùy chỉnh
Tất nhiên, bạn cũng có thể triển khai một `AuthorizationManager` tùy chỉnh và đặt gần như bất kỳ logic access control nào bạn muốn vào đó.
Logic này có thể dành riêng cho application của bạn (liên quan đến business logic) hoặc có thể triển khai một số logic quản trị security.
Ví dụ, bạn có thể tạo một triển khai có thể truy vấn Open Policy Agent hoặc database authorization của riêng mình.

[TIP]
Bạn sẽ tìm thấy một https://spring.io/blog/2009/01/03/spring-security-customization-part-2-adjusting-secured-session-in-real-time[bài viết blog] trên website Spring mô tả cách sử dụng `AccessDecisionVoter` legacy để từ chối quyền truy cập theo thời gian thực đối với user có tài khoản bị đình chỉ.
Bạn có thể đạt được kết quả tương tự bằng cách triển khai `AuthorizationManager`.

[[authz-voter-adaptation]]
== Adapter cho AccessDecisionManager và AccessDecisionVoters

Trước `AuthorizationManager`, Spring Security cung cấp <<authz-legacy-note,`AccessDecisionManager` và `AccessDecisionVoter`>>.

Trong một số trường hợp, chẳng hạn khi migration một application cũ, bạn có thể muốn giới thiệu một `AuthorizationManager` gọi `AccessDecisionManager` hoặc `AccessDecisionVoter`.

Để gọi một `AccessDecisionManager` hiện có, bạn có thể làm như sau:

.Adapter cho AccessDecisionManager
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class AccessDecisionManagerAuthorizationManagerAdapter implements AuthorizationManager {
    private final AccessDecisionManager accessDecisionManager;
    private final SecurityMetadataSource securityMetadataSource;

    @Override
    public AuthorizationResult authorize(Supplier<Authentication> authentication, Object object) {
        try {
            Collection<ConfigAttribute> attributes = this.securityMetadataSource.getAttributes(object);
            this.accessDecisionManager.decide(authentication.get(), object, attributes);
            return new AuthorizationDecision(true);
        } catch (AccessDeniedException ex) {
            return new AuthorizationDecision(false);
        }
    }

    @Override
    public void verify(Supplier<Authentication> authentication, Object object) {
        Collection<ConfigAttribute> attributes = this.securityMetadataSource.getAttributes(object);
        this.accessDecisionManager.decide(authentication.get(), object, attributes);
    }
}
----
======

Sau đó tích hợp nó vào `SecurityFilterChain` của bạn.

Hoặc để chỉ gọi một `AccessDecisionVoter`, bạn có thể làm như sau:

.Adapter cho AccessDecisionVoter
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class AccessDecisionVoterAuthorizationManagerAdapter implements AuthorizationManager {
    private final AccessDecisionVoter accessDecisionVoter;
    private final SecurityMetadataSource securityMetadataSource;

    @Override
    public AuthorizationResult authorize(Supplier<Authentication> authentication, Object object) {
        Collection<ConfigAttribute> attributes = this.securityMetadataSource.getAttributes(object);
        int decision = this.accessDecisionVoter.vote(authentication.get(), object, attributes);
        switch (decision) {
        case ACCESS_GRANTED:
            return new AuthorizationDecision(true);
        case ACCESS_DENIED:
            return new AuthorizationDecision(false);
        }
        return null;
    }
}
----
======

Sau đó tích hợp nó vào `SecurityFilterChain` của bạn.

[[authz-hierarchical-roles]]
== Role phân cấp
Một yêu cầu phổ biến là một role cụ thể trong application phải tự động "bao gồm" các role khác.
Ví dụ, trong một application có khái niệm role "admin" và "user", bạn có thể muốn admin làm được mọi thứ mà user thông thường có thể làm.
Để đạt được điều này, bạn có thể đảm bảo mọi admin user cũng được gán role "user".
Ngoài ra, bạn có thể sửa mọi access constraint yêu cầu role "user" để cũng bao gồm role "admin".
Điều này có thể trở nên khá phức tạp nếu application của bạn có nhiều role khác nhau.

Việc sử dụng role hierarchy cho phép bạn cấu hình role (hoặc authority) nào sẽ bao gồm role khác.
Tính năng này được hỗ trợ cho authorization dựa trên filter trong `HttpSecurity#authorizeHttpRequests` và cho authorization dựa trên method thông qua `DefaultMethodSecurityExpressionHandler` đối với annotation pre-post, `SecuredAuthorizationManager` đối với `@Secured`, và `Jsr250AuthorizationManager` đối với annotation JSR-250.
Bạn có thể cấu hình hành vi cho tất cả chúng cùng lúc như sau:

.Cấu hình role phân cấp
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
static RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.withDefaultRolePrefix()
        .role("ADMIN").implies("STAFF")
        .role("STAFF").implies("USER")
        .role("USER").implies("GUEST")
        .build();
}

// and, if using pre-post method security also add
@Bean
static MethodSecurityExpressionHandler methodSecurityExpressionHandler(RoleHierarchy roleHierarchy) {
	DefaultMethodSecurityExpressionHandler expressionHandler = new DefaultMethodSecurityExpressionHandler();
	expressionHandler.setRoleHierarchy(roleHierarchy);
	return expressionHandler;
}
----

Xml::
+
[source,java,role="secondary"]
----
<bean id="roleHierarchy"
		class="org.springframework.security.access.hierarchicalroles.RoleHierarchyImpl" factory-method="fromHierarchy">
	<constructor-arg>
		<value>
			ROLE_ADMIN > ROLE_STAFF
			ROLE_STAFF > ROLE_USER
			ROLE_USER > ROLE_GUEST
		</value>
	</constructor-arg>
</bean>

<!-- and, if using method security also add -->
<bean id="methodSecurityExpressionHandler"
        class="org.springframework.security.access.expression.method.MethodSecurityExpressionHandler">
    <property ref="roleHierarchy"/>
</bean>
----
======

Ở đây chúng ta có bốn role trong hierarchy `ROLE_ADMIN => ROLE_STAFF => ROLE_USER => ROLE_GUEST`.
Một user được authentication với `ROLE_ADMIN` sẽ hoạt động như thể có cả bốn role khi các security constraint được đánh giá đối với bất kỳ rule nào dựa trên filter hoặc method.

[TIP]
Có thể hiểu ký hiệu `>` là "bao gồm".

Role hierarchy cung cấp một cách thuận tiện để đơn giản hóa dữ liệu cấu hình access control cho application của bạn và/hoặc giảm số lượng authority cần gán cho user.
Đối với các yêu cầu phức tạp hơn, bạn có thể muốn xác định ánh xạ logic giữa các quyền truy cập cụ thể mà application yêu cầu và các role được gán cho user, chuyển đổi giữa hai bên khi tải thông tin user.

[[authz-access-decision-manager]]
=== AccessDecisionManager
`AccessDecisionManager` được `AbstractSecurityInterceptor` gọi và chịu trách nhiệm đưa ra các quyết định access control cuối cùng.
Interface `AccessDecisionManager` chứa ba method:

[source,java]
----
void decide(Authentication authentication, Object secureObject,
	Collection<ConfigAttribute> attrs) throws AccessDeniedException;

boolean supports(ConfigAttribute attribute);

boolean supports(Class clazz);
----

Method `decide` của `AccessDecisionManager` nhận mọi thông tin liên quan cần thiết để đưa ra quyết định authorization.
Đặc biệt, việc truyền secure `Object` cho phép kiểm tra các argument nằm trong invocation của secure object thực tế.
Ví dụ, giả sử secure object là một `MethodInvocation`.
Bạn có thể truy vấn `MethodInvocation` để tìm bất kỳ argument `Customer` nào, sau đó triển khai một dạng logic security trong `AccessDecisionManager` nhằm đảm bảo principal được phép thao tác trên customer đó.
Các triển khai được kỳ vọng ném `AccessDeniedException` nếu quyền truy cập bị từ chối.

Method `supports(ConfigAttribute)` được `AbstractSecurityInterceptor` gọi lúc startup để xác định `AccessDecisionManager` có thể xử lý `ConfigAttribute` được truyền vào hay không.
Method `supports(Class)` được một triển khai security interceptor gọi để đảm bảo `AccessDecisionManager` đã cấu hình hỗ trợ kiểu secure object mà security interceptor cung cấp.

Với cách tiếp cận này, một chuỗi các triển khai `AccessDecisionVoter` được thăm dò khi đưa ra quyết định authorization.
Sau đó, `AccessDecisionManager` quyết định có ném `AccessDeniedException` hay không dựa trên đánh giá các phiếu bầu.

Interface `AccessDecisionVoter` có ba method:

[source,java]
----
int vote(Authentication authentication, Object object, Collection<ConfigAttribute> attrs);

boolean supports(ConfigAttribute attribute);

boolean supports(Class clazz);
----

Các triển khai cụ thể trả về một `int`, với các giá trị khả dĩ được phản ánh trong những field static của `AccessDecisionVoter` có tên `ACCESS_ABSTAIN`, `ACCESS_DENIED` và `ACCESS_GRANTED`.
Một triển khai bỏ phiếu trả về `ACCESS_ABSTAIN` nếu không có ý kiến về quyết định authorization.
Nếu có ý kiến, nó phải trả về `ACCESS_DENIED` hoặc `ACCESS_GRANTED`.

Spring Security cung cấp ba triển khai `AccessDecisionManager` cụ thể để tổng hợp các phiếu bầu.
Triển khai `ConsensusBased` cấp hoặc từ chối quyền truy cập dựa trên sự đồng thuận của các phiếu không abstain.
Các property được cung cấp để kiểm soát hành vi khi số phiếu bằng nhau hoặc khi tất cả phiếu đều abstain.
Triển khai `AffirmativeBased` cấp quyền truy cập nếu nhận được một hoặc nhiều phiếu `ACCESS_GRANTED` (nói cách khác, phiếu từ chối sẽ bị bỏ qua nếu có ít nhất một phiếu cấp quyền).
Giống triển khai `ConsensusBased`, có một parameter kiểm soát hành vi nếu mọi voter đều abstain.
Provider `UnanimousBased` yêu cầu các phiếu `ACCESS_GRANTED` nhất trí để cấp quyền truy cập và bỏ qua các phiếu abstain.
Nó từ chối quyền truy cập nếu có bất kỳ phiếu `ACCESS_DENIED` nào.
Giống các triển khai khác, có một parameter kiểm soát hành vi nếu mọi voter đều abstain.

Bạn có thể triển khai một `AccessDecisionManager` tùy chỉnh để tổng hợp phiếu theo cách khác.
Ví dụ, phiếu từ một `AccessDecisionVoter` cụ thể có thể được tính trọng số bổ sung, trong khi phiếu từ một voter cụ thể có thể có hiệu lực phủ quyết.

[[authz-role-voter]]
==== RoleVoter
`AccessDecisionVoter` được sử dụng phổ biến nhất do Spring Security cung cấp là `RoleVoter`, coi các configuration attribute là tên role và bỏ phiếu cấp quyền truy cập nếu user được gán role đó.

Voter này bỏ phiếu nếu bất kỳ `ConfigAttribute` nào bắt đầu bằng prefix `ROLE_`.
Nó bỏ phiếu cấp quyền truy cập nếu có một `GrantedAuthority` trả về biểu diễn `String` (từ method `getAuthority()`) khớp chính xác với một hoặc nhiều `ConfigAttribute` bắt đầu bằng prefix `ROLE_`.
Nếu không có `ConfigAttribute` nào bắt đầu bằng `ROLE_` khớp chính xác, `RoleVoter` bỏ phiếu từ chối quyền truy cập.
Nếu không có `ConfigAttribute` nào bắt đầu bằng `ROLE_`, voter abstain.


[[authz-authenticated-voter]]
==== AuthenticatedVoter
Một voter khác mà chúng ta đã thấy một cách ngầm định là `AuthenticatedVoter`, có thể được sử dụng để phân biệt user anonymous, fully-authenticated và đã xác thực bằng remember-me.
Nhiều site cho phép một số quyền truy cập giới hạn khi authentication bằng remember-me nhưng yêu cầu user xác nhận danh tính bằng cách đăng nhập để có toàn quyền truy cập.

Khi chúng ta sử dụng attribute `IS_AUTHENTICATED_ANONYMOUSLY` để cấp quyền truy cập anonymous, attribute này được `AuthenticatedVoter` xử lý.
Để biết thêm thông tin, xem
javadoc:org.springframework.security.access.vote.AuthenticatedVoter[].


[[authz-custom-voter]]
==== Voter tùy chỉnh
Bạn cũng có thể triển khai một `AccessDecisionVoter` tùy chỉnh và đặt gần như bất kỳ logic access control nào bạn muốn vào đó.
Logic này có thể dành riêng cho application của bạn (liên quan đến business logic) hoặc có thể triển khai một số logic quản trị security.
Ví dụ, trên website Spring có một https://spring.io/blog/2009/01/03/spring-security-customization-part-2-adjusting-secured-session-in-real-time[bài viết blog] mô tả cách sử dụng voter để từ chối quyền truy cập theo thời gian thực đối với user có tài khoản bị đình chỉ.

[[authz-after-invocation]]
.Triển khai sau invocation
[.invert-dark]
image::{figures}/after-invocation.png[]

Giống nhiều phần khác của Spring Security, `AfterInvocationManager` có một triển khai cụ thể duy nhất là `AfterInvocationProviderManager`, triển khai này thăm dò một danh sách các ``AfterInvocationProvider``.
Mỗi `AfterInvocationProvider` được phép sửa đổi object được trả về hoặc ném `AccessDeniedException`.
Thực tế, nhiều provider có thể sửa đổi object, vì kết quả của provider trước được truyền cho provider tiếp theo trong danh sách.

Hãy lưu ý rằng nếu đang sử dụng `AfterInvocationManager`, bạn vẫn cần các configuration attribute cho phép `AccessDecisionManager` của ``MethodSecurityInterceptor`` cho phép một operation.
Nếu đang sử dụng các triển khai `AccessDecisionManager` điển hình đi kèm Spring Security, việc không định nghĩa configuration attribute nào cho một method invocation bảo mật cụ thể sẽ khiến mỗi `AccessDecisionVoter` abstain khi bỏ phiếu.
Do đó, nếu property "`allowIfAllAbstainDecisions`" của `AccessDecisionManager` là `false`, một `AccessDeniedException` sẽ bị ném.
Bạn có thể tránh vấn đề tiềm ẩn này bằng một trong hai cách: (i) đặt "`allowIfAllAbstainDecisions`" thành `true` (mặc dù nhìn chung không được khuyến nghị), hoặc (ii) chỉ cần đảm bảo có ít nhất một configuration attribute mà `AccessDecisionVoter` sẽ bỏ phiếu cấp quyền truy cập.
Cách thứ hai (được khuyến nghị) thường đạt được thông qua configuration attribute `ROLE_USER` hoặc `ROLE_AUTHENTICATED`.
