[[jc-method]]
= Method Security
:figures: servlet/authorization

Ngoài việc xref:servlet/authorization/authorize-http-requests.adoc[mô hình hóa authorization ở cấp request], Spring Security cũng hỗ trợ mô hình hóa ở cấp method.

[[activate-method-security]]
Bạn có thể kích hoạt tính năng này trong ứng dụng bằng cách gắn `@EnableMethodSecurity` lên bất kỳ class `@Configuration` nào hoặc thêm `<method-security>` vào bất kỳ file cấu hình XML nào, như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@EnableMethodSecurity
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@EnableMethodSecurity
----

Xml::
+
[source,xml,role="secondary"]
----
<sec:method-security/>
----
======

Sau đó, bạn có thể ngay lập tức gắn <<use-preauthorize, `@PreAuthorize`>>, <<use-postauthorize,`@PostAuthorize`>>, <<use-prefilter,`@PreFilter`>> và <<use-postfilter,`@PostFilter`>> lên bất kỳ class hoặc method do Spring quản lý nào để thực hiện authorization cho các lần gọi method, bao gồm cả tham số đầu vào và giá trị trả về.

[NOTE]
{spring-boot-reference-url}reference/using/build-systems.html#using.build-systems.starters[Spring Boot Starter Security] không kích hoạt authorization ở cấp method theo mặc định.

Method Security cũng hỗ trợ nhiều trường hợp sử dụng khác, bao gồm <<use-aspectj, hỗ trợ AspectJ>>, <<use-programmatic-authorization,annotation tùy chỉnh>> và một số điểm cấu hình.
Bạn nên tìm hiểu các trường hợp sử dụng sau:

* <<migration-enableglobalmethodsecurity,Di chuyển từ `@EnableGlobalMethodSecurity`>>
* Tìm hiểu <<method-security-architecture,cách method security hoạt động>> và lý do sử dụng nó
* So sánh <<request-vs-method,authorization ở cấp request và cấp method>>
* Thực hiện authorization cho method bằng <<use-preauthorize,`@PreAuthorize`>> và <<use-postauthorize,`@PostAuthorize`>>
* Cung cấp <<fallback-values-authorization-denied,giá trị dự phòng khi authorization bị từ chối>>
* Lọc method bằng <<use-prefilter,`@PreFilter`>> và <<use-postfilter,`@PostFilter`>>
* Thực hiện authorization cho method bằng <<use-jsr250,annotation JSR-250>>
* Thực hiện authorization cho method bằng <<use-aspectj,biểu thức AspectJ>>
* Tích hợp với <<weave-aspectj,weaving byte-code bằng AspectJ>>
* Phối hợp với <<changing-the-order,@Transactional và các annotation dựa trên AOP khác>>
* Tùy chỉnh <<customizing-expression-handling,cách xử lý biểu thức SpEL>>
* Tích hợp với <<custom-authorization-managers,hệ thống authorization tùy chỉnh>>

[[method-security-architecture]]
== Method Security Hoạt động Như thế nào

Tính năng hỗ trợ authorization cho method của Spring Security hữu ích trong các trường hợp:

* Tách riêng logic authorization chi tiết; ví dụ khi các tham số method và giá trị trả về góp phần vào quyết định authorization.
* Thực thi security ở service layer
* Ưu tiên cấu hình dựa trên annotation thay vì cấu hình dựa trên `HttpSecurity` về mặt phong cách

Và vì Method Security được xây dựng bằng {spring-framework-reference-url}core.html#aop-api[Spring AOP], bạn có thể tận dụng toàn bộ khả năng biểu đạt của nó để ghi đè các giá trị mặc định của Spring Security khi cần.

Như đã đề cập, bạn bắt đầu bằng cách thêm `@EnableMethodSecurity` vào một class `@Configuration` hoặc `<sec:method-security/>` vào file cấu hình XML của Spring.

[[use-method-security]]
[NOTE]
====
Annotation và phần tử XML này thay thế `@EnableGlobalMethodSecurity` và `<sec:global-method-security/>` tương ứng.
Chúng mang lại các cải tiến sau:

1. Sử dụng API `AuthorizationManager` đơn giản hóa thay cho metadata source, config attribute, decision manager và voter.
Điều này đơn giản hóa việc tái sử dụng và tùy chỉnh.
2. Ưu tiên cấu hình trực tiếp dựa trên bean thay vì yêu cầu mở rộng `GlobalMethodSecurityConfiguration` để tùy chỉnh bean
3. Được xây dựng bằng Spring AOP nguyên bản, loại bỏ các abstraction và cho phép bạn sử dụng các khối xây dựng của Spring AOP để tùy chỉnh
4. Kiểm tra các annotation xung đột để bảo đảm cấu hình security không mơ hồ
5. Tuân thủ JSR-250
6. Mặc định kích hoạt `@PreAuthorize`, `@PostAuthorize`, `@PreFilter` và `@PostFilter`

Nếu bạn đang sử dụng `@EnableGlobalMethodSecurity` hoặc `<global-method-security/>`, chúng hiện đã deprecated và bạn nên di chuyển sang cách mới.
====

Authorization cho method là sự kết hợp giữa authorization trước method và sau method.
Hãy xem một service bean được gắn annotation như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Service
public class MyCustomerService {
    @PreAuthorize("hasAuthority('permission:read')")
    @PostAuthorize("returnObject.owner == authentication.name")
    public Customer readCustomer(String id) { ... }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Service
open class MyCustomerService {
    @PreAuthorize("hasAuthority('permission:read')")
    @PostAuthorize("returnObject.owner == authentication.name")
    fun readCustomer(id: String): Customer { ... }
}
----
======

Một lần gọi `MyCustomerService#readCustomer` có thể diễn ra như sau khi Method Security <<activate-method-security,được kích hoạt>>:

[.invert-dark]
image::{figures}/methodsecurity.png[]

1. Spring AOP gọi method proxy cho `readCustomer`. Trong số các advisor khác của proxy, nó gọi javadoc:org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor[] khớp với <<annotation-method-pointcuts,pointcut `@PreAuthorize`>>
2. Interceptor gọi javadoc:org.springframework.security.authorization.method.PreAuthorizeAuthorizationManager[`PreAuthorizeAuthorizationManager#authorize`]
3. Authorization manager sử dụng `MethodSecurityExpressionHandler` để phân tích <<authorization-expressions,biểu thức SpEL>> của annotation và xây dựng `EvaluationContext` tương ứng từ một `MethodSecurityExpressionRoot` chứa xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Supplier<Authentication>`] và `MethodInvocation`.
4. Interceptor sử dụng context này để đánh giá biểu thức; cụ thể, nó đọc xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Authentication`] từ `Supplier` và kiểm tra xem nó có `permission:read` trong tập hợp xref:servlet/authorization/architecture.adoc#authz-authorities[các authority] hay không
5. Nếu việc đánh giá thành công, Spring AOP tiếp tục gọi method.
6. Nếu không, interceptor phát hành `AuthorizationDeniedEvent` và ném javadoc:org.springframework.security.access.AccessDeniedException[], exception này được xref:servlet/architecture.adoc#servlet-exceptiontranslationfilter[`ExceptionTranslationFilter`] bắt và trả về status code 403 cho response
7. Sau khi method trả về, Spring AOP gọi javadoc:org.springframework.security.authorization.method.AuthorizationManagerAfterMethodInterceptor[] khớp với <<annotation-method-pointcuts,pointcut `@PostAuthorize`>>, hoạt động giống như trên nhưng sử dụng javadoc:org.springframework.security.authorization.method.PostAuthorizeAuthorizationManager[]
8. Nếu việc đánh giá thành công (trong trường hợp này, giá trị trả về thuộc về người dùng đã đăng nhập), quá trình tiếp tục bình thường
9. Nếu không, interceptor phát hành `AuthorizationDeniedEvent` và ném javadoc:org.springframework.security.access.AccessDeniedException[], exception này được xref:servlet/architecture.adoc#servlet-exceptiontranslationfilter[`ExceptionTranslationFilter`] bắt và trả về status code 403 cho response

[NOTE]
Nếu method không được gọi trong context của một HTTP request, có thể bạn sẽ cần tự xử lý `AccessDeniedException`

[[unanimous-based-authorization-decisions]]
=== Nhiều Annotation Được Tính Tuần Tự

Như minh họa ở trên, nếu một lần gọi method liên quan đến nhiều <<authorizing-with-annotations,annotation Method Security>>, mỗi annotation sẽ được xử lý lần lượt.
Điều này có nghĩa là về tổng thể, chúng được kết hợp bằng phép "and".
Nói cách khác, để một lần gọi được authorization, tất cả các lần kiểm tra annotation đều phải vượt qua authorization.

[[repeated-annotations]]
=== Không Hỗ Trợ Annotation Lặp Lại

Tuy nhiên, không hỗ trợ lặp lại cùng một annotation trên cùng một method.
Ví dụ, bạn không thể đặt `@PreAuthorize` hai lần trên cùng một method.

Thay vào đó, hãy sử dụng khả năng hỗ trợ boolean của SpEL hoặc khả năng ủy quyền cho một bean riêng biệt.

[[annotation-method-pointcuts]]
=== Mỗi Annotation Có Pointcut Riêng

Mỗi annotation có một instance pointcut riêng để tìm annotation đó hoặc các <<meta-annotations,meta-annotation>> tương ứng trong toàn bộ hierarchy của object, bắt đầu từ <<class-or-interface-annotations,method và class bao quanh nó>>.

[[annotation-method-interceptors]]
=== Mỗi Annotation Có Method Interceptor Riêng

Mỗi annotation có method interceptor chuyên dụng riêng.
Lý do là để các thành phần có thể kết hợp với nhau dễ dàng hơn.
Ví dụ, nếu cần, bạn có thể tắt các giá trị mặc định của Spring Security và <<_enabling_certain_annotations,chỉ publish method interceptor `@PostAuthorize`>>.

Các method interceptor như sau:

* Với <<use-preauthorize,`@PreAuthorize`>>, Spring Security sử dụng javadoc:org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor[`AuthorizationManagerBeforeMethodInterceptor#preAuthorize`], interceptor này lần lượt sử dụng javadoc:org.springframework.security.authorization.method.PreAuthorizeAuthorizationManager[]
* Với <<use-postauthorize,`@PostAuthorize`>>, Spring Security sử dụng javadoc:org.springframework.security.authorization.method.AuthorizationManagerAfterMethodInterceptor[`AuthorizationManagerAfterMethodInterceptor#postAuthorize`], interceptor này lần lượt sử dụng javadoc:org.springframework.security.authorization.method.PostAuthorizeAuthorizationManager[]
* Với <<use-prefilter,`@PreFilter`>>, Spring Security sử dụng javadoc:org.springframework.security.authorization.method.PreFilterAuthorizationMethodInterceptor[]
* Với <<use-postfilter,`@PostFilter`>>, Spring Security sử dụng javadoc:org.springframework.security.authorization.method.PostFilterAuthorizationMethodInterceptor[]
* Với <<use-secured,`@Secured`>>, Spring Security sử dụng javadoc:org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor[`AuthorizationManagerBeforeMethodInterceptor#secured`], interceptor này lần lượt sử dụng javadoc:org.springframework.security.authorization.method.SecuredAuthorizationManager[]
* Với annotation JSR-250, Spring Security sử dụng javadoc:org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor[`AuthorizationManagerBeforeMethodInterceptor#jsr250`], interceptor này lần lượt sử dụng javadoc:org.springframework.security.authorization.method.Jsr250AuthorizationManager[]

Nói chung, bạn có thể xem đoạn code sau là đại diện cho các interceptor mà Spring Security publish khi bạn thêm `@EnableMethodSecurity`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
static Advisor preAuthorizeMethodInterceptor() {
    return AuthorizationManagerBeforeMethodInterceptor.preAuthorize();
}

@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
static Advisor postAuthorizeMethodInterceptor() {
    return AuthorizationManagerAfterMethodInterceptor.postAuthorize();
}

@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
static Advisor preFilterMethodInterceptor() {
    return AuthorizationManagerBeforeMethodInterceptor.preFilter();
}

@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
static Advisor postFilterMethodInterceptor() {
    return AuthorizationManagerAfterMethodInterceptor.postFilter();
}
----
======

Bạn thường dễ muốn đưa vào một biểu thức SpEL phức tạp như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@PreAuthorize("hasAuthority('permission:read') || hasRole('ADMIN')")

Kotlin::

Tuy nhiên, thay vào đó bạn có thể cấp `permission:read` cho những người có `ROLE_ADMIN`.
Một cách để làm điều này là sử dụng `RoleHierarchy` như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
static RoleHierarchy roleHierarchy() {
    return RoleHierarchyImpl.fromHierarchy("ROLE_ADMIN > permission:read");
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
companion object {
    @Bean
    fun roleHierarchy(): RoleHierarchy {
        return RoleHierarchyImpl.fromHierarchy("ROLE_ADMIN > permission:read")
    }
}
----

Xml::
+
[source,xml,role="secondary"]
----
<bean id="roleHierarchy"
        class="org.springframework.security.access.hierarchicalroles.RoleHierarchyImpl" factory-method="fromHierarchy">
    <constructor-arg value="ROLE_ADMIN > permission:read"/>
</bean>
----
======

và sau đó <<customizing-expression-handling,đặt nó vào một instance `MethodSecurityExpressionHandler`>>.
Khi đó, bạn có thể sử dụng biểu thức <<use-preauthorize,`@PreAuthorize`>> đơn giản hơn như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@PreAuthorize("hasAuthority('permission:read')")
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@PreAuthorize("hasAuthority('permission:read')")
----
======

Hoặc, nếu có thể, hãy chuyển logic authorization riêng của ứng dụng thành các authority được cấp tại thời điểm login.

[[request-vs-method]]
== So sánh Authorization ở Cấp Request và Cấp Method

Khi nào nên ưu tiên authorization ở cấp method thay cho xref:servlet/authorization/authorize-http-requests.adoc[authorization ở cấp request]?
Một phần phụ thuộc vào sở thích; tuy nhiên, hãy cân nhắc danh sách ưu điểm sau của mỗi cách để đưa ra quyết định.

|===
|| *request-level* | *method-level*
| *loại authorization* | coarse-grained | fine-grained
| *vị trí cấu hình* | khai báo trong một config class | cục bộ tại khai báo method
| *phong cách cấu hình* | DSL | Annotation
| *định nghĩa authorization* | programmatic | SpEL
|===

Đánh đổi chính dường như nằm ở nơi bạn muốn đặt các quy tắc authorization.

[NOTE]
Điều quan trọng cần nhớ là khi sử dụng Method Security dựa trên annotation, các method không có annotation sẽ không được bảo vệ.
Để bảo vệ khỏi điều này, hãy khai báo xref:servlet/authorization/authorize-http-requests.adoc#activate-request-security[một quy tắc authorization bao quát] trong instance xref:servlet/configuration/java.adoc#jc-httpsecurity[`HttpSecurity`].

[[authorizing-with-annotations]]
== Thực hiện Authorization bằng Annotation

Cách chính để Spring Security hỗ trợ authorization ở cấp method là thông qua các annotation mà bạn có thể thêm vào method, class và interface.

[[use-preauthorize]]
=== Thực hiện Authorization cho Lần Gọi Method bằng `@PreAuthorize`

Khi <<activate-method-security,Method Security đang hoạt động>>, bạn có thể gắn annotation javadoc:org.springframework.security.access.prepost.PreAuthorize[format=annotation] lên một method như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class BankService {
	@PreAuthorize("hasRole('ADMIN')")
	public Account readAccount(Long id) {
        // ... is only invoked if the `Authentication` has the `ROLE_ADMIN` authority
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
open class BankService {
	@PreAuthorize("hasRole('ADMIN')")
	fun readAccount(id: Long): Account {
        // ... is only invoked if the `Authentication` has the `ROLE_ADMIN` authority
	}
}
----
======

Điều này cho biết method chỉ có thể được gọi nếu biểu thức được cung cấp `hasRole('ADMIN')` cho kết quả đạt.

Sau đó, bạn có thể xref:servlet/test/method.adoc[kiểm thử class] để xác nhận class thực thi quy tắc authorization như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Autowired
BankService bankService;

@WithMockUser(roles="ADMIN")
@Test
void readAccountWithAdminRoleThenInvokes() {
    Account account = this.bankService.readAccount("12345678");
    // ... assertions
}

@WithMockUser(roles="WRONG")
@Test
void readAccountWithWrongRoleThenAccessDenied() {
    assertThatExceptionOfType(AccessDeniedException.class).isThrownBy(
        () -> this.bankService.readAccount("12345678"));
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@WithMockUser(roles="ADMIN")
@Test
fun readAccountWithAdminRoleThenInvokes() {
    val account: Account = this.bankService.readAccount("12345678")
    // ... assertions
}

@WithMockUser(roles="WRONG")
@Test
fun readAccountWithWrongRoleThenAccessDenied() {
    assertThatExceptionOfType(AccessDeniedException::class.java).isThrownBy {
        this.bankService.readAccount("12345678")
    }
}
----
======

[TIP]
`@PreAuthorize` cũng có thể là một <<meta-annotations, meta-annotation>>, được định nghĩa <<class-or-interface-annotations,ở cấp class hoặc interface>> và sử dụng <<authorization-expressions,biểu thức Authorization SpEL>>.

Mặc dù `@PreAuthorize` rất hữu ích để khai báo các authority cần thiết, nó cũng có thể được dùng để đánh giá các <<using_method_parameters,biểu thức phức tạp hơn có sử dụng tham số method>>.

[[use-postauthorize]]
=== Thực hiện Authorization cho Kết quả Method bằng `@PostAuthorize`

Khi Method Security đang hoạt động, bạn có thể gắn annotation javadoc:org.springframework.security.access.prepost.PostAuthorize[format=annotation] lên một method như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class BankService {
	@PostAuthorize("returnObject.owner == authentication.name")
	public Account readAccount(Long id) {
        // ... is only returned if the `Account` belongs to the logged in user
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
open class BankService {
	@PostAuthorize("returnObject.owner == authentication.name")
	fun readAccount(id: Long): Account {
        // ... is only returned if the `Account` belongs to the logged in user
	}
}
----
======

Điều này cho biết method chỉ có thể trả về giá trị nếu biểu thức được cung cấp `returnObject.owner == authentication.name` cho kết quả đạt.
`returnObject` đại diện cho object `Account` sẽ được trả về.

Sau đó, bạn có thể xref:servlet/test/method.adoc[kiểm thử class] để xác nhận class thực thi quy tắc authorization:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Autowired
BankService bankService;

@WithMockUser(username="owner")
@Test
void readAccountWhenOwnedThenReturns() {
    Account account = this.bankService.readAccount("12345678");
    // ... assertions
}

@WithMockUser(username="wrong")
@Test
void readAccountWhenNotOwnedThenAccessDenied() {
    assertThatExceptionOfType(AccessDeniedException.class).isThrownBy(
        () -> this.bankService.readAccount("12345678"));
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@WithMockUser(username="owner")
@Test
fun readAccountWhenOwnedThenReturns() {
    val account: Account = this.bankService.readAccount("12345678")
    // ... assertions
}

@WithMockUser(username="wrong")
@Test
fun readAccountWhenNotOwnedThenAccessDenied() {
    assertThatExceptionOfType(AccessDeniedException::class.java).isThrownBy {
        this.bankService.readAccount("12345678")
    }
}
----
======

[TIP]
`@PostAuthorize` cũng có thể là một <<meta-annotations,meta-annotation>>, được định nghĩa <<class-or-interface-annotations,ở cấp class hoặc interface>> và sử dụng <<authorization-expressions,biểu thức Authorization SpEL>>.

`@PostAuthorize` đặc biệt hữu ích khi phòng chống https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html[Insecure Direct Object Reference].
Thực tế, bạn có thể định nghĩa nó thành một <<meta-annotations,meta-annotation>> như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Target({ ElementType.METHOD, ElementType.TYPE })
@Retention(RetentionPolicy.RUNTIME)
@PostAuthorize("returnObject.owner == authentication.name")
public @interface RequireOwnership {}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Target(ElementType.METHOD, ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@PostAuthorize("returnObject.owner == authentication.name")
annotation class RequireOwnership
----
======

Nhờ đó, bạn có thể gắn annotation lên service theo cách sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class BankService {
	@RequireOwnership
	public Account readAccount(Long id) {
        // ... is only returned if the `Account` belongs to the logged in user
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
open class BankService {
	@RequireOwnership
	fun readAccount(id: Long): Account {
        // ... is only returned if the `Account` belongs to the logged in user
	}
}
----
======

Kết quả là method ở trên chỉ trả về `Account` nếu attribute `owner` của nó khớp với `name` của người dùng đã đăng nhập.
Nếu không, Spring Security sẽ ném `AccessDeniedException` và trả về status code 403.

[NOTE]
=====
Lưu ý rằng `@PostAuthorize` không được khuyến nghị cho các class thực hiện ghi vào database vì điều đó thường có nghĩa là thay đổi database đã xảy ra trước khi các invariant về security được kiểm tra.
Một ví dụ phổ biến là khi bạn có `@Transactional` và `@PostAuthorize` trên cùng một method.
Thay vào đó, trước tiên hãy đọc giá trị bằng cách sử dụng `@PostAuthorize` cho thao tác đọc, rồi thực hiện ghi vào database nếu thao tác đọc đó được authorization.
Nếu bắt buộc phải làm như vậy, bạn có thể <<changing-the-order,đảm bảo `@EnableTransactionManagement` đứng trước `@EnableMethodSecurity`>>.
=====

[[use-prefilter]]
=== Lọc Tham số Method bằng `@PreFilter`

Khi Method Security đang hoạt động, bạn có thể gắn annotation javadoc:org.springframework.security.access.prepost.PreFilter[format=annotation] lên một method như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class BankService {
	@PreFilter("filterObject.owner == authentication.name")
	public Collection<Account> updateAccounts(Account... accounts) {
        // ... `accounts` will only contain the accounts owned by the logged-in user
        return updated;
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
open class BankService {
	@PreFilter("filterObject.owner == authentication.name")
	fun updateAccounts(vararg accounts: Account): Collection<Account> {
        // ... `accounts` will only contain the accounts owned by the logged-in user
        return updated
	}
}
----
======

Điều này nhằm lọc ra khỏi `accounts` mọi giá trị mà biểu thức `filterObject.owner == authentication.name` cho kết quả không đạt.
`filterObject` đại diện cho từng `account` trong `accounts` và được dùng để kiểm tra từng `account`.

Sau đó, bạn có thể kiểm thử class theo cách sau để xác nhận class thực thi quy tắc authorization:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Autowired
BankService bankService;

@WithMockUser(username="owner")
@Test
void updateAccountsWhenOwnedThenReturns() {
    Account ownedBy = ...
    Account notOwnedBy = ...
    Collection<Account> updated = this.bankService.updateAccounts(ownedBy, notOwnedBy);
    assertThat(updated).containsOnly(ownedBy);
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Autowired
lateinit var bankService: BankService

@WithMockUser(username="owner")
@Test
fun updateAccountsWhenOwnedThenReturns() {
    val ownedBy: Account = ...
    val notOwnedBy: Account = ...
    val updated: Collection<Account> = bankService.updateAccounts(ownedBy, notOwnedBy)
    assertThat(updated).containsOnly(ownedBy)
}
----
======

[TIP]
`@PreFilter` cũng có thể là một <<meta-annotations,meta-annotation>>, được định nghĩa <<class-or-interface-annotations,ở cấp class hoặc interface>> và sử dụng <<authorization-expressions,biểu thức Authorization SpEL>>.

`@PreFilter` hỗ trợ array, collection, map và stream (miễn là stream vẫn đang mở).

Ví dụ, khai báo `updateAccounts` ở trên sẽ hoạt động giống như bốn khai báo sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@PreFilter("filterObject.owner == authentication.name")
public Collection<Account> updateAccounts(Account[] accounts)

@PreFilter("filterObject.owner == authentication.name")
public Collection<Account> updateAccounts(Collection<Account> accounts)

@PreFilter("filterObject.value.owner == authentication.name")
public Collection<Account> updateAccounts(Map<String, Account> accounts)

@PreFilter("filterObject.owner == authentication.name")
public Collection<Account> updateAccounts(Stream<Account> accounts)
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@PreFilter("filterObject.owner == authentication.name")
fun updateAccounts(accounts: Array<Account>): Collection<Account>

@PreFilter("filterObject.owner == authentication.name")
fun updateAccounts(accounts: Collection<Account>): Collection<Account>

@PreFilter("filterObject.value.owner == authentication.name")
fun updateAccounts(accounts: Map<String, Account>): Collection<Account>

@PreFilter("filterObject.owner == authentication.name")
fun updateAccounts(accounts: Stream<Account>): Collection<Account>
----
======

Kết quả là method ở trên chỉ có các instance `Account` mà attribute `owner` của chúng khớp với `name` của người dùng đã đăng nhập.

[[use-secured]]

Để sử dụng annotation `@Secured`, trước tiên bạn cần thay đổi khai báo Method Security để kích hoạt nó như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@EnableMethodSecurity(securedEnabled = true)
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@EnableMethodSecurity(securedEnabled = true)
----

Xml::
+
[source,xml,role="secondary"]
----

----
======

Điều này khiến Spring Security publish <<annotation-method-interceptors,method interceptor tương ứng>> để thực hiện authorization cho các method, class và interface được gắn `@Secured`.

[[class-or-interface-annotations]]
=== Khai báo Annotation ở Cấp Class hoặc Interface

Method Security cũng hỗ trợ annotation ở cấp class và interface.

Nếu annotation ở cấp class như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Controller
@PreAuthorize("hasAuthority('ROLE_USER')")
public class MyController {
    @GetMapping("/endpoint")
    public String endpoint() { ... }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Controller
@PreAuthorize("hasAuthority('ROLE_USER')")
open class MyController {
    @GetMapping("/endpoint")
    fun endpoint(): String { ... }
}
----
======

thì tất cả method sẽ kế thừa behavior ở cấp class.

Hoặc nếu nó được khai báo ở cả cấp class và method như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Controller
@PreAuthorize("hasAuthority('ROLE_USER')")
public class MyController {
    @GetMapping("/endpoint")
    @PreAuthorize("hasAuthority('ROLE_ADMIN')")
    public String endpoint() { ... }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Controller
@PreAuthorize("hasAuthority('ROLE_USER')")
open class MyController {
    @GetMapping("/endpoint")
    @PreAuthorize("hasAuthority('ROLE_ADMIN')")
    fun endpoint(): String { ... }
}
----
======

thì các method khai báo annotation sẽ ghi đè annotation ở cấp class.

Điều tương tự cũng đúng với interface, ngoại trừ trường hợp một class kế thừa annotation từ hai interface khác nhau thì startup sẽ thất bại.
Đó là vì Spring Security không có cách nào biết bạn muốn sử dụng annotation nào.

Trong trường hợp như vậy, bạn có thể giải quyết sự mơ hồ bằng cách thêm annotation vào method cụ thể.

[[meta-annotations]]
=== Sử dụng Meta-Annotation

Method Security hỗ trợ meta-annotation.
Điều này có nghĩa là bạn có thể sử dụng bất kỳ annotation nào và cải thiện khả năng đọc dựa trên các trường hợp sử dụng riêng của ứng dụng.

Ví dụ, bạn có thể đơn giản hóa `@PreAuthorize("hasRole('ADMIN')")` thành `@IsAdmin` như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Target({ ElementType.METHOD, ElementType.TYPE })
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("hasRole('ADMIN')")
public @interface IsAdmin {}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Target(ElementType.METHOD, ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@PreAuthorize("hasRole('ADMIN')")
annotation class IsAdmin
----
======

Kết quả là trên các method được bảo vệ, giờ đây bạn có thể dùng cách sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class BankService {
	@IsAdmin
	public Account readAccount(Long id) {
        // ... is only returned if the `Account` belongs to the logged in user
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
open class BankService {
	@IsAdmin
	fun readAccount(id: Long): Account {
        // ... is only returned if the `Account` belongs to the logged in user
	}
}
----
======

Điều này tạo ra các định nghĩa method dễ đọc hơn.

Kết quả là trên các method được bảo vệ, giờ đây bạn có thể dùng cách sau:

=== Kích hoạt Annotation Cụ thể

Bạn có thể tắt cấu hình trước của ``@EnableMethodSecurity`` và thay thế bằng cấu hình của riêng mình.
Bạn có thể chọn cách này nếu muốn <<custom-authorization-managers,tùy chỉnh `AuthorizationManager`>> hoặc `Pointcut`.
Hoặc bạn chỉ muốn kích hoạt một annotation cụ thể, chẳng hạn `@PostAuthorize`.

Bạn có thể làm như sau:

.Chỉ cấu hình @PostAuthorize
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableMethodSecurity(prePostEnabled = false)
class MethodSecurityConfig {
	@Bean
	@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
	Advisor postAuthorize() {
		return AuthorizationManagerAfterMethodInterceptor.postAuthorize();
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

	@Bean

----

Xml::
+
[source,xml,role="secondary"]

======

Đoạn code trên thực hiện điều này bằng cách trước tiên tắt các cấu hình trước của Method Security, sau đó tự publish <<annotation-method-interceptors,interceptor `@PostAuthorize`>>.

[[use-intercept-methods]]
== Thực hiện Authorization bằng `<intercept-methods>`

Mặc dù sử dụng <<authorizing-with-annotations,tính năng hỗ trợ dựa trên annotation>> của Spring Security được ưu tiên cho method security, bạn cũng có thể sử dụng XML để khai báo các quy tắc authorization cho bean.

Nếu cần khai báo trong cấu hình XML, bạn có thể sử dụng xref:servlet/appendix/namespace/method-security.adoc#nsa-intercept-methods[`<intercept-methods>`] như sau:

[tabs]
======
Xml::
+
[source,xml,role="primary"]
----
<bean class="org.mycompany.MyController">
    <intercept-methods>
        <protect method="get*" access="hasAuthority('read')"/>
        <protect method="*" access="hasAuthority('write')"/>
    </intercept-methods>
</bean>
----
======

[NOTE]
Tính năng này chỉ hỗ trợ khớp method theo prefix hoặc theo tên.
Nếu nhu cầu của bạn phức tạp hơn, hãy sử dụng <<authorizing-with-annotations,tính năng hỗ trợ annotation>>.

[[use-programmatic-authorization]]
== Thực hiện Authorization cho Method bằng Programmatic API

Như đã thấy, có một số cách để bạn chỉ định các quy tắc authorization không tầm thường bằng <<authorization-expressions,biểu thức SpEL của Method Security>>.

Thay vào đó, có một số cách cho phép bạn viết logic dựa trên Java thay vì dựa trên SpEL.
Điều này cho phép sử dụng toàn bộ ngôn ngữ Java để tăng khả năng kiểm thử và kiểm soát flow.

=== Sử dụng Bean Tùy chỉnh trong SpEL

Cách đầu tiên để thực hiện authorization cho method bằng programmatic API là một quy trình gồm hai bước.

Trước tiên, khai báo một bean có method nhận một instance `MethodSecurityExpressionOperations` như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component("authz")
public class AuthorizationLogic {
    public boolean decide(MethodSecurityExpressionOperations operations) {
        // ... authorization logic
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component("authz")
open class AuthorizationLogic {
    fun decide(operations: MethodSecurityExpressionOperations): boolean {
        // ... authorization logic
    }
}
----
======

Sau đó, tham chiếu bean đó trong annotation như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Controller
public class MyController {
    @PreAuthorize("@authz.decide(#root)")
    @GetMapping("/endpoint")
    public String endpoint() {
        // ...
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Controller
open class MyController {
    @PreAuthorize("@authz.decide(#root)")
    @GetMapping("/endpoint")
    fun String endpoint() {
        // ...
    }
}
----
======

Spring Security sẽ gọi method đã cho trên bean đó trong mỗi lần gọi method.

Điểm hữu ích là toàn bộ logic authorization nằm trong một class riêng, có thể được unit test và xác minh tính đúng đắn độc lập.
Class này cũng có quyền truy cập toàn bộ ngôn ngữ Java.

[TIP]
Ngoài việc trả về `Boolean`, bạn cũng có thể trả về `null` để cho biết code không đưa ra quyết định.

Nếu muốn đưa thêm thông tin về bản chất của quyết định, thay vào đó bạn có thể trả về `AuthorizationDecision` tùy chỉnh như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component("authz")
public class AuthorizationLogic {
    public AuthorizationDecision decide(MethodSecurityExpressionOperations operations) {
        // ... authorization logic
        return new MyAuthorizationDecision(false, details);
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component("authz")
open class AuthorizationLogic {
    fun decide(operations: MethodSecurityExpressionOperations): AuthorizationDecision {
        // ... authorization logic
        return MyAuthorizationDecision(false, details)
    }
}
----
======

Hoặc ném một instance `AuthorizationDeniedException` tùy chỉnh.
Tuy nhiên, nên ưu tiên trả về một object vì cách này không phát sinh chi phí tạo stacktrace.

Sau đó, bạn có thể truy cập các chi tiết tùy chỉnh khi <<fallback-values-authorization-denied,tùy chỉnh cách xử lý kết quả authorization>>.

[TIP]
====
Ngoài ra, bạn có thể tự trả về một `AuthorizationManager`.
Điều này hữu ích khi hợp nhất các quy tắc web authorization tùy chỉnh với các quy tắc method security, vì web security theo mặc định yêu cầu chỉ định một instance `AuthorizationManager`.
====

[[custom-authorization-managers]]
=== Sử dụng Authorization Manager Tùy chỉnh

Cách thứ hai để thực hiện authorization cho method bằng programmatic API là tạo xref:servlet/authorization/architecture.adoc#_the_authorizationmanager[`AuthorizationManager`] tùy chỉnh.

Trước tiên, khai báo một instance authorization manager, chẳng hạn như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class MyPreAuthorizeAuthorizationManager implements AuthorizationManager<MethodInvocation> {
    @Override
    public AuthorizationResult authorize(Supplier<Authentication> authentication, MethodInvocation invocation) {
        // ... authorization logic
    }
}

@Component
public class MyPostAuthorizeAuthorizationManager implements AuthorizationManager<MethodInvocationResult> {
    @Override
    public AuthorizationResult authorize(Supplier<Authentication> authentication, MethodInvocationResult invocation) {
        // ... authorization logic
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
class MyPreAuthorizeAuthorizationManager : AuthorizationManager<MethodInvocation> {
    override fun authorize(authentication: Supplier<Authentication>, invocation: MethodInvocation): AuthorizationResult {
        // ... authorization logic
    }
}

@Component
class MyPostAuthorizeAuthorizationManager : AuthorizationManager<MethodInvocationResult> {
    override fun authorize(authentication: Supplier<Authentication>, invocation: MethodInvocationResult): AuthorizationResult {
        // ... authorization logic
    }
}
----
======

Sau đó, publish method interceptor với một pointcut tương ứng với thời điểm bạn muốn `AuthorizationManager` đó chạy.
Ví dụ, bạn có thể thay thế cách hoạt động của `@PreAuthorize` và `@PostAuthorize` như sau:

.Chỉ cấu hình @PreAuthorize và @PostAuthorize
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableMethodSecurity(prePostEnabled = false)
class MethodSecurityConfig {
    @Bean
	@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
	Advisor preAuthorize(MyPreAuthorizeAuthorizationManager manager) {
		return AuthorizationManagerBeforeMethodInterceptor.preAuthorize(manager);
	}

	@Bean
	@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
	Advisor postAuthorize(MyPostAuthorizeAuthorizationManager manager) {
		return AuthorizationManagerAfterMethodInterceptor.postAuthorize(manager);
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Configuration
@EnableMethodSecurity(prePostEnabled = false)
class MethodSecurityConfig {
	@Bean
	@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
	fun preAuthorize(manager: MyPreAuthorizeAuthorizationManager): Advisor {
		return AuthorizationManagerBeforeMethodInterceptor.preAuthorize(manager)
	}

	@Bean
	@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
	fun postAuthorize(manager: MyPostAuthorizeAuthorizationManager): Advisor {
		return AuthorizationManagerAfterMethodInterceptor.postAuthorize(manager)
	}
}
----

Xml::
+
[source,xml,role="secondary"]
----

	class="org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor"
	factory-method="preAuthorize">
    <constructor-arg ref="myPreAuthorizeAuthorizationManager"/>
</bean>

<bean id="postAuthorize"
	class="org.springframework.security.authorization.method.AuthorizationManagerAfterMethodInterceptor"
	factory-method="postAuthorize">
    <constructor-arg ref="myPostAuthorizeAuthorizationManager"/>
</bean>
----
======

[TIP]
====
Bạn có thể đặt interceptor của mình giữa các method interceptor của Spring Security bằng cách sử dụng các hằng số order được chỉ định trong `AuthorizationInterceptorsOrder`.
====

Bạn cũng có thể implement `MethodAuthorizationDeniedHandler` trong cùng manager class để ghi đè behavior xử lý exception mặc định.

[[pre-post-authorize-aot]]
=== Làm việc với AOT

Spring Security sẽ quét tất cả bean trong application context để tìm các method sử dụng `@PreAuthorize` hoặc `@PostAuthorize`.
Khi tìm thấy, nó sẽ resolve mọi bean được sử dụng bên trong biểu thức security và đăng ký runtime hint thích hợp cho bean đó.
Nếu tìm thấy một method sử dụng `@AuthorizeReturnObject`, nó sẽ đệ quy tìm trong kiểu trả về của method các annotation `@PreAuthorize` và `@PostAuthorize`, rồi đăng ký chúng tương ứng.

Ví dụ, hãy xem ứng dụng Spring Boot sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Service
public class AccountService { <1>

    @PreAuthorize("@authz.decide()") <2>
    @AuthorizeReturnObject <3>
    public Account getAccountById(String accountId) {
        // ...
    }

}

public class Account {

    private final String accountNumber;

    // ...

    @PreAuthorize("@accountAuthz.canViewAccountNumber()") <4>
    public String getAccountNumber() {
        return this.accountNumber;
    }

    @AuthorizeReturnObject <5>
    public User getUser() {
        return new User("John Doe");
    }

}

public class User {

    private final String fullName;

    // ...

    @PostAuthorize("@myOtherAuthz.decide()") <6>
    public String getFullName() {
        return this.fullName;
    }

}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Service
class AccountService { <1>

    @PreAuthorize("@authz.decide()") <2>
    @AuthorizeReturnObject <3>
    fun getAccountById(accountId: String): Account {
        // ...
    }

}

class Account(private val accountNumber: String) {

    @PreAuthorize("@accountAuthz.canViewAccountNumber()") <4>
    fun getAccountNumber(): String {
        return this.accountNumber
    }

    @AuthorizeReturnObject <5>
    fun getUser(): User {
        return User("John Doe")
    }

}

class User(private val fullName: String) {

    @PostAuthorize("@myOtherAuthz.decide()") <6>
    fun getFullName(): String {
        return this.fullName
    }

}
----
======

<1> Spring Security tìm thấy bean `AccountService`
<2> Khi tìm thấy method sử dụng `@PreAuthorize`, nó sẽ resolve mọi tên bean được dùng trong biểu thức, trong trường hợp này là `authz`, và đăng ký runtime hint cho class của bean
<3> Khi tìm thấy method sử dụng `@AuthorizeReturnObject`, nó sẽ tìm trong kiểu trả về của method các annotation `@PreAuthorize` hoặc `@PostAuthorize`
<4> Sau đó, nó tìm thấy `@PreAuthorize` với một tên bean khác là `accountAuthz`; runtime hint cũng được đăng ký cho class của bean
<5> Khi tìm thấy một `@AuthorizeReturnObject` khác, nó lại tìm trong kiểu trả về của method
<6> Lúc này, một `@PostAuthorize` được tìm thấy với tên bean khác được sử dụng là `myOtherAuthz`; runtime hint cũng được đăng ký cho class của bean

Có nhiều trường hợp Spring Security không thể xác định trước kiểu trả về thực tế của method vì kiểu đó có thể bị ẩn trong một generic type đã bị xóa.

Hãy xem service sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Service
public class AccountService {

    @AuthorizeReturnObject
    public List<Account> getAllAccounts() {
        // ...
    }

}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Service
class AccountService {

    @AuthorizeReturnObject
    fun getAllAccounts(): List<Account> {
        // ...
    }

}
----
======

Trong trường hợp này, generic type đã bị xóa nên Spring Security không thể biết trước rằng cần duyệt `Account` để kiểm tra `@PreAuthorize` và `@PostAuthorize`.

Để giải quyết, bạn có thể publish javadoc:org.springframework.security.aot.hint.PrePostAuthorizeExpressionBeanHintsRegistrar[`PrePostAuthorizeExpressionBeanHintsRegistrar`] như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----

@Role(BeanDefinition.ROLE_INFRASTRUCTURE)

    return new PrePostAuthorizeExpressionBeanHintsRegistrar(Account.class);
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

@Role(BeanDefinition.ROLE_INFRASTRUCTURE)

    return PrePostAuthorizeExpressionBeanHintsRegistrar(Account::class.java)
}
----

=== Khớp Method bằng Pointcut Tùy chỉnh

Vì được xây dựng trên Spring AOP, bạn có thể khai báo các pattern không liên quan đến annotation, tương tự như xref:servlet/authorization/authorize-http-requests.adoc[authorization ở cấp request].
Cách này có ưu điểm tiềm năng là tập trung các quy tắc authorization ở cấp method.

Ví dụ, bạn có thể publish `Advisor` của riêng mình hoặc sử dụng xref:servlet/appendix/namespace/method-security.adoc#nsa-protect-pointcut[`<protect-pointcut>`] để khớp các biểu thức AOP với các quy tắc authorization cho service layer như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
import static org.springframework.security.authorization.AuthorityAuthorizationManager.hasRole

@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
static Advisor protectServicePointcut() {
    AspectJExpressionPointcut pattern = new AspectJExpressionPointcut()
    pattern.setExpression("execution(* com.mycompany.*Service.*(..))")
    return new AuthorizationManagerBeforeMethodInterceptor(pattern, hasRole("USER"))
}
----

Kotlin::

[source,kotlin,role="secondary"]

[[changing-the-order]]
== Chỉ định Order

Như đã lưu ý, mỗi annotation có một method interceptor của Spring AOP, và mỗi interceptor có một vị trí trong advisor chain của Spring AOP.

Cụ thể, order của method interceptor `@PreFilter` là 100, của ``@PreAuthorize`` là 200, v.v.

Bạn có thể sử dụng tham số `offset` trên `@EnableMethodSecurity` để di chuyển toàn bộ interceptor cùng lúc, khiến advice của chúng chạy sớm hơn hoặc muộn hơn trong một lần gọi method.

[[authorization-expressions]]
== Biểu đạt Authorization bằng SpEL

Bạn đã thấy một số ví dụ sử dụng SpEL, vì vậy bây giờ hãy tìm hiểu API sâu hơn một chút.

Spring Security đóng gói tất cả field và method authorization của mình trong một tập hợp root object.
Root object tổng quát nhất có tên là `SecurityExpressionRoot` và nó là nền tảng cho `MethodSecurityExpressionRoot`.
Spring Security cung cấp root object này cho `MethodSecurityEvaluationContext` khi chuẩn bị đánh giá một biểu thức authorization.

[[using-authorization-expression-fields-and-methods]]
=== Sử dụng Field và Method của Biểu thức Authorization

Điều đầu tiên mà tính năng này cung cấp là một tập hợp field và method authorization được mở rộng cho các biểu thức SpEL của bạn.
Sau đây là tổng quan nhanh về các method phổ biến nhất:

* `permitAll` - Method không yêu cầu authorization để được gọi; lưu ý rằng trong trường hợp này, xref:servlet/authentication/architecture.adoc#servlet-authentication-authentication[`Authentication`] không bao giờ được lấy từ session
* `denyAll` - Method không được phép trong bất kỳ trường hợp nào; lưu ý rằng trong trường hợp này, `Authentication` không bao giờ được lấy từ session
* `hasAuthority` - Method yêu cầu `Authentication` có xref:servlet/authorization/architecture.adoc#authz-authorities[`GrantedAuthority`] khớp với giá trị đã cho
* `hasRole` - Shortcut cho `hasAuthority`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasAnyAuthority` - Method yêu cầu `Authentication` có một `GrantedAuthority` khớp với bất kỳ giá trị nào đã cho
* `hasAnyRole` - Shortcut cho `hasAnyAuthority`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasAllAuthorities` - Method yêu cầu `Authentication` có các ``GrantedAuthority`` khớp với tất cả giá trị đã cho
* `hasAllRoles` - Shortcut cho `hasAllAuthorities`, thêm tiền tố `ROLE_` hoặc tiền tố mặc định đã được cấu hình
* `hasPermission` - Một hook vào instance `PermissionEvaluator` của bạn để thực hiện authorization ở cấp object

Sau đây là phần giới thiệu ngắn về các field phổ biến nhất:

* `authentication` - Instance `Authentication` gắn với lần gọi method này
* `principal` - `Authentication#getPrincipal` gắn với lần gọi method này

Sau khi đã biết các pattern, quy tắc và cách kết hợp chúng, bạn có thể hiểu điều gì đang xảy ra trong ví dụ phức tạp hơn sau:

.Authorization cho Request
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class MyService {
    @PreAuthorize("denyAll") <1>
    MyResource myDeprecatedMethod(...);

    @PreAuthorize("hasRole('ADMIN')") <2>
    MyResource writeResource(...)

    @PreAuthorize("hasAuthority('db') and hasRole('ADMIN')") <3>
    MyResource deleteResource(...)

    @PreAuthorize("principal.claims['aud'] == 'my-audience'") <4>
    MyResource readResource(...);

	@PreAuthorize("@authz.check(authentication, #root)")
    MyResource shareResource(...);
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
open class MyService {
    @PreAuthorize("denyAll") <1>
    fun myDeprecatedMethod(...): MyResource

    @PreAuthorize("hasRole('ADMIN')") <2>
    fun writeResource(...): MyResource

    @PreAuthorize("hasAuthority('db') and hasRole('ADMIN')") <3>
    fun deleteResource(...): MyResource

    @PreAuthorize("principal.claims['aud'] == 'my-audience'") <4>
    fun readResource(...): MyResource

    @PreAuthorize("@authz.check(#root)")
    fun shareResource(...): MyResource
}
----

Xml::
+
[source,xml,role="secondary"]
----
<sec:method-security>
    <protect-pointcut expression="execution(* com.mycompany.*Service.myDeprecatedMethod(..))" access="denyAll"/> <1>
    <protect-pointcut expression="execution(* com.mycompany.*Service.writeResource(..))" access="hasRole('ADMIN')"/> <2>
    <protect-pointcut expression="execution(* com.mycompany.*Service.deleteResource(..))" access="hasAuthority('db') and hasRole('ADMIN')"/> <3>
    <protect-pointcut expression="execution(* com.mycompany.*Service.readResource(..))" access="principal.claims['aud'] == 'my-audience'"/> <4>
    <protect-pointcut expression="execution(* com.mycompany.*Service.shareResource(..))" access="@authz.check(#root)"/> <5>
</sec:method-security>

======
<1> Không ai có thể gọi method này vì bất kỳ lý do nào
<2> Method này chỉ có thể được gọi bởi ``Authentication`` được cấp authority `ROLE_ADMIN`
<3> Method này chỉ có thể được gọi bởi ``Authentication`` được cấp các authority `db` và `ROLE_ADMIN`
<4> Method này chỉ có thể được gọi bởi ``Principal`` có claim `aud` bằng "my-audience"
<5> Method này chỉ có thể được gọi nếu method `check` của bean ``authz`` trả về `true`

[TIP]
====
Bạn có thể sử dụng bean như `authz` ở trên để <<_using_a_custom_bean_in_spel,thêm authorization bằng programmatic API>>.
====

[[using_method_parameters]]
=== Sử dụng Tham số Method

Ngoài ra, Spring Security cung cấp cơ chế phát hiện tham số method để các tham số này cũng có thể được truy cập trong biểu thức SpEL.

Để tham chiếu đầy đủ, Spring Security sử dụng `DefaultSecurityParameterNameDiscoverer` để phát hiện tên tham số.
Theo mặc định, các tùy chọn sau được thử cho một method.

1. Nếu annotation `@P` của Spring Security hiện diện trên một đối số duy nhất của method, giá trị đó sẽ được sử dụng.
Ví dụ sau sử dụng annotation `@P`:

+

[tabs]
======
Java::
+
[source,java,role="primary"]
----
import org.springframework.security.access.method.P;

...

@PreAuthorize("hasPermission(#c, 'write')")
public void updateContact(@P("c") Contact contact);
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
import org.springframework.security.access.method.P

...

@PreAuthorize("hasPermission(#c, 'write')")
fun doSomething(@P("c") contact: Contact?)
----
======
+
Mục đích của biểu thức này là yêu cầu `Authentication` hiện tại có permission `write` dành riêng cho instance `Contact` này.
+
Ở phía sau, tính năng này được triển khai bằng `AnnotationParameterNameDiscoverer`, mà bạn có thể tùy chỉnh để hỗ trợ attribute value của bất kỳ annotation được chỉ định nào.

2. Nếu annotation `@Param` của xref:servlet/integrations/data.adoc[Spring Data] hiện diện trên ít nhất một tham số của method, giá trị đó sẽ được sử dụng.
Ví dụ sau sử dụng annotation `@Param`:
+
[tabs]
======
Java::
+
[source,java,role="primary"]
----
import org.springframework.data.repository.query.Param;

...

@PreAuthorize("#n == authentication.name")
Contact findContactByName(@Param("n") String name);
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
import org.springframework.data.repository.query.Param

...

@PreAuthorize("#n == authentication.name")
fun findContactByName(@Param("n") name: String?): Contact?
----
======
+
Mục đích của biểu thức này là yêu cầu `name` bằng `Authentication#getName` để lần gọi được authorization.
+
Ở phía sau, tính năng này được triển khai bằng `AnnotationParameterNameDiscoverer`, mà bạn có thể tùy chỉnh để hỗ trợ attribute value của bất kỳ annotation được chỉ định nào.

3. Nếu biên dịch code bằng đối số `-parameters`, standard JDK reflection API sẽ được sử dụng để phát hiện tên tham số.
Cách này hoạt động trên cả class và interface.

4. Cuối cùng, nếu biên dịch code với debug symbol, tên tham số được phát hiện bằng cách sử dụng debug symbol.
Cách này không hoạt động với interface vì interface không có thông tin debug về tên tham số.
Với interface, phải sử dụng annotation hoặc cách tiếp cận `-parameters`.

[[customizing-authorization-managers]]
== Tùy chỉnh Authorization Manager

Khi sử dụng biểu thức SpEL với <<use-preauthorize,`@PreAuthorize`>>, <<use-postauthorize,`@PostAuthorize`>>, <<use-prefilter,`@PreFilter`>> và <<use-postfilter,`@PostFilter`>>, Spring Security sẽ tự tạo các instance `AuthorizationManager` thích hợp cho bạn.
Trong một số trường hợp, bạn có thể muốn tùy chỉnh những gì được tạo ra để kiểm soát hoàn toàn cách đưa ra quyết định authorization xref:servlet/authorization/architecture.adoc#authz-delegate-authorization-manager[ở cấp framework].

Để kiểm soát việc tạo instance `AuthorizationManager` cho các annotation pre và post, bạn có thể tạo xref:servlet/authorization/architecture.adoc#authz-authorization-manager-factory[`AuthorizationManagerFactory`] tùy chỉnh.
Ví dụ, giả sử bạn muốn cho phép người dùng có role `ADMIN` bất cứ khi nào yêu cầu một role khác.
Để làm vậy, bạn có thể tạo implementation tùy chỉnh cho method security như trong ví dụ sau:

include-code::./CustomMethodInvocationAuthorizationManagerFactory[tag=class,indent=0]

Giờ đây, bất cứ khi nào bạn <<use-preauthorize,sử dụng annotation `@PreAuthorize`>> với `hasRole` hoặc `hasAnyRole`, Spring Security sẽ tự động gọi factory tùy chỉnh để tạo instance `AuthorizationManager` cho phép truy cập với role đã cho _HOẶC_ role `ADMIN`.

[TIP]
Đây là ví dụ đơn giản về việc tạo `AuthorizationManagerFactory` tùy chỉnh, dù bạn cũng có thể đạt được kết quả tương tự bằng <<favor-granting-authorities,một role hierarchy>>.
Hãy sử dụng cách tiếp cận phù hợp nhất với tình huống của bạn.

[[authorize-object]]
== Thực hiện Authorization cho Object Bất kỳ

Spring Security cũng hỗ trợ wrapping bất kỳ object nào được gắn annotation method security.

Cách đơn giản nhất là gắn annotation `@AuthorizeReturnObject` lên bất kỳ method nào trả về object mà bạn muốn thực hiện authorization.

Ví dụ, hãy xem class `User` sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
public class User {
	private String name;
	private String email;

	public User(String name, String email) {
		this.name = name;
		this.email = email;
	}

	public String getName() {
		return this.name;
	}

    @PreAuthorize("hasAuthority('user:read')")
    public String getEmail() {
		return this.email;
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
class User (val name:String, @get:PreAuthorize("hasAuthority('user:read')") val email:String)
----
======

Với một interface như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
public class UserRepository {
	@AuthorizeReturnObject
    Optional<User> findByName(String name) {
		// ...
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
class UserRepository {
    @AuthorizeReturnObject
    fun findByName(name:String?): Optional<User?>? {
        // ...
    }
}
----
======

Khi đó, mọi `User` được trả về từ `findById` sẽ được bảo vệ như các component khác được Spring Security bảo vệ:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Autowired
UserRepository users;

@Test
void getEmailWhenProxiedThenAuthorizes() {
    Optional<User> securedUser = users.findByName("name");
    assertThatExceptionOfType(AccessDeniedException.class).isThrownBy(() -> securedUser.get().getEmail());
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

import jdk.incubator.vector.VectorOperators.Test
import java.nio.file.AccessDeniedException
import java.util.*

@Autowired
var users:UserRepository? = null

@Test
fun getEmailWhenProxiedThenAuthorizes() {
    val securedUser: Optional<User> = users.findByName("name")
    assertThatExceptionOfType(AccessDeniedException::class.java).isThrownBy{securedUser.get().getEmail()}
}
----
======

=== Sử dụng `@AuthorizeReturnObject` ở Cấp Class

`@AuthorizeReturnObject` có thể được đặt ở cấp class. Tuy nhiên, lưu ý rằng điều này có nghĩa Spring Security sẽ cố proxy mọi object trả về, bao gồm ``String``, ``Integer`` và các kiểu khác.
Đây thường không phải điều bạn muốn.

Nếu muốn sử dụng `@AuthorizeReturnObject` trên một class hoặc interface có method trả về các kiểu giá trị như `int`, `String`, `Double` hoặc collection của những kiểu này, bạn cũng nên publish `AuthorizationAdvisorProxyFactory.TargetVisitor` thích hợp như sau:


[tabs]
======
Java::
+
[source,java,role="primary"]
----
import org.springframework.security.authorization.method.AuthorizationAdvisorProxyFactory.TargetVisitor;

// ...

@Bean
static TargetVisitor skipValueTypes() {
    return TargetVisitor.defaultsSkipValueTypes();
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
import org.springframework.security.authorization.method.AuthorizationAdvisorProxyFactory.TargetVisitor

// ...

@Bean
open fun skipValueTypes() = TargetVisitor.defaultsSkipValueTypes()
----
======

[TIP]
====
Bạn có thể đặt `AuthorizationAdvisorProxyFactory.TargetVisitor` của riêng mình để tùy chỉnh việc proxy cho bất kỳ tập hợp kiểu nào
====

=== Proxy bằng Programmatic API

Bạn cũng có thể proxy một object đã cho bằng programmatic API.

Để làm vậy, bạn có thể autowire instance `AuthorizationProxyFactory` được cung cấp, dựa trên các method security interceptor mà bạn đã cấu hình.
Nếu sử dụng `@EnableMethodSecurity`, theo mặc định nó sẽ có interceptor cho `@PreAuthorize`, `@PostAuthorize`, `@PreFilter` và `@PostFilter`.


Bạn có thể proxy một instance của user như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Autowired
AuthorizationProxyFactory proxyFactory;

@Test
void getEmailWhenProxiedThenAuthorizes() {
    User user = new User("name", "email");
    assertThat(user.getEmail()).isNotNull();
    User securedUser = proxyFactory.proxy(user);
    assertThatExceptionOfType(AccessDeniedException.class).isThrownBy(securedUser::getEmail);
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Autowired
var proxyFactory:AuthorizationProxyFactory? = null

@Test
fun getEmailWhenProxiedThenAuthorizes() {
    val user: User = User("name", "email")
    assertThat(user.getEmail()).isNotNull()
    val securedUser: User = proxyFactory.proxy(user)
    assertThatExceptionOfType(AccessDeniedException::class.java).isThrownBy(securedUser::getEmail)
}
----
======

=== Tạo Thủ công

Bạn cũng có thể tự định nghĩa instance nếu cần một thứ khác với giá trị mặc định của Spring Security.

Ví dụ, nếu định nghĩa một instance `AuthorizationProxyFactory` như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
import org.springframework.security.authorization.method.AuthorizationAdvisorProxyFactory.TargetVisitor;
import static org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor.preAuthorize;
// ...

AuthorizationProxyFactory proxyFactory = AuthorizationAdvisorProxyFactory.withDefaults();
// and if needing to skip value types
proxyFactory.setTargetVisitor(TargetVisitor.defaultsSkipValueTypes());
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
import org.springframework.security.authorization.method.AuthorizationAdvisorProxyFactory.TargetVisitor;
import org.springframework.security.authorization.method.AuthorizationManagerBeforeMethodInterceptor.preAuthorize

// ...

val proxyFactory: AuthorizationProxyFactory = AuthorizationProxyFactory(preAuthorize())
// and if needing to skip value types
proxyFactory.setTargetVisitor(TargetVisitor.defaultsSkipValueTypes())
----
======

Sau đó, bạn có thể wrap bất kỳ instance `User` nào như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Test
void getEmailWhenProxiedThenAuthorizes() {
	AuthorizationProxyFactory proxyFactory = AuthorizationAdvisorProxyFactory.withDefaults();
    User user = new User("name", "email");
    assertThat(user.getEmail()).isNotNull();

}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Test
fun getEmailWhenProxiedThenAuthorizes() {
    val proxyFactory: AuthorizationProxyFactory = AuthorizationAdvisorProxyFactory.withDefaults()
    val user: User = User("name", "email")
    assertThat(user.getEmail()).isNotNull()
    val securedUser: User = proxyFactory.proxy(user)
    assertThatExceptionOfType(AccessDeniedException::class.java).isThrownBy(securedUser::getEmail)
}
----
======

=== Proxy Collection

`AuthorizationProxyFactory` hỗ trợ collection, stream, array, optional và iterator của Java bằng cách proxy element type, đồng thời proxy map bằng cách proxy value type.

Điều này có nghĩa là khi proxy một `List` các object, cách sau cũng hoạt động:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Test
void getEmailWhenProxiedThenAuthorizes() {
	AuthorizationProxyFactory proxyFactory = AuthorizationAdvisorProxyFactory.withDefaults();
    List<User> users = List.of(ada, albert, marie);
    List<User> securedUsers = proxyFactory.proxy(users);
	securedUsers.forEach((securedUser) ->
        assertThatExceptionOfType(AccessDeniedException.class).isThrownBy(securedUser::getEmail));
}
----
======

=== Proxy Class

Trong một số trường hợp hạn chế, proxy chính `Class` có thể hữu ích, và `AuthorizationProxyFactory` cũng hỗ trợ việc này.
Điều này gần tương đương với việc gọi `ProxyFactory#getProxyClass` trong tính năng hỗ trợ tạo proxy của Spring Framework.

Một trường hợp hữu ích là khi bạn cần tạo proxy class ahead-of-time, chẳng hạn với Spring AOT.

=== Hỗ trợ Mọi Annotation Method Security

`AuthorizationProxyFactory` hỗ trợ các annotation method security được kích hoạt trong ứng dụng.
Nó dựa trên các class `AuthorizationAdvisor` được publish dưới dạng bean.

Vì `@EnableMethodSecurity` mặc định publish advisor cho `@PreAuthorize`, `@PostAuthorize`, `@PreFilter` và `@PostFilter`, thông thường bạn không cần làm gì để kích hoạt khả năng này.

[NOTE]
====
Các biểu thức SpEL sử dụng `returnObject` hoặc `filterObject` nằm phía sau proxy nên có toàn quyền truy cập object.
====

[#custom_advice]
=== Advice Tùy chỉnh

Nếu có security advice cũng muốn áp dụng, bạn có thể publish `AuthorizationAdvisor` của riêng mình như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@EnableMethodSecurity
class SecurityConfig {
    @Bean
    static AuthorizationAdvisor myAuthorizationAdvisor() {
        return new AuthorizationAdvisor();
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@EnableMethodSecurity
internal class SecurityConfig {
    @Bean
    fun myAuthorizationAdvisor(): AuthorizationAdvisor {
        return AuthorizationAdvisor()
    }
]
----
======

Spring Security sẽ thêm advisor đó vào tập hợp advice mà `AuthorizationProxyFactory` thêm vào khi proxy một object.

Một cách sử dụng mạnh mẽ của tính năng này là trả về một giá trị được bảo vệ từ controller như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@RestController

Bạn sẽ cần <<fallback-values-authorization-denied,thêm một `MethodAuthorizationDeniedHandler`>> như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
public class Null implements MethodAuthorizationDeniedHandler {
    @Override
    public Object handleDeniedInvocation(MethodInvocation methodInvocation, AuthorizationResult authorizationResult) {
        return null;
    }
}

// ...

@HandleAuthorizationDenied(handlerClass = Null.class)
public class User {
	...
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

    override fun handleDeniedInvocation(methodInvocation: MethodInvocation?, authorizationResult: AuthorizationResult?): Any? {
        return null
    }
}

// ...

open class User {
	...
}

Sau đó, bạn sẽ thấy serialization JSON khác nhau dựa trên mức authorization của người dùng.

[source,json]

    "email" : null

----

Nếu có authority đó, họ sẽ thấy:

[source,json]

----

Bạn cũng có thể thêm property Spring Boot `spring.jackson.default-property-inclusion=non_null` để loại trừ giá trị null khỏi serialization, nếu không muốn tiết lộ JSON key cho người dùng chưa được authorization.

[[authorize-return-object-aot]]
=== Làm việc với AOT

Spring Security sẽ quét tất cả bean trong application context để tìm các method sử dụng `@AuthorizeReturnObject`.
Khi tìm thấy, nó sẽ tạo và đăng ký proxy class thích hợp ahead-of-time.
Nó cũng sẽ đệ quy tìm các object lồng nhau khác sử dụng `@AuthorizeReturnObject` và đăng ký chúng tương ứng.

Ví dụ, hãy xem ứng dụng Spring Boot sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@SpringBootApplication
public class MyApplication {
	@RestController
    public static class MyController { <1>
		@GetMapping
        @AuthorizeReturnObject
        Message getMessage() { <2>
			return new Message(someUser, "hello!");
        }
    }

	public static class Message { <3>
		User to;
		String text;

		// ...

        @AuthorizeReturnObject
        public User getTo() { <4>
			return this.to;
        }

		// ...
	}

	public static class User { <5>
		// ...
	}

	public static void main(String[] args) {
		SpringApplication.run(MyApplication.class);
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@SpringBootApplication
open class MyApplication {
	@RestController
    open class MyController { <1>
		@GetMapping
        @AuthorizeReturnObject
        fun getMessage():Message { <2>
			return Message(someUser, "hello!")
        }
    }

	open class Message { <3>
		val to: User
		val test: String

		// ...

        @AuthorizeReturnObject
        fun getTo(): User { <4>
			return this.to
        }

		// ...
	}

	open class User { <5>
		// ...
	}

	fun main(args: Array<String>) {
		SpringApplication.run(MyApplication.class)
	}
}
----
======
<1> - Trước tiên, Spring Security tìm thấy bean `MyController`
<2> - Khi tìm thấy method sử dụng `@AuthorizeReturnObject`, nó proxy `Message`, giá trị trả về, và đăng ký proxy class đó vào `RuntimeHints`
<3> - Sau đó, nó duyệt `Message` để xem có sử dụng `@AuthorizeReturnObject` hay không
<4> - Khi tìm thấy method sử dụng `@AuthorizeReturnObject`, nó proxy `User`, giá trị trả về, và đăng ký proxy class đó vào `RuntimeHints`
<5> - Cuối cùng, nó duyệt `User` để xem có sử dụng `@AuthorizeReturnObject` hay không; không tìm thấy gì, thuật toán hoàn tất

Có nhiều trường hợp Spring Security không thể xác định trước proxy class vì proxy class có thể bị ẩn trong một generic type đã bị xóa.

Hãy xem thay đổi sau đối với `MyController`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@RestController
public static class MyController {
    @GetMapping
    @AuthorizeReturnObject
    List<Message> getMessages() {
        return List.of(new Message(someUser, "hello!"));
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@RestController
static class MyController {
    @AuthorizeReturnObject
    @GetMapping
    fun getMessages(): Array<Message> = arrayOf(Message(someUser, "hello!"))
}
----
======

Trong trường hợp này, generic type đã bị xóa nên Spring Security không thể biết trước rằng `Message` sẽ cần được proxy tại runtime.

Để giải quyết, bạn có thể publish `AuthorizeProxyFactoryHintsRegistrar` như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)

	return new AuthorizeReturnObjectHintsRegistrar(proxyFactory, Message.class);
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
@Role(BeanDefinition.ROLE_INFRASTRUCTURE)
fun registerTheseToo(proxyFactory: AuthorizationProxyFactory?): SecurityHintsRegistrar {
    return AuthorizeReturnObjectHintsRegistrar(proxyFactory, Message::class.java)
}
----
======

Spring Security sẽ đăng ký class đó rồi duyệt kiểu của nó như trước.

[[fallback-values-authorization-denied]]
== Cung cấp Giá trị Dự phòng Khi Authorization Bị Từ chối

Có một số trường hợp bạn có thể không muốn ném `AuthorizationDeniedException` khi method được gọi mà không có permission cần thiết.
Thay vào đó, bạn có thể muốn trả về kết quả đã được post-process, chẳng hạn kết quả được che, hoặc một giá trị mặc định trong trường hợp authorization bị từ chối trước khi gọi method.

Spring Security hỗ trợ xử lý authorization bị từ chối khi gọi method bằng javadoc:org.springframework.security.authorization.method.HandleAuthorizationDenied[format=annotation].
Handler này hoạt động với authorization bị từ chối xảy ra trong <<authorizing-with-annotations,annotation `@PreAuthorize` và `@PostAuthorize`>>, cũng như javadoc:org.springframework.security.authorization.AuthorizationDeniedException[] được ném từ chính lần gọi method.

Hãy xem ví dụ trong <<authorize-object,phần trước>>, nhưng thay vì tạo `AccessDeniedExceptionInterceptor` để chuyển `AccessDeniedException` thành giá trị trả về `null`, chúng ta sẽ sử dụng attribute `handlerClass` của `@HandleAuthorizationDenied`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
public class NullMethodAuthorizationDeniedHandler implements MethodAuthorizationDeniedHandler { <1>

    @Override
    public Object handleDeniedInvocation(MethodInvocation methodInvocation, AuthorizationResult authorizationResult) {
        return null;
    }

}

@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean <2>
    public NullMethodAuthorizationDeniedHandler nullMethodAuthorizationDeniedHandler() {
        return new NullMethodAuthorizationDeniedHandler();
    }

}

public class User {
    // ...

    @PreAuthorize(value = "hasAuthority('user:read')")
    @HandleAuthorizationDenied(handlerClass = NullMethodAuthorizationDeniedHandler.class)
    public String getEmail() {
        return this.email;
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

    }

@Configuration

<1> Tạo một implementation của `MethodAuthorizationDeniedHandler` trả về giá trị `null`
<2> Đăng ký `NullMethodAuthorizationDeniedHandler` dưới dạng bean
<3> Gắn `@HandleAuthorizationDenied` lên method và truyền `NullMethodAuthorizationDeniedHandler` vào attribute `handlerClass`

Sau đó, bạn có thể xác minh rằng giá trị `null` được trả về thay vì `AccessDeniedException`:

=== Sử dụng Kết quả Bị Từ chối từ Lần gọi Method

Có một số trường hợp bạn có thể muốn trả về kết quả an toàn được tạo ra từ kết quả bị từ chối.
Ví dụ, nếu người dùng không được authorization để xem địa chỉ email, bạn có thể muốn che một phần địa chỉ email ban đầu, tức là _useremail@example.com_ sẽ trở thành _use\\******@example.com_.

Trong các trường hợp đó, bạn có thể ghi đè `handleDeniedInvocationResult` của `MethodAuthorizationDeniedHandler`, method này nhận javadoc:org.springframework.security.authorization.method.MethodInvocationResult[] làm đối số.
Hãy tiếp tục với ví dụ trước, nhưng thay vì trả về `null`, chúng ta sẽ trả về giá trị email đã được che:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
public class EmailMaskingMethodAuthorizationDeniedHandler implements MethodAuthorizationDeniedHandler { <1>

    @Override
    public Object handleDeniedInvocation(MethodInvocation methodInvocation, AuthorizationResult authorizationResult) {
        return "***";
    }

    @Override
    public Object handleDeniedInvocationResult(MethodInvocationResult methodInvocationResult, AuthorizationResult authorizationResult) {
        String email = (String) methodInvocationResult.getResult();
        return email.replaceAll("(^[^@]{3}|(?!^)\\G)[^@]", "$1*");
    }

}

@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean <2>
    public EmailMaskingMethodAuthorizationDeniedHandler emailMaskingMethodAuthorizationDeniedHandler() {
        return new EmailMaskingMethodAuthorizationDeniedHandler();
    }

}

public class User {
    // ...

    @PostAuthorize(value = "hasAuthority('user:read')")
    @HandleAuthorizationDenied(handlerClass = EmailMaskingMethodAuthorizationDeniedHandler.class)
    public String getEmail() {
        return this.email;
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
class EmailMaskingMethodAuthorizationDeniedHandler : MethodAuthorizationDeniedHandler {

    override fun handleDeniedInvocation(methodInvocation: MethodInvocation, authorizationResult: AuthorizationResult): Any {
        return "***"
    }

    override fun handleDeniedInvocationResult(methodInvocationResult: MethodInvocationResult, authorizationResult: AuthorizationResult): Any {
        val email = methodInvocationResult.result as String
        return email.replace("(^[^@]{3}|(?!^)\\G)[^@]".toRegex(), "$1*")
    }

}

@Configuration

    @Bean

        return EmailMaskingMethodAuthorizationDeniedHandler()
    }

class User (val name:String, @PostAuthorize(value = "hasAuthority('user:read')") @HandleAuthorizationDenied(handlerClass = EmailMaskingMethodAuthorizationDeniedHandler::class) val email:String) <3>

======

<1> Tạo một implementation của `MethodAuthorizationDeniedHandler` trả về giá trị đã che của kết quả chưa được authorization
<2> Đăng ký `EmailMaskingMethodAuthorizationDeniedHandler` dưới dạng bean
<3> Gắn `@HandleAuthorizationDenied` lên method và truyền `EmailMaskingMethodAuthorizationDeniedHandler` vào attribute `handlerClass`

Sau đó, bạn có thể xác minh rằng email đã che được trả về thay vì `AccessDeniedException`:

[WARNING]
====
Vì bạn có quyền truy cập giá trị ban đầu bị từ chối, hãy bảo đảm xử lý đúng giá trị đó và không trả nó về cho caller.
====

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Autowired
UserRepository users;

@Test
void getEmailWhenProxiedThenMaskedEmail() {
    Optional<User> securedUser = users.findByName("name");
    // email is useremail@example.com
    assertThat(securedUser.get().getEmail()).isEqualTo("use******@example.com");
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

@Test

    // email is useremail@example.com
    assertThat(securedUser.get().getEmail()).isEqualTo("use******@example.com")
}
----
======

Khi implement `MethodAuthorizationDeniedHandler`, bạn có một số lựa chọn về kiểu có thể trả về:

- Giá trị `null`.
- Giá trị khác null, phù hợp với kiểu trả về của method.
- Ném một exception, thường là instance của `AuthorizationDeniedException`. Đây là behavior mặc định.
- Kiểu `Mono` cho các ứng dụng reactive.

Lưu ý rằng vì handler phải được đăng ký dưới dạng bean trong application context, bạn có thể inject dependency vào chúng nếu cần logic phức tạp hơn.
Ngoài ra, bạn có thể sử dụng `MethodInvocation` hoặc `MethodInvocationResult`, cũng như `AuthorizationResult` để lấy thêm chi tiết liên quan đến quyết định authorization.

[[deciding-return-based-parameters]]
=== Quyết định Giá trị Trả về Dựa trên Tham số Có sẵn

Hãy xem trường hợp có thể có nhiều giá trị mask cho các method khác nhau; việc phải tạo một handler cho từng method sẽ không hiệu quả, dù hoàn toàn có thể làm như vậy.
Trong những trường hợp đó, chúng ta có thể sử dụng thông tin được truyền qua tham số để quyết định phải làm gì.
Ví dụ, chúng ta có thể tạo annotation `@Mask` tùy chỉnh và một handler phát hiện annotation đó để quyết định giá trị mask cần trả về:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
import org.springframework.core.annotation.AnnotationUtils;

@Target({ ElementType.METHOD, ElementType.TYPE })
@Retention(RetentionPolicy.RUNTIME)
public @interface Mask {

    String value();

}

public class MaskAnnotationDeniedHandler implements MethodAuthorizationDeniedHandler {

    @Override
    public Object handleDeniedInvocation(MethodInvocation methodInvocation, AuthorizationResult authorizationResult) {
        Mask mask = AnnotationUtils.getAnnotation(methodInvocation.getMethod(), Mask.class);
        return mask.value();
    }

}

@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    public MaskAnnotationDeniedHandler maskAnnotationDeniedHandler() {
        return new MaskAnnotationDeniedHandler();
    }

}

@Component
public class MyService {

    @PreAuthorize(value = "hasAuthority('user:read')")
    @HandleAuthorizationDenied(handlerClass = MaskAnnotationDeniedHandler.class)
    @Mask("***")
    public String foo() {
        return "foo";
    }

    @PreAuthorize(value = "hasAuthority('user:read')")
    @HandleAuthorizationDenied(handlerClass = MaskAnnotationDeniedHandler.class)
    @Mask("???")
    public String bar() {
        return "bar";
    }

}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

=== Kết hợp với Tính năng Hỗ trợ Meta-Annotation

Bạn cũng có thể kết hợp `@HandleAuthorizationDenied` với các annotation khác để giảm bớt và đơn giản hóa số annotation trên một method.
Hãy xem <<deciding-return-based-parameters,ví dụ trong phần trước>> và hợp nhất `@HandleAuthorizationDenied` với `@Mask`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Target({ ElementType.METHOD, ElementType.TYPE })
@Retention(RetentionPolicy.RUNTIME)
@HandleAuthorizationDenied(handlerClass = MaskAnnotationDeniedHandler.class)
public @interface Mask {

    String value();

}

@Mask("***")
public String myMethod() {
    // ...
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----

Giờ đây, bạn không cần nhớ thêm cả hai annotation khi cần behavior mask trong method.

=== Sử dụng `@Bean` Tùy chỉnh thay vì Mở rộng `DefaultMethodSecurityExpressionHandler`

Để tối ưu hiệu năng, một method mới được thêm vào `MethodSecurityExpressionHandler`, nhận `Supplier<Authentication>` thay vì `Authentication`.

Điều này cho phép Spring Security trì hoãn việc tìm `Authentication`, và được tự động tận dụng khi bạn sử dụng `@EnableMethodSecurity` thay vì `@EnableGlobalMethodSecurity`.

Tuy nhiên, giả sử code của bạn mở rộng `DefaultMethodSecurityExpressionHandler` và ghi đè `createSecurityExpressionRoot(Authentication, MethodInvocation)` để trả về một instance `SecurityExpressionRoot` tùy chỉnh.
Cách này sẽ không còn hoạt động vì cấu hình do `@EnableMethodSecurity` thiết lập sẽ gọi `createEvaluationContext(Supplier<Authentication>, MethodInvocation)` thay thế.

May mắn là mức độ tùy chỉnh này thường không cần thiết.
Thay vào đó, bạn có thể tạo một bean tùy chỉnh với các method authorization cần thiết.

Ví dụ, giả sử bạn muốn đánh giá tùy chỉnh `@PostAuthorize("hasAuthority('ADMIN')")`.
Bạn có thể tạo `@Bean` tùy chỉnh như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
class MyAuthorizer {
	boolean isAdmin(MethodSecurityExpressionOperations root) {
		boolean decision = root.hasAuthority("ADMIN");
		// custom work ...
        return decision;
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
class MyAuthorizer {
	fun isAdmin(root: MethodSecurityExpressionOperations): boolean {
		val decision = root.hasAuthority("ADMIN");
		// custom work ...
        return decision;
	}
}
----
======

và sau đó tham chiếu nó trong annotation như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@PreAuthorize("@authz.isAdmin(#root)")
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@PreAuthorize("@authz.isAdmin(#root)")
----
======

[[subclass-defaultmethodsecurityexpressionhandler]]
==== Tôi vẫn muốn mở rộng `DefaultMethodSecurityExpressionHandler`

Nếu vẫn phải tiếp tục mở rộng `DefaultMethodSecurityExpressionHandler`, bạn vẫn có thể làm vậy.
Thay vào đó, hãy ghi đè method `createEvaluationContext(Supplier<Authentication>, MethodInvocation)` như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Component
class MyExpressionHandler extends DefaultMethodSecurityExpressionHandler {
    @Override
    public EvaluationContext createEvaluationContext(Supplier<Authentication> authentication, MethodInvocation mi) {
		StandardEvaluationContext context = (StandardEvaluationContext) super.createEvaluationContext(authentication, mi);
        MethodSecurityExpressionOperations delegate = (MethodSecurityExpressionOperations) context.getRootObject().getValue();
        MySecurityExpressionRoot root = new MySecurityExpressionRoot(delegate);
        context.setRootObject(root);
        return context;
    }
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Component
class MyExpressionHandler: DefaultMethodSecurityExpressionHandler {
    override fun createEvaluationContext(authentication: Supplier<Authentication>,
        val mi: MethodInvocation): EvaluationContext {
		val context = super.createEvaluationContext(authentication, mi) as StandardEvaluationContext
        val delegate = context.getRootObject().getValue() as MethodSecurityExpressionOperations
        val root = MySecurityExpressionRoot(delegate)
        context.setRootObject(root)
        return context
    }
}
