[[oauth2-dpop-bound-access-tokens]]
= Access token ràng buộc DPoP của OAuth 2.0

https://datatracker.ietf.org/doc/html/rfc9449[RFC 9449 OAuth 2.0 Demonstrating Proof of Possession (DPoP)] là một cơ chế ở cấp ứng dụng để ràng buộc access token theo bên gửi.

Mục tiêu chính của DPoP là ngăn các client không được ủy quyền hoặc không hợp lệ sử dụng access token bị rò rỉ hoặc đánh cắp, bằng cách ràng buộc access token với một khóa công khai khi authorization server cấp token và yêu cầu client chứng minh quyền sở hữu khóa riêng tương ứng khi sử dụng access token tại resource server.

Access token được ràng buộc theo bên gửi thông qua DPoP khác với bearer token thông thường, vốn có thể được sử dụng bởi bất kỳ client nào sở hữu access token đó.

DPoP giới thiệu khái niệm https://datatracker.ietf.org/doc/html/rfc9449#name-dpop-proof-jwts[bằng chứng DPoP], là một JWT được client tạo và gửi dưới dạng header trong HTTP request.
Client sử dụng bằng chứng DPoP để chứng minh quyền sở hữu khóa riêng tương ứng với một khóa công khai cụ thể.

Khi client khởi tạo một <<dpop-access-token-request,yêu cầu access token>>, client đính kèm bằng chứng DPoP vào request trong một HTTP header.
Authorization server ràng buộc (ràng buộc theo bên gửi) access token với khóa công khai được liên kết trong bằng chứng DPoP.

Khi client khởi tạo một <<dpop-protected-resource-request,yêu cầu tài nguyên được bảo vệ>>, client lại đính kèm bằng chứng DPoP vào request trong một HTTP header.

Resource server lấy thông tin về khóa công khai được ràng buộc với access token, trực tiếp trong access token (JWT) hoặc thông qua token introspection endpoint.
Sau đó, resource server xác minh rằng khóa công khai được ràng buộc với access token khớp với khóa công khai trong bằng chứng DPoP.
Resource server cũng xác minh rằng hash của access token trong bằng chứng DPoP khớp với access token trong request.

[[dpop-access-token-request]]
== Yêu cầu access token DPoP

Để yêu cầu một access token được ràng buộc với khóa công khai bằng DPoP, client MUST cung cấp bằng chứng DPoP hợp lệ trong header `DPoP` khi thực hiện yêu cầu access token tới token endpoint của authorization server.
Điều này áp dụng cho mọi yêu cầu access token, bất kể authorization grant type (ví dụ: `authorization_code`, `refresh_token`, `client_credentials`, v.v.).

Đoạn code sau đây minh họa cách tạo JWT bằng chứng DPoP:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
RSAKey rsaKey = ...
JWKSource<SecurityContext> jwkSource = (jwkSelector, securityContext) -> jwkSelector
		.select(new JWKSet(rsaKey));
NimbusJwtEncoder jwtEncoder = new NimbusJwtEncoder(jwkSource);

JwsHeader jwsHeader = JwsHeader.with(SignatureAlgorithm.RS256)
		.type("dpop+jwt")
		.jwk(rsaKey.toPublicJWK().toJSONObject())
		.build();
JwtClaimsSet claims = JwtClaimsSet.builder()
		.issuedAt(Instant.now())
		.claim("htm", "POST")
		.claim("htu", "https://server.example.com/oauth2/token")
		.id(UUID.randomUUID().toString())
		.build();

Jwt dPoPProof = jwtEncoder.encode(JwtEncoderParameters.from(jwsHeader, claims));
----
======

Sau khi authorization server xác minh thành công bằng chứng DPoP, khóa công khai từ bằng chứng DPoP sẽ được ràng buộc (ràng buộc theo bên gửi) với access token đã cấp.

Phản hồi access token sau đây đặt tham số `token_type` là `DPoP` để báo hiệu cho client rằng access token đã được ràng buộc với khóa công khai trong bằng chứng DPoP:

[source,shell]
----
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
 "access_token": "Kz~8mXK1EalYznwH-LC-1fBAo.4Ljp~zsPE_NeO.gxU",
 "token_type": "DPoP",
 "expires_in": 2677
}
----

[[dpop-public-key-confirmation]]
== Xác nhận khóa công khai

Resource server MUST có khả năng xác định access token có được ràng buộc DPoP hay không và xác minh việc ràng buộc với khóa công khai của bằng chứng DPoP.
Việc ràng buộc được thực hiện bằng cách liên kết khóa công khai với access token theo cách resource server có thể truy cập, chẳng hạn như nhúng trực tiếp hash của khóa công khai vào access token (JWT) hoặc thông qua token introspection.

Khi access token được biểu diễn dưới dạng JWT, hash của khóa công khai được chứa trong claim `jkt`, bên dưới claim phương thức xác nhận (`cnf`).

Ví dụ sau đây minh họa các claim của JWT access token chứa claim `cnf` với claim `jkt`, là JWK SHA-256 Thumbprint của khóa công khai trong bằng chứng DPoP:

[source,json]
----
{
  "sub":"user@example.com",
  "iss":"https://server.example.com",
  "nbf":1562262611,
  "exp":1562266216,
  "cnf":
  {
    "jkt":"CQMknzRoZ5YUi7vS58jck1q8TmZT8wiIiXrCN1Ny4VU"
  }
}
----

[[dpop-protected-resource-request]]
== Yêu cầu tài nguyên được bảo vệ DPoP

Request tới tài nguyên được bảo vệ bằng DPoP MUST bao gồm cả bằng chứng DPoP và access token được ràng buộc DPoP.
Bằng chứng DPoP MUST bao gồm claim `ath` chứa hash hợp lệ của access token.
Resource server sẽ tính hash của access token nhận được và xác minh rằng hash này giống với claim `ath` trong bằng chứng DPoP.

Access token được ràng buộc DPoP được gửi bằng request header `Authorization` với authentication scheme là `DPoP`.

HTTP request sau đây minh họa request tới tài nguyên được bảo vệ, với access token được ràng buộc DPoP trong header `Authorization` và bằng chứng DPoP trong header `DPoP`:

[source,shell]
----
