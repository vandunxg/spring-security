[[oauth2login-advanced]]
= Cấu hình nâng cao

`HttpSecurity.oauth2Login()` cung cấp một số tùy chọn cấu hình để tùy chỉnh OAuth 2.0 Login.
Các tùy chọn cấu hình chính được nhóm theo các protocol endpoint tương ứng.

Ví dụ, `oauth2Login().authorizationEndpoint()` cho phép cấu hình _Authorization Endpoint_, trong khi `oauth2Login().tokenEndpoint()` cho phép cấu hình _Token Endpoint_.

Đoạn code sau đây minh họa cấu hình này:

.Cấu hình OAuth2 Login nâng cao
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableWebSecurity
public class OAuth2LoginSecurityConfig {

	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
			.oauth2Login((oauth2) -> oauth2
			    .authorizationEndpoint((authorization) -> authorization
			            ...
			    )
			    .redirectionEndpoint((redirection) -> redirection
			            ...
			    )
			    .tokenEndpoint((token) -> token
			            ...
			    )
			    .userInfoEndpoint((userInfo) -> userInfo
			            ...
			    )
			);
		return http.build();
	}
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Configuration
@EnableWebSecurity
class OAuth2LoginSecurityConfig {

    @Bean
    open fun filterChain(http: HttpSecurity): SecurityFilterChain {
        http {
            oauth2Login {
                authorizationEndpoint {
                    ...
                }
                redirectionEndpoint {
                    ...
                }
                tokenEndpoint {
                    ...
                }
                userInfoEndpoint {
                    ...
                }
            }
        }
        return http.build()
    }
}
----
======

Mục tiêu chính của DSL `oauth2Login()` là bám sát cách đặt tên được định nghĩa trong các specification.

OAuth 2.0 Authorization Framework định nghĩa các https://tools.ietf.org/html/rfc6749#section-3[Protocol Endpoints] như sau:

Quy trình authorization sử dụng hai endpoint của Authorization Server (các HTTP resource):

* Authorization Endpoint: Được client sử dụng để lấy authorization từ resource owner thông qua chuyển hướng user-agent.
* Token Endpoint: Được client sử dụng để đổi authorization grant lấy access token, thường kèm theo client authentication.

Quy trình authorization cũng sử dụng một client endpoint:

* Redirection Endpoint: Được Authorization Server sử dụng để trả về các response chứa các authorization credential cho client thông qua user-agent của resource owner.

OpenID Connect Core 1.0 specification định nghĩa https://openid.net/specs/openid-connect-core-1_0.html#UserInfo[UserInfo Endpoint] như sau:

UserInfo Endpoint là một OAuth 2.0 Protected Resource trả về các claim về end-user đã được authenticated.
Để lấy các claim được yêu cầu về end-user, client gửi request đến UserInfo Endpoint bằng access token nhận được thông qua OpenID Connect Authentication.
Các claim này thường được biểu diễn dưới dạng một JSON object chứa một tập hợp các cặp name-value của claim.

Đoạn code sau đây cho thấy đầy đủ các tùy chọn cấu hình có sẵn trong DSL `oauth2Login()`:

.Các tùy chọn cấu hình OAuth2 Login
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableWebSecurity
public class OAuth2LoginSecurityConfig {

	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
			.oauth2Login((oauth2) -> oauth2
			    .clientRegistrationRepository(this.clientRegistrationRepository())
			    .authorizedClientRepository(this.authorizedClientRepository())
			    .authorizedClientService(this.authorizedClientService())
			    .loginPage("/login")
			    .authorizationEndpoint((authorization) -> authorization
			        .baseUri(this.authorizationRequestBaseUri())
			        .authorizationRequestRepository(this.authorizationRequestRepository())
			        .authorizationRequestResolver(this.authorizationRequestResolver())
			    )
			    .redirectionEndpoint((redirection) -> redirection
			        .baseUri(this.authorizationResponseBaseUri())
			    )
			    .tokenEndpoint((token) -> token
			        .accessTokenResponseClient(this.accessTokenResponseClient())
			    )
			    .userInfoEndpoint((userInfo) -> userInfo
			        .userAuthoritiesMapper(this.userAuthoritiesMapper())
			        .userService(this.oauth2UserService())
			        .oidcUserService(this.oidcUserService())
			    )
			);
		return http.build();
	}
}
----

[[oauth2login-advanced-login-page]]
== Trang OAuth 2.0 Login

Theo mặc định, trang OAuth 2.0 Login được tự động tạo bởi `DefaultLoginPageGeneratingFilter`.
Trang login mặc định hiển thị từng OAuth Client đã được cấu hình, với `ClientRegistration.clientName` làm link có thể khởi tạo Authorization Request (hoặc OAuth 2.0 Login).

[NOTE]
====
Để `DefaultLoginPageGeneratingFilter` hiển thị link cho các OAuth Client đã cấu hình, `ClientRegistrationRepository` được đăng ký cũng cần implement `Iterable<ClientRegistration>`.
Xem `InMemoryClientRegistrationRepository` để tham khảo.
====

URL đích của link cho mỗi OAuth Client mặc định là:

`+OAuth2AuthorizationRequestRedirectFilter.DEFAULT_AUTHORIZATION_REQUEST_BASE_URI + "/{registrationId}"+`

Dòng sau đây minh họa một ví dụ:

[source,html]
----
<a href="/oauth2/authorization/google">Google</a>
----

Để ghi đè trang login mặc định, hãy cấu hình `oauth2Login().loginPage()` và (tùy chọn) `oauth2Login().authorizationEndpoint().baseUri()`.

Ví dụ sau đây minh họa cấu hình:

[[oauth2login-advanced-redirection-endpoint]]
== Redirection Endpoint

Redirection Endpoint được Authorization Server sử dụng để trả về Authorization Response (chứa các authorization credential) cho client thông qua user-agent của Resource Owner.

[TIP]
====
OAuth 2.0 Login sử dụng Authorization Code Grant.
Do đó, authorization credential là authorization code.
====

`baseUri` mặc định của Authorization Response (redirection endpoint) là `*/login/oauth2/code/**`, được định nghĩa trong `OAuth2LoginAuthenticationFilter.DEFAULT_FILTER_PROCESSES_URI`.

			        .baseUri("/login/oauth2/callback/*")

[[oauth2login-advanced-map-authorities]]
=== Ánh xạ authority của user

Sau khi user authenticated thành công với OAuth 2.0 Provider, `OAuth2User.getAuthorities()` (hoặc `OidcUser.getAuthorities()`) chứa danh sách các authority được cấp, được lấy từ `OAuth2UserRequest.getAccessToken().getScopes()` và thêm tiền tố `SCOPE_`.
Các authority được cấp này có thể được ánh xạ thành một tập hợp instance `GrantedAuthority` mới, rồi cung cấp cho `OAuth2AuthenticationToken` khi hoàn tất authentication.

[TIP]
`OAuth2AuthenticationToken.getAuthorities()` được sử dụng để authorize các request, chẳng hạn trong `hasRole('USER')` hoặc `hasRole('ADMIN')`.

Có một số tùy chọn khi ánh xạ authority của user:

* <<oauth2login-advanced-map-authorities-grantedauthoritiesmapper>>
* <<oauth2login-advanced-map-authorities-oauth2userservice>>


[[oauth2login-advanced-map-authorities-grantedauthoritiesmapper]]
==== Sử dụng GrantedAuthoritiesMapper

`GrantedAuthoritiesMapper` nhận một danh sách authority đã cấp, trong đó có authority đặc biệt thuộc kiểu `OAuth2UserAuthority` và authority string `OAUTH2_USER` (hoặc `OidcUserAuthority` và authority string `OIDC_USER`).

Cung cấp một implementation của `GrantedAuthoritiesMapper` và cấu hình như sau:

.Cấu hình Granted Authorities Mapper
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableWebSecurity
public class OAuth2LoginSecurityConfig {

    @Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
			.oauth2Login((oauth2) -> oauth2
			    .userInfoEndpoint((userInfo) -> userInfo
			        .userAuthoritiesMapper(this.userAuthoritiesMapper())
			        ...
			    )
			);
		return http.build();
	}

	private GrantedAuthoritiesMapper userAuthoritiesMapper() {
		return (authorities) -> {
			Set<GrantedAuthority> mappedAuthorities = new HashSet<>();

			authorities.forEach(authority -> {
				if (OidcUserAuthority.class.isInstance(authority)) {
					OidcUserAuthority oidcUserAuthority = (OidcUserAuthority)authority;

					OidcIdToken idToken = oidcUserAuthority.getIdToken();
					OidcUserInfo userInfo = oidcUserAuthority.getUserInfo();

					// Ánh xạ các claim tìm thấy trong idToken và/hoặc userInfo
					// thành một hoặc nhiều GrantedAuthority rồi thêm vào mappedAuthorities

				} else if (OAuth2UserAuthority.class.isInstance(authority)) {
					OAuth2UserAuthority oauth2UserAuthority = (OAuth2UserAuthority)authority;

					Map<String, Object> userAttributes = oauth2UserAuthority.getAttributes();

					// Ánh xạ các attribute tìm thấy trong userAttributes
					// thành một hoặc nhiều GrantedAuthority rồi thêm vào mappedAuthorities

				}
			});

			return mappedAuthorities;
		};
	}
}
----

[[oauth2login-advanced-map-authorities-oauth2userservice]]
==== Chiến lược dựa trên delegation với OAuth2UserService

Chiến lược này nâng cao hơn so với việc sử dụng `GrantedAuthoritiesMapper`. Tuy nhiên, nó cũng linh hoạt hơn vì cho phép bạn truy cập `OAuth2UserRequest` và `OAuth2User` (khi sử dụng OAuth 2.0 UserService) hoặc `OidcUserRequest` và `OidcUser` (khi sử dụng OpenID Connect 1.0 UserService).

`OAuth2UserRequest` (và `OidcUserRequest`) cho phép truy cập `OAuth2AccessToken` tương ứng. Điều này rất hữu ích khi _delegator_ cần lấy thông tin authority từ một protected resource trước khi có thể ánh xạ các authority tùy chỉnh cho user.

Ví dụ sau đây cho thấy cách implement và cấu hình một chiến lược dựa trên delegation bằng một OpenID Connect 1.0 UserService:

.Cấu hình OAuth2UserService
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableWebSecurity
public class OAuth2LoginSecurityConfig {

	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
			.oauth2Login((oauth2) -> oauth2
			    .userInfoEndpoint((userInfo) -> userInfo
			        .oidcUserService(this.oidcUserService())
			        ...
			    )
			);
		return http.build();
	}

	private OAuth2UserService<OidcUserRequest, OidcUser> oidcUserService() {
		final OidcUserService delegate = new OidcUserService();

		return (userRequest) -> {
			// Delegate cho implementation mặc định để load user
			OidcUser oidcUser = delegate.loadUser(userRequest);

			OAuth2AccessToken accessToken = userRequest.getAccessToken();
			Set<GrantedAuthority> mappedAuthorities = new HashSet<>();

			// TODO
			// 1) Lấy thông tin authority từ protected resource bằng accessToken
			// 2) Ánh xạ thông tin authority thành một hoặc nhiều GrantedAuthority rồi thêm vào mappedAuthorities

			// 3) Tạo một bản sao của oidcUser nhưng sử dụng mappedAuthorities thay thế
			ProviderDetails providerDetails = userRequest.getClientRegistration().getProviderDetails();
			String userNameAttributeName = providerDetails.getUserInfoEndpoint().getUserNameAttributeName();
			if (StringUtils.hasText(userNameAttributeName)) {
				oidcUser = new DefaultOidcUser(mappedAuthorities, oidcUser.getIdToken(), oidcUser.getUserInfo(), userNameAttributeName);
			} else {
				oidcUser = new DefaultOidcUser(mappedAuthorities, oidcUser.getIdToken(), oidcUser.getUserInfo());
			}

			return oidcUser;
		};
	}
}

[[oauth2login-advanced-oauth2-user-service]]
=== OAuth 2.0 UserService

`DefaultOAuth2UserService` là một implementation của `OAuth2UserService` hỗ trợ các OAuth 2.0 Provider chuẩn.

[NOTE]
====
`OAuth2UserService` lấy các user attribute của end-user (resource owner) từ UserInfo Endpoint (bằng access token được cấp cho client trong authorization flow) và trả về một `AuthenticatedPrincipal` dưới dạng `OAuth2User`.
====

`DefaultOAuth2UserService` sử dụng một instance `RestOperations` khi request các user attribute tại UserInfo Endpoint.

Nếu cần tùy chỉnh việc xử lý trước UserInfo Request, bạn có thể cung cấp một `Converter<OAuth2UserRequest, RequestEntity<?>>` tùy chỉnh cho `DefaultOAuth2UserService.setRequestEntityConverter()`.
Implementation mặc định `OAuth2UserRequestEntityConverter` tạo một biểu diễn `RequestEntity` của UserInfo Request, mặc định đặt `OAuth2AccessToken` trong header `Authorization`.

Mặt khác, nếu cần tùy chỉnh việc xử lý sau UserInfo Response, bạn cần cung cấp một `RestOperations` được cấu hình tùy chỉnh cho `DefaultOAuth2UserService.setRestOperations()`.
`RestOperations` mặc định được cấu hình như sau:

[source,java]
----
RestTemplate restTemplate = new RestTemplate();
restTemplate.setErrorHandler(new OAuth2ErrorResponseErrorHandler());
----

`OAuth2ErrorResponseErrorHandler` là một `ResponseErrorHandler` có thể xử lý OAuth 2.0 Error (400 Bad Request).
Nó sử dụng `OAuth2ErrorHttpMessageConverter` để chuyển đổi các tham số OAuth 2.0 Error thành một `OAuth2Error`.

Dù tùy chỉnh `DefaultOAuth2UserService` hay cung cấp implementation riêng của `OAuth2UserService`, bạn cần cấu hình như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Configuration
@EnableWebSecurity
public class OAuth2LoginSecurityConfig {

	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
			.oauth2Login((oauth2) -> oauth2
			    .userInfoEndpoint((userInfo) -> userInfo
			        .userService(this.oauth2UserService())
			        ...
			    )
			);
		return http.build();
	}

	private OAuth2UserService<OAuth2UserRequest, OAuth2User> oauth2UserService() {
		...
	}
}
----

+
[source,kotlin,role="secondary"]
----

[[oauth2login-advanced-idtoken-verify]]
== Xác minh chữ ký ID Token

OpenID Connect 1.0 Authentication giới thiệu https://openid.net/specs/openid-connect-core-1_0.html#IDToken[ID Token], một security token chứa các Claim về việc một End-User được Authorization Server authenticated khi token được Client sử dụng.

ID Token được biểu diễn dưới dạng https://tools.ietf.org/html/rfc7519[JSON Web Token] (JWT) và MUST được ký bằng https://tools.ietf.org/html/rfc7515[JSON Web Signature] (JWS).

`OidcIdTokenDecoderFactory` cung cấp một `JwtDecoder` được sử dụng để xác minh chữ ký `OidcIdToken`. Algorithm mặc định là `RS256` nhưng có thể khác nếu được gán trong quá trình đăng ký client.
Trong các trường hợp này, bạn có thể cấu hình một resolver để trả về JWS algorithm dự kiến được gán cho một client cụ thể.

JWS algorithm resolver là một `Function` nhận `ClientRegistration` và trả về `JwsAlgorithm` dự kiến cho client, chẳng hạn `SignatureAlgorithm.RS256` hoặc `MacAlgorithm.HS256`.

Đoạn code sau đây cho thấy cách cấu hình `@Bean` `OidcIdTokenDecoderFactory` để mặc định sử dụng `MacAlgorithm.HS256` cho mọi instance `ClientRegistration`:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
public JwtDecoderFactory<ClientRegistration> idTokenDecoderFactory() {
	OidcIdTokenDecoderFactory idTokenDecoderFactory = new OidcIdTokenDecoderFactory();
	idTokenDecoderFactory.setJwsAlgorithmResolver((clientRegistration) -> clientRegistration.HS256);
	return idTokenDecoderFactory;
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
fun idTokenDecoderFactory(): JwtDecoderFactory<ClientRegistration?> {
    val idTokenDecoderFactory = OidcIdTokenDecoderFactory()
    idTokenDecoderFactory.setJwsAlgorithmResolver { MacAlgorithm.HS256 }
    return idTokenDecoderFactory
}
----
======

[NOTE]
====
Đối với các algorithm dựa trên MAC (chẳng hạn `HS256`, `HS384` hoặc `HS512`), `client-secret` tương ứng với `client-id` được sử dụng làm symmetric key để xác minh chữ ký.
====

[TIP]
====
Nếu có nhiều hơn một `ClientRegistration` được cấu hình cho OpenID Connect 1.0 Authentication, JWS algorithm resolver có thể đánh giá `ClientRegistration` được cung cấp để xác định algorithm cần trả về.
====

[[oauth2login-advanced-idtoken-decoder-factory]]
== Cung cấp JwtDecoderFactory tùy chỉnh

`OidcIdTokenDecoderFactory` được thiết kế có phạm vi hẹp một cách có chủ đích: nó tồn tại để giúp dễ dàng hỗ trợ nhiều instance `ClientRegistration`, mỗi instance có thể cần một `JwtDecoder` khác nhau, và bề mặt cấu hình của nó được giới hạn ở những gì hầu hết application cần cho mục đích đó, chẳng hạn JWS algorithm resolver được trình bày ở trên.

Nếu application cần kiểm soát sâu hơn cách tạo `JwtDecoder` của ID Token -- ví dụ cung cấp `RestOperations` riêng -- bạn có thể thay vào đó cung cấp `JwtDecoderFactory<ClientRegistration>` `@Bean` riêng.
Vì OAuth2 Login không sử dụng bean `JwtDecoder` của resource server cho mục đích này, đây là cách được hỗ trợ để đạt cùng mức độ kiểm soát mà builder của `NimbusJwtDecoder` đã cung cấp, mà không cần bổ sung các configuration property trên chính `OidcIdTokenDecoderFactory`.

Với một `ClientRegistration` duy nhất, việc này có thể đơn giản như sau:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
JwtDecoderFactory<ClientRegistration> idTokenDecoderFactory(RestOperations rest) {
	return (clientRegistration) -> {
		String issuerUri = clientRegistration.getProviderDetails().getIssuerUri();
		NimbusJwtDecoder decoder = NimbusJwtDecoder.withIssuerLocation(issuerUri).restOperations(rest).build();
		decoder.setJwtValidator(JwtValidators.createDefaultWithValidators(new OidcIdTokenValidator(clientRegistration)));
		decoder.setClaimTypeConverter(OidcIdTokenDecoderFactory.createDefaultClaimTypeConverter());
		return decoder;
	};
}
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
fun idTokenDecoderFactory(rest: RestOperations): JwtDecoderFactory<ClientRegistration> {
    return JwtDecoderFactory { clientRegistration ->
        val issuerUri = clientRegistration.providerDetails.issuerUri
        val decoder = NimbusJwtDecoder.withIssuerLocation(issuerUri).restOperations(rest).build()
        decoder.setJwtValidator(JwtValidators.createDefaultWithValidators(OidcIdTokenValidator(clientRegistration)))
        decoder.setClaimTypeConverter(OidcIdTokenDecoderFactory.createDefaultClaimTypeConverter())
        decoder
    }
}
----
======

Nếu có nhiều instance `ClientRegistration` và muốn tránh việc tạo lại `JwtDecoder` trong mỗi request, hãy cache decoder theo từng registration, chẳng hạn bằng cách gắn annotation `@Cacheable` cho factory method hoặc dùng `ClientRegistration#getRegistrationId()` làm key cho một `Map`.
