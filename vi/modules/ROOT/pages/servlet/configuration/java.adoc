
[[jc]]
= Cấu hình Java

Hỗ trợ chung cho {spring-framework-reference-url}core/beans/java.html[cấu hình Java] được thêm vào Spring Framework trong Spring 3.1.
Spring Security 3.2 giới thiệu cấu hình Java để người dùng có thể cấu hình Spring Security mà không cần sử dụng XML.

Nếu bạn đã quen với xref:servlet/configuration/xml-namespace.adoc#ns-config[Security Namespace Configuration], bạn sẽ thấy khá nhiều điểm tương đồng giữa cách đó và Java configuration của Spring Security.

[NOTE]
====
Spring Security cung cấp https://github.com/spring-projects/spring-security-samples/tree/main/servlet/java-configuration[nhiều ứng dụng mẫu] để minh họa cách sử dụng Java Configuration của Spring Security.
====

[[jc-hello-wsca]]
== Cấu hình Java cho Hello Web Security

Bước đầu tiên là tạo Java Configuration cho Spring Security.
Cấu hình này tạo một Servlet Filter có tên là `springSecurityFilterChain`, chịu trách nhiệm cho toàn bộ chức năng security (bảo vệ URL của ứng dụng, validate username và password được submit, chuyển hướng đến form đăng nhập, v.v.) trong application của bạn.
Ví dụ sau đây là cấu hình Java cơ bản nhất của Spring Security:

[source,java]
----
import org.springframework.beans.factory.annotation.Autowired;

import org.springframework.context.annotation.*;
import org.springframework.security.config.annotation.authentication.builders.*;
import org.springframework.security.config.annotation.web.configuration.*;

@Configuration
@EnableWebSecurity
public class WebSecurityConfig {

	@Bean
	public UserDetailsService userDetailsService() {
		InMemoryUserDetailsManager manager = new InMemoryUserDetailsManager();
		manager.createUser(User.withDefaultPasswordEncoder().username("user").password("password").roles("USER").build());
		return manager;
	}
}
----

Cấu hình này không phức tạp hay dài dòng, nhưng thực hiện được nhiều việc:

* Yêu cầu authentication trên mọi URL trong application
* Tự động tạo form đăng nhập
* Cho phép user có *Username* là `user` và *Password* là `password` authenticate bằng form-based authentication
* Cho phép user logout
* Ngăn chặn https://en.wikipedia.org/wiki/Cross-site_request_forgery[CSRF attack]
* Bảo vệ khỏi https://en.wikipedia.org/wiki/Session_fixation[Session Fixation]
* Tích hợp Security Header:
** https://en.wikipedia.org/wiki/HTTP_Strict_Transport_Security[HTTP Strict Transport Security] cho các secure request
** Tích hợp https://msdn.microsoft.com/en-us/library/ie/gg622941(v=vs.85).aspx[X-Content-Type-Options]
** Cache Control (sau này bạn có thể ghi đè trong ứng dụng để cho phép cache các tài nguyên tĩnh)
** Tích hợp https://msdn.microsoft.com/en-us/library/dd565647(v=vs.85).aspx[X-XSS-Protection]
** Tích hợp X-Frame-Options để giúp ngăn chặn https://en.wikipedia.org/wiki/Clickjacking[Clickjacking]
* Tích hợp với các method sau của Servlet API:
** https://docs.oracle.com/javaee/6/api/javax/servlet/http/HttpServletRequest.html#getRemoteUser()[`HttpServletRequest#getRemoteUser()`]
** https://docs.oracle.com/javaee/6/api/javax/servlet/http/HttpServletRequest.html#getUserPrincipal()[`HttpServletRequest#getUserPrincipal()`]
** https://docs.oracle.com/javaee/6/api/javax/servlet/http/HttpServletRequest.html#isUserInRole(java.lang.String)[`HttpServletRequest#isUserInRole(java.lang.String)`]
** https://docs.oracle.com/javaee/6/api/javax/servlet/http/HttpServletRequest.html#login(java.lang.String,%20java.lang.String)[`HttpServletRequest#login(java.lang.String, java.lang.String)`]
** https://docs.oracle.com/javaee/6/api/javax/servlet/http/HttpServletRequest.html#logout()[`HttpServletRequest#logout()`]

=== AbstractSecurityWebApplicationInitializer

Bước tiếp theo là đăng ký `springSecurityFilterChain` vào WAR file.
Bạn có thể thực hiện việc này bằng Java configuration với {spring-framework-reference-url}web/webmvc/mvc-servlet/container-config.html[hỗ trợ `WebApplicationInitializer` của Spring] trong môi trường Servlet 3.0+.
Không có gì ngạc nhiên khi Spring Security cung cấp một base class (`AbstractSecurityWebApplicationInitializer`) để đảm bảo `springSecurityFilterChain` được đăng ký cho bạn.
Cách sử dụng `AbstractSecurityWebApplicationInitializer` khác nhau tùy thuộc vào việc ứng dụng đã sử dụng Spring hay Spring Security là component Spring duy nhất trong ứng dụng.

* <<abstractsecuritywebapplicationinitializer-without-existing-spring>> - Sử dụng các hướng dẫn này nếu application chưa sử dụng Spring
* <<abstractsecuritywebapplicationinitializer-with-spring-mvc>> - Sử dụng các hướng dẫn này nếu application đã sử dụng Spring

[[abstractsecuritywebapplicationinitializer-without-existing-spring]]
=== AbstractSecurityWebApplicationInitializer khi chưa có Spring

Nếu bạn không sử dụng Spring hoặc Spring MVC, bạn cần truyền `WebSecurityConfig` cho superclass để đảm bảo configuration được load:

[source,java]
----
import org.springframework.security.web.context.*;

public class SecurityWebApplicationInitializer
	extends AbstractSecurityWebApplicationInitializer {

	public SecurityWebApplicationInitializer() {
		super(WebSecurityConfig.class);
	}
}
----

`SecurityWebApplicationInitializer` sẽ:

* Tự động đăng ký Filter `springSecurityFilterChain` cho mọi URL trong application.
* Thêm một `ContextLoaderListener` load <<jc-hello-wsca,WebSecurityConfig>>.

[[abstractsecuritywebapplicationinitializer-with-spring-mvc]]
=== AbstractSecurityWebApplicationInitializer với Spring MVC

Nếu sử dụng Spring ở nơi khác trong application, có lẽ chúng ta đã có một `WebApplicationInitializer` đang load Spring configuration.
Nếu sử dụng configuration trước đó, chúng ta sẽ gặp lỗi.
Thay vào đó, chúng ta nên đăng ký Spring Security với `ApplicationContext` hiện có.
Ví dụ, nếu sử dụng Spring MVC, `SecurityWebApplicationInitializer` có thể trông như sau:

[source,java]
----
import org.springframework.security.web.context.*;

public class SecurityWebApplicationInitializer
	extends AbstractSecurityWebApplicationInitializer {

}
----

Việc này chỉ đăng ký `springSecurityFilterChain` cho mọi URL trong application.
Sau đó, chúng ta cần đảm bảo `WebSecurityConfig` được load trong `ApplicationInitializer` hiện có.
Ví dụ, nếu sử dụng Spring MVC, nó được thêm vào `getServletConfigClasses()`:

[[message-web-application-inititializer-java]]
[source,java]
----
public class MvcWebApplicationInitializer extends
		AbstractAnnotationConfigDispatcherServletInitializer {

	@Override
	protected Class<?>[] getServletConfigClasses() {
		return new Class[] { WebSecurityConfig.class, WebMvcConfig.class };
	}

	// ... các override khác ...
}
----

Lý do là Spring Security cần inspect một số Spring MVC configuration để cấu hình chính xác xref:servlet/authorization/authorize-http-requests.adoc#authorizing-endpoints[các request matcher tương ứng], vì vậy chúng cần nằm trong cùng một application context.
Đặt Spring Security trong `getRootConfigClasses` sẽ đưa nó vào một application context cha, nơi có thể không tìm thấy `PathPatternParser` của Spring MVC.

==== Cấu hình cho nhiều Spring MVC Dispatcher

Nếu muốn, mọi cấu hình Spring Security không liên quan đến Spring MVC có thể được đặt trong một configuration class khác như sau:

[source,java]
----
public class MvcWebApplicationInitializer extends
		AbstractAnnotationConfigDispatcherServletInitializer {

	@Override
    protected Class<?>[] getRootConfigClasses() {
		return new Class[] { NonWebSecurityConfig.class };
    }

	@Override
	protected Class<?>[] getServletConfigClasses() {
		return new Class[] { WebSecurityConfig.class, WebMvcConfig.class };
	}

	// ... các override khác ...
}
----

Điều này hữu ích nếu bạn có nhiều instance của `AbstractAnnotationConfigDispatcherServletInitializer` và không muốn nhân bản cấu hình bảo mật chung trong tất cả chúng.

[[jc-httpsecurity]]
== HttpSecurity

Cho đến nay, <<jc-hello-wsca,`WebSecurityConfig`>> của chúng ta chỉ chứa thông tin về cách authenticate user.
Làm thế nào Spring Security biết chúng ta muốn yêu cầu mọi user phải authenticated?
Làm thế nào Spring Security biết chúng ta muốn hỗ trợ authentication dựa trên form?
Thực ra có một configuration class (được gọi là `SecurityFilterChain`) được invoke ngầm phía sau.
Nó được cấu hình bằng implementation mặc định sau:

[source,java]
----
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
	http
		.authorizeHttpRequests((authorize) -> authorize
			.anyRequest().authenticated()
		)
		.formLogin(Customizer.withDefaults())
		.httpBasic(Customizer.withDefaults());
	return http.build();
}
----

Cấu hình mặc định (được minh họa trong ví dụ trước):

* Đảm bảo mọi request đến application đều yêu cầu user phải authenticated
* Cho phép user authenticate bằng form-based login
* Cho phép user authenticate bằng HTTP Basic authentication

Lưu ý rằng cấu hình này tương đương với cấu hình XML namespace:

[source,xml]
----
<http>
	<intercept-url pattern="/**" access="authenticated"/>
	<form-login />
	<http-basic />
</http>
----

=== Nhiều instance HttpSecurity

Để quản lý security hiệu quả trong một application mà một số khu vực cần mức bảo vệ khác nhau, chúng ta có thể sử dụng nhiều filter chain cùng với DSL method `securityMatcher`.
Cách tiếp cận này cho phép định nghĩa các security configuration riêng biệt phù hợp với từng phần cụ thể của application, qua đó tăng cường security và khả năng kiểm soát tổng thể.

Chúng ta có thể cấu hình nhiều instance `HttpSecurity`, tương tự như có nhiều block `<http>` trong XML.
Điểm cốt lõi là đăng ký nhiều `SecurityFilterChain` ``@Bean``.
Ví dụ sau có configuration khác dành cho các URL bắt đầu bằng `/api/`:

[[multiple-httpsecurity-instances-java]]
[source,java]
----
@Configuration
@EnableWebSecurity
public class MultiHttpSecurityConfig {
	@Bean                                                             <1>
	public UserDetailsService userDetailsService() throws Exception {
		UserBuilder users = User.withDefaultPasswordEncoder();
		InMemoryUserDetailsManager manager = new InMemoryUserDetailsManager();
		manager.createUser(users.username("user").password("password").roles("USER").build());
		manager.createUser(users.username("admin").password("password").roles("USER","ADMIN").build());
		return manager;
	}

	@Bean
	@Order(1)                                                        <2>
	public SecurityFilterChain apiFilterChain(HttpSecurity http) throws Exception {
		http
			.securityMatcher("/api/**")                              <3>
			.authorizeHttpRequests((authorize) -> authorize
				.anyRequest().hasRole("ADMIN")
			)
			.httpBasic(Customizer.withDefaults());
		return http.build();
	}

	@Bean                                                            <4>
	public SecurityFilterChain formLoginFilterChain(HttpSecurity http) throws Exception {
		http
			.authorizeHttpRequests((authorize) -> authorize
				.anyRequest().authenticated()
			)
			.formLogin(Customizer.withDefaults());
		return http.build();
	}
}
----
<1> Cấu hình Authentication như bình thường.
<2> Tạo một instance `SecurityFilterChain` có `@Order` để chỉ định `SecurityFilterChain` nào được xem xét trước.
<3> `http.securityMatcher()` cho biết `HttpSecurity` này chỉ áp dụng cho các URL bắt đầu bằng `/api/`.
<4> Tạo một instance `SecurityFilterChain` khác.
Nếu URL không bắt đầu bằng `/api/`, configuration này sẽ được sử dụng.
Configuration này được xem xét sau `apiFilterChain` vì có giá trị `@Order` sau `1` (không có `@Order` thì mặc định được xử lý sau cùng).

=== Chọn `securityMatcher` hay `requestMatchers`

Một câu hỏi thường gặp là:

> Sự khác nhau giữa method `http.securityMatcher()` và `requestMatchers()` được sử dụng cho request authorization (tức là bên trong `http.authorizeHttpRequests()`) là gì?

Để trả lời câu hỏi này, cần hiểu rằng mỗi instance `HttpSecurity` được sử dụng để xây dựng một `SecurityFilterChain` đều chứa một `RequestMatcher` để match các request gửi đến.
Nếu một request không match `SecurityFilterChain` có độ ưu tiên cao hơn (ví dụ `@Order(1)`), request đó có thể được đem match với filter chain có độ ưu tiên thấp hơn (ví dụ không có `@Order`).

[NOTE]
====
Logic matching cho nhiều filter chain được thực hiện bởi xref:servlet/architecture.adoc#servlet-filterchainproxy[`FilterChainProxy`].
====

`RequestMatcher` mặc định match *mọi request* để đảm bảo Spring Security *bảo vệ mọi request theo mặc định*.

[NOTE]
====
Việc chỉ định `securityMatcher` sẽ ghi đè giá trị mặc định này.
====

[WARNING]
====
Nếu không có filter chain nào match một request cụ thể, request đó sẽ *không được* Spring Security bảo vệ.
====

Ví dụ sau minh họa một filter chain duy nhất chỉ bảo vệ các request bắt đầu bằng `/secured/`:

[[choosing-security-matcher-request-matchers-java]]
[source,java]
----
@Configuration
@EnableWebSecurity
public class PartialSecurityConfig {

	@Bean
	public UserDetailsService userDetailsService() throws Exception {
		// ...
	}

	@Bean
	public SecurityFilterChain securedFilterChain(HttpSecurity http) throws Exception {
		http
			.securityMatcher("/secured/**")                            <1>
			.authorizeHttpRequests((authorize) -> authorize
				.requestMatchers("/secured/user").hasRole("USER")      <2>
				.requestMatchers("/secured/admin").hasRole("ADMIN")    <3>
				.anyRequest().authenticated()                          <4>
			)
			.httpBasic(Customizer.withDefaults())
			.formLogin(Customizer.withDefaults());
		return http.build();
	}
}
----
<1> Các request bắt đầu bằng `/secured/` sẽ được bảo vệ, còn các request khác thì không.
<2> Request đến `/secured/user` yêu cầu authority `ROLE_USER`.
<3> Request đến `/secured/admin` yêu cầu authority `ROLE_ADMIN`.
<4> Mọi request khác (chẳng hạn `/secured/other`) chỉ yêu cầu user phải authenticated.

[TIP]
====
_Khuyến nghị_ cung cấp một `SecurityFilterChain` không chỉ định `securityMatcher` để đảm bảo toàn bộ application được bảo vệ, như minh họa trong <<multiple-httpsecurity-instances-java,ví dụ trước đó>>.
====

Lưu ý rằng method `requestMatchers` chỉ áp dụng cho từng authorization rule riêng lẻ.
Mỗi request được liệt kê ở đó cũng phải match `securityMatcher` tổng thể của instance `HttpSecurity` cụ thể được sử dụng để tạo `SecurityFilterChain`.
Trong ví dụ này, `anyRequest()` match tất cả request còn lại bên trong `SecurityFilterChain` cụ thể này (các request đó phải bắt đầu bằng `/secured/`).

[NOTE]
====
Xem xref:servlet/authorization/authorize-http-requests.adoc[Authorization cho HttpServletRequests] để biết thêm thông tin về `requestMatchers`.
====

=== Các endpoint của `SecurityFilterChain`

Một số filter trong `SecurityFilterChain` trực tiếp cung cấp endpoint, chẳng hạn `UsernamePasswordAuthenticationFilter` được thiết lập bởi `http.formLogin()` và cung cấp endpoint `POST /login`.
Trong <<choosing-security-matcher-request-matchers-java,ví dụ trên>>, endpoint `/login` không match `http.securityMatcher("/secured/**")`, vì vậy application đó sẽ không có endpoint `GET /login` hoặc `POST /login`.
Các request như vậy sẽ trả về `404 Not Found`.
Điều này thường khiến người dùng bất ngờ.

Việc chỉ định `http.securityMatcher()` ảnh hưởng đến các request được `SecurityFilterChain` đó match.
Tuy nhiên, nó không tự động ảnh hưởng đến các endpoint do filter chain cung cấp.
Trong những trường hợp đó, bạn có thể cần tùy chỉnh URL của các endpoint mà bạn muốn filter chain cung cấp.

Ví dụ sau minh họa một configuration bảo vệ các request bắt đầu bằng `/secured/` và từ chối mọi request khác, đồng thời tùy chỉnh các endpoint do `SecurityFilterChain` cung cấp:

[[security-filter-chain-endpoints-java]]
[source,java]
----
@Configuration
@EnableWebSecurity
public class SecuredSecurityConfig {

	@Bean
	public UserDetailsService userDetailsService() throws Exception {
		// ...
	}

	@Bean
	@Order(1)
	public SecurityFilterChain securedFilterChain(HttpSecurity http) throws Exception {
		http
			.securityMatcher("/secured/**")                            <1>
			.authorizeHttpRequests((authorize) -> authorize
				.anyRequest().authenticated()                          <2>
			)
			.formLogin((formLogin) -> formLogin                          <3>
				.loginPage("/secured/login")
				.loginProcessingUrl("/secured/login")
				.permitAll()
			)
			.logout((logout) -> logout                                   <4>
				.logoutUrl("/secured/logout")
				.logoutSuccessUrl("/secured/login?logout")
				.permitAll()
			);
		return http.build();
	}

	@Bean
	public SecurityFilterChain defaultFilterChain(HttpSecurity http) throws Exception {
		http
			.authorizeHttpRequests((authorize) -> authorize
				.anyRequest().denyAll()                                <5>
			);
		return http.build();
	}
}
----
<1> Các request bắt đầu bằng `/secured/` sẽ được filter chain này bảo vệ.
<2> Các request bắt đầu bằng `/secured/` yêu cầu user đã được authenticated.
<3> Tùy chỉnh Form Login để thêm tiền tố `/secured/` vào URL.
<4> Tùy chỉnh logout để thêm tiền tố `/secured/` vào URL.
<5> Tất cả request khác sẽ bị từ chối.

[NOTE]
====
Ví dụ này tùy chỉnh các trang đăng nhập và logout, do đó vô hiệu hóa các trang được Spring Security tạo tự động.
Bạn phải xref:servlet/authentication/passwords/form.adoc#servlet-authentication-form-custom[tự cung cấp] các endpoint tùy chỉnh cho `GET /secured/login` và `GET /secured/logout`.
Lưu ý rằng Spring Security vẫn cung cấp các endpoint `POST /secured/login` và `POST /secured/logout` cho bạn.
====

=== Ví dụ thực tế

Ví dụ sau minh họa một cấu hình gần với thực tế hơn, kết hợp tất cả các thành phần này:

[[real-world-example-java]]
[source,java]
----
@Configuration
@EnableWebSecurity
public class BankingSecurityConfig {

    @Bean                                                              <1>
    public UserDetailsService userDetailsService() {
		UserBuilder users = User.withDefaultPasswordEncoder();
        InMemoryUserDetailsManager manager = new InMemoryUserDetailsManager();
        manager.createUser(users.username("user1").password("password").roles("USER", "VIEW_BALANCE").build());
        manager.createUser(users.username("user2").password("password").roles("USER").build());
        manager.createUser(users.username("admin").password("password").roles("ADMIN").build());
        return manager;
    }

    @Bean
    @Order(1)                                                          <2>
    public SecurityFilterChain approvalsSecurityFilterChain(HttpSecurity http) throws Exception {
        String[] approvalsPaths = { "/accounts/approvals/**", "/loans/approvals/**", "/credit-cards/approvals/**" };
        http
            .securityMatcher(approvalsPaths)
            .authorizeHttpRequests((authorize) -> authorize
				.anyRequest().hasRole("ADMIN")
            )
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }

    @Bean
    @Order(2)                                                          <3>
    public SecurityFilterChain bankingSecurityFilterChain(HttpSecurity http) throws Exception {
        String[] bankingPaths = { "/accounts/**", "/loans/**", "/credit-cards/**", "/balances/**" };
		String[] viewBalancePaths = { "/balances/**" };
        http
			.securityMatcher(bankingPaths)
			.authorizeHttpRequests((authorize) -> authorize
				.requestMatchers(viewBalancePaths).hasRole("VIEW_BALANCE")
				.anyRequest().hasRole("USER")
            );
        return http.build();
    }

    @Bean                                                              <4>
    public SecurityFilterChain defaultSecurityFilterChain(HttpSecurity http) throws Exception {
		String[] allowedPaths = { "/", "/user-login", "/user-logout", "/notices", "/contact", "/register" };
        http
            .authorizeHttpRequests((authorize) -> authorize
				.requestMatchers(allowedPaths).permitAll()
				.anyRequest().authenticated()
            )
			.formLogin((formLogin) -> formLogin
				.loginPage("/user-login")
				.loginProcessingUrl("/user-login")
			)
			.logout((logout) -> logout
				.logoutUrl("/user-logout")
				.logoutSuccessUrl("/?logout")
			);
        return http.build();
    }
}
----
<1> Bắt đầu bằng việc cấu hình authentication settings.
<2> Định nghĩa một instance `SecurityFilterChain` với `@Order(1)`, nghĩa là filter chain này có độ ưu tiên cao nhất.
    Filter chain này chỉ áp dụng cho các request bắt đầu bằng `/accounts/approvals/`, `/loans/approvals/` hoặc `/credit-cards/approvals/`.
	Các request được filter chain này xử lý yêu cầu authority `ROLE_ADMIN` và cho phép HTTP Basic Authentication.
<3> Tiếp theo, tạo một instance `SecurityFilterChain` khác với `@Order(2)`, được xem xét thứ hai.
    Filter chain này chỉ áp dụng cho các request bắt đầu bằng `/accounts/`, `/loans/`, `/credit-cards/` hoặc `/balances/`.
	Lưu ý rằng vì filter chain này được xem xét thứ hai, mọi request chứa `/approvals/` sẽ match filter chain trước đó và *không* được filter chain này match.
	Các request được filter chain này xử lý yêu cầu authority `ROLE_USER`.
	Filter chain này không định nghĩa authentication nào vì filter chain tiếp theo (mặc định) chứa cấu hình đó.
<4> Cuối cùng, tạo thêm một instance `SecurityFilterChain` không có annotation `@Order`.
    Cấu hình này sẽ xử lý các request không được các filter chain khác bao phủ và được xử lý sau cùng (không có `@Order` thì mặc định xử lý sau cùng).
    Các request match `/`, `/user-login`, `/user-logout`, `/notices`, `/contact` và `/register` được phép truy cập mà không cần authentication.
    Mọi request khác yêu cầu user phải được authenticated để truy cập bất kỳ URL nào không được cho phép rõ ràng hoặc không được các filter chain khác bảo vệ.

[[jc-custom-dsls]]
== DSL tùy chỉnh

Bạn có thể cung cấp DSL tùy chỉnh riêng trong Spring Security:

[tabs]
======
Java::
+
[source,java,role="primary"]
----
public class MyCustomDsl extends AbstractHttpConfigurer<MyCustomDsl, HttpSecurity> {
	private boolean flag;

	@Override
	public void init(HttpSecurity http) {
		// mọi method thêm một configurer khác
		// phải được thực hiện trong method init
		http.csrf(csrf -> csrf.disable());
	}

	@Override
	public void configure(HttpSecurity http) {
		ApplicationContext context = http.getSharedObject(ApplicationContext.class);

		// tra cứu từ ApplicationContext tại đây. Bạn cũng có thể tạo một instance mới.
		MyFilter myFilter = context.getBean(MyFilter.class);
		myFilter.setFlag(flag);
		http.addFilterBefore(myFilter, UsernamePasswordAuthenticationFilter.class);
	}

	public MyCustomDsl flag(boolean value) {
		this.flag = value;
		return this;
	}

	public static MyCustomDsl customDsl() {
		return new MyCustomDsl();
	}
}
----

+

[[top-level-customizer-bean]]
=== Các bean Customizer cấp cao nhất của HttpSecurity

Nếu muốn module hóa thêm security configuration, Spring Security sẽ tự động áp dụng mọi bean `Customizer` cấp cao nhất của `HttpSecurity`.

Có thể hiểu type `Customizer` cấp cao nhất của `HttpSecurity` là bất kỳ `Customizer<T>` nào khớp với `public HttpSecurity.*(Customizer<T>)`.
Điều này tương đương với mọi `Customizer<T>` là một argument duy nhất của một public method trên javadoc:org.springframework.security.config.annotation.web.builders.HttpSecurity[].

Một vài ví dụ có thể giúp làm rõ điều này.
Nếu `Customizer<ContentTypeOptionsConfig>` được expose dưới dạng bean, nó sẽ không được tự động áp dụng vì đó là một argument của javadoc:org.springframework.security.config.annotation.web.configurers.HeadersConfigurer#contentTypeOptions(org.springframework.security.config.Customizer)[], vốn không phải method được định nghĩa trên `HttpSecurity`.
Tuy nhiên, nếu `Customizer<HeadersConfigurer<HttpSecurity>>` được expose dưới dạng bean, nó sẽ được tự động áp dụng vì đó là một argument của javadoc:org.springframework.security.config.annotation.web.builders.HttpSecurity#headers(org.springframework.security.config.Customizer)[].

Ví dụ, cấu hình sau sẽ đảm bảo xref:servlet/exploits/headers.adoc#servlet-headers-csp[Content Security Policy] được đặt thành `object-src 'none'`:

[[customizer-bean-ordering]]
=== Thứ tự của bean Customizer

Trước tiên, mỗi xref:#httpsecurity-customizer-bean[bean Customizer<HttpSecurity>] được áp dụng bằng {spring-framework-api-url}org/springframework/beans/factory/ObjectProvider.html#orderedStream()[ObjectProvider#orderedStream()].
Điều này có nghĩa là nếu có nhiều bean `Customizer<HttpSecurity>`, có thể thêm annotation {spring-framework-api-url}org/springframework/core/annotation/Order.html[@Order] vào các định nghĩa bean để kiểm soát thứ tự.

Tiếp theo, từng type xref:#top-level-customizer-bean[bean HttpSecurity Customizer cấp cao nhất] được lookup và áp dụng bằng `ObjectProvider#orderedStream()`.
Nếu có hai bean `Customizer<HeadersConfigurer<HttpSecurity>>` và hai instance `Customizer<HttpsRedirectConfigurer<HttpSecurity>>`, thứ tự gọi từng type `Customizer` là không xác định.
Tuy nhiên, thứ tự của từng instance `Customizer<HttpsRedirectConfigurer<HttpSecurity>>` được xác định bởi `ObjectProvider#orderedStream()` và có thể được kiểm soát bằng `@Order` trên các định nghĩa bean.

Cuối cùng, `HttpSecurity` được inject như một bean.
Tất cả instance `Customizer` được áp dụng trước khi bean `HttpSecurity` được tạo.
Điều này cho phép ghi đè các tùy chỉnh do các bean `Customizer` cung cấp.

Bạn có thể xem ví dụ bên dưới minh họa thứ tự này:

include-code::./CustomizerBeanOrderingConfiguration[tag=sample,indent=0]

<1> Trước tiên, tất cả instance `Customizer<HttpSecurity>` được áp dụng.
Bean `adminAuthorization` có `@Order` cao nhất nên được áp dụng trước.
Nếu các bean `Customizer<HttpSecurity>` không có annotation `@Order` hoặc các annotation `@Order` có cùng giá trị, thứ tự áp dụng các instance `Customizer<HttpSecurity>` là không xác định.
<2> `userAuthorization` được áp dụng tiếp theo vì đây là một instance của `Customizer<HttpSecurity>`.
<3> Thứ tự của các type `Customizer` là không xác định.
Trong ví dụ này, thứ tự của `contentSecurityPolicy`, `contentTypeOptions` và `httpsRedirect` là không xác định.
Nếu thêm `@Order(Ordered.HIGHEST_PRECEDENCE)` vào `contentTypeOptions`, chúng ta sẽ biết `contentTypeOptions` đứng trước `contentSecurityPolicy` (chúng cùng type), nhưng không biết `httpsRedirect` đứng trước hay sau các bean `Customizer<HeadersConfigurer<HttpSecurity>>`.
<4> Sau khi tất cả bean `Customizer` được áp dụng, `HttpSecurity` được truyền vào như một bean.


[[post-processing-configured-objects]]
== Post-process các object đã được cấu hình

Java configuration của Spring Security không expose mọi property của mọi object mà nó cấu hình.
Điều này đơn giản hóa việc cấu hình cho phần lớn người dùng.
Suy cho cùng, nếu mọi property đều được expose, người dùng có thể sử dụng cấu hình bean tiêu chuẩn.

Mặc dù có những lý do chính đáng để không expose trực tiếp mọi property, người dùng vẫn có thể cần các tùy chọn cấu hình nâng cao hơn.
Để giải quyết vấn đề này, Spring Security giới thiệu khái niệm `ObjectPostProcessor`, có thể được sử dụng để sửa đổi hoặc thay thế nhiều instance `Object` được tạo bởi Java configuration.
Ví dụ, để cấu hình property `filterSecurityPublishAuthorizationSuccess` trên `FilterSecurityInterceptor`, bạn có thể sử dụng như sau:

[source,java]
----
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
	http
		.authorizeHttpRequests((authorize) -> authorize
			.anyRequest().authenticated()
			.withObjectPostProcessor(new ObjectPostProcessor<FilterSecurityInterceptor>() {
				public <O extends FilterSecurityInterceptor> O postProcess(
						O fsi) {
					fsi.setPublishAuthorizationSuccess(true);
					return fsi;
				}
			})
		);
	return http.build();
}
----
