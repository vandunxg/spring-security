<1> `@ExtendWith` chỉ dẫn cho module spring-test tạo một `ApplicationContext`. Để biết thêm thông tin, xem {spring-framework-reference-url}testing.html#testcontext-junit-jupiter-extension[tài liệu tham khảo của Spring].
<2> `@ContextConfiguration` chỉ dẫn cho spring-test configuration cần dùng để tạo `ApplicationContext`. Vì không chỉ định configuration, framework sẽ thử các configuration location mặc định. [NOTE]
====
Spring Security tích hợp với Spring Test support thông qua `WithSecurityContextTestExecutionListener`, đảm bảo test được chạy với đúng user.
Listener này thực hiện việc đó bằng cách populate `SecurityContextHolder` trước khi chạy test.
Nếu sử dụng reactive method security, cũng cần `ReactorContextTestExecutionListener`; listener này populate `ReactiveSecurityContextHolder`.
Sau khi test hoàn tất, listener xóa `SecurityContextHolder`.
Nếu chỉ cần Spring Security-related support, có thể thay `@ContextConfiguration` bằng `@SecurityTestExecutionListeners`.
====

== @WithMockUser

Câu hỏi là: "Làm thế nào để dễ dàng nhất chạy test dưới một user cụ thể?"
Câu trả lời là sử dụng `@WithMockUser`.
Test sau sẽ chạy dưới một user có username là "user", password là "password" và role là "ROLE_USER".

include-code::./WithMockUserTests[tag=mock-user,indent=0]

Cụ thể:

* User có username là `user` không cần tồn tại vì user object được mock.
* `Authentication` được populate vào `SecurityContext` có type `UsernamePasswordAuthenticationToken`.
* principal của `Authentication` là `User` object của Spring Security.
* `User` có username là `user`.
* `User` có password là `password`.
* Một `GrantedAuthority` duy nhất có tên `ROLE_USER` được sử dụng.

Ví dụ trên tiện lợi vì cho phép sử dụng nhiều giá trị mặc định.
Nếu muốn chạy test với username khác thì sao?
Test sau sẽ chạy với username là `customUser` (một lần nữa, user không cần thực sự tồn tại):

include-code::./WithMockUserTests[tag=custom-user,indent=0]

Chúng ta cũng có thể dễ dàng customize role.
Ví dụ, test sau được invoke với username là `admin` và các role `ROLE_USER`, `ROLE_ADMIN`.

include-code::./WithMockUserTests[tag=custom-roles,indent=0]

Nếu không muốn value được tự động thêm tiền tố `ROLE_`, chúng ta có thể sử dụng attribute `authorities`.
Ví dụ, test sau được invoke với username là `admin` và các authority `USER`, `ADMIN`.

include-code::./WithMockUserTests[tag=custom-authorities,indent=0]

Việc đặt annotation trên mọi test method có thể hơi mất công.
Thay vào đó, chúng ta có thể đặt annotation ở cấp class. Khi đó, mọi test sẽ dùng user được chỉ định.
Ví dụ sau chạy tất cả test với một user có username là `admin`, password là `password` và các role `ROLE_USER`, `ROLE_ADMIN`:

include-code::./WithMockUserClassTests[tag=snippet,indent=0]

Nếu sử dụng test support `@Nested` của JUnit 5, bạn cũng có thể đặt annotation trên enclosing class để áp dụng cho mọi nested class.
Ví dụ sau chạy tất cả test method với một user có username là `admin`, password là `password` và các role `ROLE_USER`, `ROLE_ADMIN` cho cả hai test method:

include-code::./WithMockUserNestedTests[tag=snippet,indent=0]

Theo mặc định, `SecurityContext` được set trong event `TestExecutionListener.beforeTestMethod`.
Điều này tương đương với việc thiết lập diễn ra trước `@Before` của JUnit.
Bạn có thể thay đổi để việc này diễn ra trong event `TestExecutionListener.beforeTestExecution`, tức là sau `@Before` của JUnit nhưng trước khi gọi test method:

----

[[test-method-withuserdetails]]
== @WithUserDetails

Mặc dù `@WithMockUser` là cách thuận tiện để bắt đầu, annotation này có thể không phù hợp trong mọi trường hợp.
Ví dụ, một số application yêu cầu principal của `Authentication` có một type cụ thể.
Nhờ đó, application có thể tham chiếu principal bằng custom type và giảm coupling với Spring Security.

Custom principal thường được trả về bởi custom `UserDetailsService`, service này trả về một object implement cả `UserDetails` lẫn custom type.
Trong những trường hợp như vậy, việc tạo test user bằng custom `UserDetailsService` rất hữu ích.
Đó chính là việc `@WithUserDetails` thực hiện.

Giả sử chúng ta có một `UserDetailsService` được expose dưới dạng bean, test sau sẽ được invoke với một `Authentication` có type `UsernamePasswordAuthenticationToken` và principal do `UserDetailsService` trả về với username là `user`:

include-code::./WithUserDetailsTests[tag=user-details,indent=0]

Chúng ta cũng có thể customize username dùng để lookup user từ `UserDetailsService`.
Ví dụ, test này có thể chạy với principal do `UserDetailsService` trả về và có username là `customUsername`:

include-code::./WithUserDetailsTests[tag=user-details-custom-username,indent=0]

Chúng ta cũng có thể cung cấp rõ bean name dùng để lookup `UserDetailsService`.
Test sau lookup user có username `customUsername` bằng `UserDetailsService` có bean name là `myUserDetailsService`:

include-code::./WithCustomUserDetailsTests[tag=custom-user-details-service,indent=0]

Tương tự như với `@WithMockUser`, chúng ta cũng có thể đặt annotation ở cấp class để mọi test dùng cùng một user.
Tuy nhiên, khác với `@WithMockUser`, `@WithUserDetails` yêu cầu user phải tồn tại.

Theo mặc định, `SecurityContext` được set trong event `TestExecutionListener.beforeTestMethod`.
Điều này tương đương với việc thiết lập diễn ra trước `@Before` của JUnit.
Bạn có thể thay đổi để việc này diễn ra trong event `TestExecutionListener.beforeTestExecution`, tức là sau `@Before` của JUnit nhưng trước khi gọi test method:

[source,java]
----
@WithUserDetails(setupBefore = TestExecutionEvent.TEST_EXECUTION)
----

[[test-method-withsecuritycontext]]
== @WithSecurityContext

Chúng ta đã thấy `@WithMockUser` là lựa chọn rất tốt nếu không sử dụng custom `Authentication` principal.
Tiếp theo, `@WithUserDetails` cho phép sử dụng custom `UserDetailsService` để tạo `Authentication` principal, nhưng yêu cầu user phải tồn tại.
Bây giờ, hãy xem tùy chọn linh hoạt nhất.

Chúng ta có thể tạo annotation riêng sử dụng `@WithSecurityContext` để tạo bất kỳ `SecurityContext` nào mong muốn.
Ví dụ, chúng ta có thể tạo một annotation tên là `@WithMockCustomUser`:

include-code::./WithMockCustomUser[tag=snippet,indent=0]

Có thể thấy `@WithMockCustomUser` được đánh dấu bằng annotation `@WithSecurityContext`.
Điều này báo cho Spring Security test support rằng chúng ta muốn tạo một `SecurityContext` cho test.
Annotation `@WithSecurityContext` yêu cầu chỉ định một `SecurityContextFactory` để tạo `SecurityContext` mới dựa trên annotation `@WithMockCustomUser`.
Implementation `WithMockCustomUserSecurityContextFactory` như sau:

include-code::./WithMockCustomUserSecurityContextFactory[tag=snippet,indent=0]

Giờ đây, chúng ta có thể đánh dấu một test class hoặc test method bằng annotation mới; `WithSecurityContextTestExecutionListener` của Spring Security sẽ đảm bảo `SecurityContext` được populate đúng cách.

Khi tạo implementation `WithSecurityContextFactory` của riêng mình, cần biết rằng chúng có thể được đánh dấu bằng các annotation Spring tiêu chuẩn.
Ví dụ, `WithUserDetailsSecurityContextFactory` sử dụng annotation `@Autowired` để inject `UserDetailsService`:

include-code::./WithUserDetailsSecurityContextFactory[tag=snippet,indent=0]

Theo mặc định, `SecurityContext` được set trong event `TestExecutionListener.beforeTestMethod`.
Điều này tương đương với việc thiết lập diễn ra trước `@Before` của JUnit.
Bạn có thể thay đổi để việc này diễn ra trong event `TestExecutionListener.beforeTestExecution`, tức là sau `@Before` của JUnit nhưng trước khi gọi test method:

[source,java]
----
@WithSecurityContext(setupBefore = TestExecutionEvent.TEST_EXECUTION)
----

[NOTE]
====
`@WithMockUser`, `@WithUserDetails` và `@WithSecurityContext` populate xref:servlet/authentication/architecture.adoc#servlet-authentication-securitycontextholder[`SecurityContextHolder`] cho test thread.
Điều này không áp dụng cho full HTTP request mà test gửi đến running server, vì request đó được xử lý bởi một thread khác.
Đối với end-to-end HTTP test, hãy xref:servlet/authentication/index.adoc[authenticate] chính request đó (ví dụ bằng HTTP Basic hoặc bearer token).
====
