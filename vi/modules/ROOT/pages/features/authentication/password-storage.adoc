[[authentication-password-storage]]
= Lưu trữ mật khẩu

Interface `PasswordEncoder` của Spring Security được dùng để thực hiện phép biến đổi một chiều đối với password, nhằm cho phép lưu trữ password một cách an toàn.
Vì `PasswordEncoder` là một phép biến đổi một chiều, nó không phù hợp khi phép biến đổi password cần là hai chiều (chẳng hạn như lưu trữ các credential được dùng để authentication với một cơ sở dữ liệu).
Thông thường, `PasswordEncoder` được dùng để lưu trữ một password cần được so sánh với password do user cung cấp tại thời điểm authentication.

[[authentication-password-storage-history]]
== Lịch sử lưu trữ mật khẩu

Qua nhiều năm, cơ chế tiêu chuẩn để lưu trữ password đã phát triển.
Ban đầu, password được lưu dưới dạng plaintext.
Mật khẩu được cho là an toàn vì data store chứa password yêu cầu credential để truy cập.
Tuy nhiên, những user độc hại đã tìm ra cách lấy được các "`data dump`" lớn chứa username và password bằng cách sử dụng các cuộc tấn công như SQL Injection.
Khi ngày càng nhiều credential của user bị công khai, các chuyên gia bảo mật nhận ra rằng cần làm nhiều hơn để bảo vệ password của user.

Sau đó, các nhà phát triển được khuyến nghị lưu trữ password sau khi chạy chúng qua một one-way hash, chẳng hạn như SHA-256.
Khi user thử authentication, password đã được hash sẽ được so sánh với hash của password mà họ đã nhập.
Điều này có nghĩa là system chỉ cần lưu trữ one-way hash của password.
Nếu xảy ra một vụ vi phạm, chỉ các one-way hash của password bị lộ.
Vì các hash là một chiều và việc đoán password dựa trên hash đòi hỏi nhiều tính toán, việc tìm ra từng password trong system sẽ không đáng công sức.
Để đánh bại hệ thống mới này, những user độc hại đã quyết định tạo các bảng tra cứu được gọi là https://en.wikipedia.org/wiki/Rainbow_table[các Rainbow Table].
Thay vì phải đoán từng password mỗi lần, họ tính toán hash của password một lần rồi lưu nó trong một bảng tra cứu.

Để giảm hiệu quả của các Rainbow Table, các nhà phát triển được khuyến nghị sử dụng password có salt.
Thay vì chỉ dùng password làm đầu vào cho hash function, các byte ngẫu nhiên (được gọi là salt) sẽ được tạo cho password của mỗi user.
Salt và password của user sẽ được chạy qua hash function để tạo ra một hash duy nhất.
Salt sẽ được lưu cùng với password của user dưới dạng clear text.
Sau đó, khi user thử authentication, password đã được hash sẽ được so sánh với hash của salt đã lưu và password mà họ đã nhập.
Salt duy nhất có nghĩa là các Rainbow Table không còn hiệu quả vì hash khác nhau đối với mỗi tổ hợp salt và password.

Ngày nay, chúng ta nhận ra rằng các cryptographic hash (như SHA-256) không còn an toàn.
Lý do là với hardware hiện đại, chúng ta có thể thực hiện hàng tỷ phép tính hash mỗi giây.
Điều này có nghĩa là chúng ta có thể dễ dàng crack từng password riêng lẻ.

Hiện nay, các nhà phát triển được khuyến nghị tận dụng các adaptive one-way function để lưu trữ password.
Việc validate password bằng các adaptive one-way function có chủ ý tiêu tốn nhiều resource (chúng cố ý sử dụng nhiều CPU, memory hoặc resource khác).
Một adaptive one-way function cho phép cấu hình một "`work factor`" có thể tăng lên khi hardware trở nên tốt hơn.
Chúng tôi khuyến nghị điều chỉnh "`work factor`" để mất khoảng một giây cho việc verify một password trên system của bạn.
Sự đánh đổi này nhằm khiến attacker khó crack password, nhưng không quá tốn kém đến mức tạo gánh nặng quá lớn cho system của bạn hoặc làm user khó chịu.
Spring Security đã cố gắng cung cấp một điểm khởi đầu phù hợp cho "`work factor`", nhưng chúng tôi khuyến khích user tùy chỉnh "`work factor`" cho system của mình, vì hiệu năng thay đổi rất đáng kể giữa các system.
Các ví dụ về adaptive one-way function nên được sử dụng gồm <<authentication-password-storage-bcrypt,bcrypt>>, <<authentication-password-storage-pbkdf2,PBKDF2>>, <<authentication-password-storage-scrypt,scrypt>> và <<authentication-password-storage-argon2,argon2>>.

Vì các adaptive one-way function cố ý tiêu tốn nhiều resource, việc validate username và password cho mọi request có thể làm suy giảm đáng kể hiệu năng của application.
Không có gì mà Spring Security (hoặc bất kỳ library nào khác) có thể làm để tăng tốc việc validate password, vì tính bảo mật đạt được bằng cách khiến việc validate tiêu tốn nhiều resource.
User được khuyến nghị đổi credential dài hạn (tức username và password) lấy credential ngắn hạn (chẳng hạn như một session, một OAuth Token, vân vân).
Credential ngắn hạn có thể được validate nhanh chóng mà không làm mất tính bảo mật.


[[authentication-password-storage-dpe]]
== DelegatingPasswordEncoder

Trước Spring Security 5.0, `PasswordEncoder` mặc định là `NoOpPasswordEncoder`, yêu cầu password ở dạng plaintext.
Dựa trên phần <<authentication-password-storage-history,Lịch sử lưu trữ mật khẩu>>, bạn có thể mong đợi rằng `PasswordEncoder` mặc định hiện nay sẽ là một thứ gì đó như `BCryptPasswordEncoder`.
Tuy nhiên, điều này bỏ qua ba vấn đề thực tế:

- Nhiều application sử dụng các password encoding cũ không thể dễ dàng migrate.
- Best practice cho việc lưu trữ password sẽ lại thay đổi.
- Với tư cách là một framework, Spring Security không thể thường xuyên thực hiện các breaking change.

Thay vào đó, Spring Security giới thiệu `DelegatingPasswordEncoder`, giải quyết tất cả các vấn đề bằng cách:

- Đảm bảo password được encode theo các khuyến nghị hiện tại về lưu trữ password
- Cho phép validate password ở các format hiện đại và legacy
- Cho phép nâng cấp encoding trong tương lai

[[authentication-password-storage-dpe-format]]
=== Định dạng lưu trữ mật khẩu

Format chung cho một password là:

.Định dạng lưu trữ của DelegatingPasswordEncoder
[source,text,attrs="-attributes"]
----
{id}encodedPassword
----

`id` là một identifier được dùng để tra cứu `PasswordEncoder` nào nên được sử dụng, còn `encodedPassword` là password đã được encode ban đầu của `PasswordEncoder` được chọn.
`id` phải ở đầu password, bắt đầu bằng `{` và kết thúc bằng `}`.
Nếu không tìm thấy `id`, `id` được đặt thành null.
Ví dụ, dưới đây có thể là một danh sách các password được encode bằng những giá trị `id` khác nhau.
Tất cả password ban đầu đều là `password`.

.Ví dụ về password đã encode của DelegatingPasswordEncoder
[source,text,attrs="-attributes"]
----
{bcrypt}$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG // <1>
{noop}password // <2>
{pbkdf2}5d923b44a6d129f3ddf3e3c8d29412723dcbde72445e8ef6bf3b508fbf17fa4ed4d6b99ca763d8dc // <3>
{scrypt}$e0801$8bWJaSu2IKSn9Z9kM+TPXfOc/9bdYSrN1oD9qfVThWEwdRTnO7re7Ei+fUZRJ68k9lTyuTeUp4of4g24hHnazw==$OAOec05+bXxvuu/1qZ6NUR+xQYvYv7BeL1QxwRpY5Pc=  // <4>
{sha256}97cde38028ad898ebc02e690819fa220e88c62e0699403e94fff291cfffaf8410849f27605abcbc0 // <5>
----

<1> Password đầu tiên có `PasswordEncoder` id là `bcrypt` và giá trị `encodedPassword` là `$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG`.
Khi matching, nó sẽ delegate tới `BCryptPasswordEncoder`
<2> Password thứ hai có `PasswordEncoder` id là `noop` và giá trị `encodedPassword` là `password`.
Khi matching, nó sẽ delegate tới `NoOpPasswordEncoder`
<3> Password thứ ba có `PasswordEncoder` id là `pbkdf2` và giá trị `encodedPassword` là `5d923b44a6d129f3ddf3e3c8d29412723dcbde72445e8ef6bf3b508fbf17fa4ed4d6b99ca763d8dc`.
Khi matching, nó sẽ delegate tới `Pbkdf2PasswordEncoder`
<4> Password thứ tư có `PasswordEncoder` id là `scrypt` và giá trị `encodedPassword` là `$e0801$8bWJaSu2IKSn9Z9kM+TPXfOc/9bdYSrN1oD9qfVThWEwdRTnO7re7Ei+fUZRJ68k9lTyuTeUp4of4g24hHnazw==$OAOec05+bXxvuu/1qZ6NUR+xQYvYv7BeL1QxwRpY5Pc=`
Khi matching, nó sẽ delegate tới `SCryptPasswordEncoder`
<5> Password cuối cùng có `PasswordEncoder` id là `sha256` và giá trị `encodedPassword` là `97cde38028ad898ebc02e690819fa220e88c62e0699403e94fff291cfffaf8410849f27605abcbc0`.
Khi matching, nó sẽ delegate tới `StandardPasswordEncoder`

[NOTE]
====
Một số user có thể lo ngại rằng một attacker tiềm năng biết được storage format.
Đây không phải là vấn đề đáng lo vì password storage không dựa vào việc giữ bí mật algorithm.
Ngoài ra, attacker có thể dễ dàng xác định hầu hết format ngay cả khi không có prefix.
Ví dụ, password BCrypt thường bắt đầu bằng `$2a$`.
====

[[authentication-password-storage-dpe-encoding]]
=== Encode password

`idForEncode` được truyền vào constructor quyết định `PasswordEncoder` nào được dùng để encode password.
Trong `DelegatingPasswordEncoder` mà chúng ta đã tạo trước đó, điều này có nghĩa là kết quả encode `password` sẽ được delegate tới `BCryptPasswordEncoder` và có prefix `+{bcrypt}+`.
Kết quả cuối cùng trông như ví dụ sau:

.Ví dụ encode của DelegatingPasswordEncoder
[source,text,attrs="-attributes"]
----
{bcrypt}$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG
----

[[authentication-password-storage-dpe-matching]]
=== Matching password

Matching dựa trên `+{id}+` và mapping từ `id` tới `PasswordEncoder` được cung cấp trong constructor.
Ví dụ trong <<authentication-password-storage-dpe-format,Định dạng lưu trữ mật khẩu>> minh họa cách thực hiện việc này.
Theo mặc định, việc gọi `matches(CharSequence, String)` với một password và một `id` chưa được mapping (bao gồm cả id null) sẽ cho kết quả là `IllegalArgumentException`.
Có thể tùy chỉnh hành vi này bằng cách sử dụng `DelegatingPasswordEncoder.setDefaultPasswordEncoderForMatches(PasswordEncoder)`.

Bằng cách sử dụng `id`, chúng ta có thể matching với bất kỳ password encoding nào nhưng encode password bằng encoding hiện đại nhất.
Điều này quan trọng vì khác với encryption, password hash được thiết kế để không có cách đơn giản nào khôi phục plaintext.
Vì không có cách khôi phục plaintext, việc migrate password rất khó.
Mặc dù user có thể dễ dàng migrate khỏi `NoOpPasswordEncoder`, chúng tôi chọn đưa nó vào mặc định để đơn giản hóa việc bắt đầu sử dụng.

[[authentication-password-storage-dpe-troubleshoot]]
=== Khắc phục sự cố

Lỗi sau xảy ra khi một trong các password được lưu trữ không có `id`, như được mô tả trong <<authentication-password-storage-dpe-format>>.

----
java.lang.IllegalArgumentException: There is no PasswordEncoder mapped for the id "null"
	at org.springframework.security.crypto.password.DelegatingPasswordEncoder$UnmappedIdPasswordEncoder.matches(DelegatingPasswordEncoder.java:233)
	at org.springframework.security.crypto.password.DelegatingPasswordEncoder.matches(DelegatingPasswordEncoder.java:196)
----

Cách dễ nhất để giải quyết là xác định cách password của bạn hiện đang được lưu trữ và chỉ định đúng `PasswordEncoder`.

Nếu bạn đang migrate từ Spring Security 4.2.x, bạn có thể quay lại hành vi trước đó bằng cách <<authentication-password-storage-configuration,expose một bean `NoOpPasswordEncoder`>>.

Ngoài ra, bạn có thể thêm prefix `id` chính xác vào tất cả password của mình và tiếp tục sử dụng `DelegatingPasswordEncoder`.
Ví dụ, nếu bạn đang sử dụng BCrypt, bạn sẽ migrate password từ dạng:

----
$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG
----

thành

[source,attrs="-attributes"]
----
{bcrypt}$2a$10$dXJ3SW6G7P50lGmMkkmwe.20cQQubK3.HZWzG3YB1tlRy.fqvM/BG
----

Để xem danh sách mapping đầy đủ, hãy xem Javadoc của javadoc:org.springframework.security.crypto.factory.PasswordEncoderFactories[].

[[authentication-password-storage-other]]
== Các ``PasswordEncoder`` khác

Có khá nhiều implementation `PasswordEncoder` khác chỉ tồn tại vì mục đích backward compatibility.
Tất cả đều đã deprecated để cho biết rằng chúng không còn được xem là an toàn.
Tuy nhiên, chưa có kế hoạch xóa chúng vì việc migrate các legacy system hiện có rất khó.

[[password4j]]
== Các Password Encoder dựa trên Password4j

Spring Security 7.0 giới thiệu các implementation password encoder thay thế dựa trên thư viện https://github.com/Password4j/password4j[Password4j].
Các encoder này cung cấp thêm lựa chọn cho những thuật toán hash phổ biến và có thể được dùng thay thế cho các implementation hiện có của Spring Security.

Thư viện Password4j là một cryptographic library dành cho Java, tập trung vào việc hash password và hỗ trợ nhiều algorithm.
Các encoder này đặc biệt hữu ích khi bạn cần cấu hình algorithm cụ thể hoặc muốn tận dụng các tối ưu hóa của Password4j.

Tất cả encoder dựa trên Password4j đều thread-safe và có thể được dùng chung giữa nhiều thread.

[[password4j-argon2]]
=== Argon2Password4jPasswordEncoder

Implementation `Argon2Password4jPasswordEncoder` sử dụng thuật toán https://en.wikipedia.org/wiki/Argon2[Argon2] thông qua thư viện Password4j để hash password.

[[authentication-password-storage-configuration]]
== Cấu hình lưu trữ password

Spring Security sử dụng <<authentication-password-storage-dpe>> theo mặc định.
Tuy nhiên, bạn có thể tùy chỉnh điều này bằng cách expose một `PasswordEncoder` dưới dạng Spring bean.


Nếu bạn đang migrate từ Spring Security 4.2.x, bạn có thể quay lại hành vi trước đó bằng cách expose một bean `NoOpPasswordEncoder`.

[WARNING]
====
Quay lại sử dụng `NoOpPasswordEncoder` không được xem là an toàn.
Thay vào đó, bạn nên migrate sang sử dụng `DelegatingPasswordEncoder` để hỗ trợ encode password an toàn.
====

.NoOpPasswordEncoder
[tabs]
======
Java::
+
[source,java,role="primary"]
----
@Bean
public static NoOpPasswordEncoder passwordEncoder() {
    return NoOpPasswordEncoder.getInstance();
}
----

XML::
+
[source,xml,role="secondary"]
----
<b:bean id="passwordEncoder"
        class="org.springframework.security.crypto.password.NoOpPasswordEncoder" factory-method="getInstance"/>
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
@Bean
fun passwordEncoder(): PasswordEncoder {
    return NoOpPasswordEncoder.getInstance();
}
----
======

[NOTE]
====
Cấu hình XML yêu cầu tên bean `NoOpPasswordEncoder` phải là `passwordEncoder`.
====

[[authentication-change-password-configuration]]
== Cấu hình đổi password

Hầu hết application cho phép user chỉ định password cũng yêu cầu một tính năng để cập nhật password đó.

https://w3c.github.io/webappsec-change-password-url/[Well-Known URL để đổi password] chỉ ra một cơ chế mà password manager có thể dùng để tìm password update endpoint của một application cụ thể.

Bạn có thể cấu hình Spring Security để cung cấp discovery endpoint này.
Ví dụ, nếu change password endpoint trong application của bạn là `/change-password`, bạn có thể cấu hình Spring Security như sau:

.Endpoint đổi password mặc định
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .passwordManagement(Customizer.withDefaults())
----

XML::
+
[source,xml,role="secondary"]
----
<sec:password-management/>
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    passwordManagement { }
}
----
======

Sau đó, khi password manager điều hướng tới `/.well-known/change-password`, Spring Security sẽ redirect tới endpoint `/change-password` của bạn.

Hoặc, nếu endpoint của bạn không phải là `/change-password`, bạn cũng có thể chỉ định endpoint đó như sau:

.Endpoint đổi password
[tabs]
======
Java::
+
[source,java,role="primary"]
----
http
    .passwordManagement((management) -> management
        .changePasswordPage("/update-password")
    )
----

XML::
+
[source,xml,role="secondary"]
----
<sec:password-management change-password-page="/update-password"/>
----

Kotlin::
+
[source,kotlin,role="secondary"]
----
http {
    passwordManagement {
        changePasswordPage = "/update-password"
    }
}
----
======

Với cấu hình trên, khi password manager điều hướng tới `/.well-known/change-password`, Spring Security sẽ redirect tới `/update-password`.

[[authentication-compromised-password-check]]
== Kiểm tra password bị lộ

Có một số tình huống bạn cần kiểm tra xem password có bị lộ hay không. Ví dụ, nếu bạn đang tạo một application xử lý dữ liệu nhạy cảm, thường cần thực hiện một số kiểm tra trên password của user để đánh giá độ tin cậy của password.
Một trong các kiểm tra đó có thể là kiểm tra xem password có bị lộ hay không, thường là vì nó được tìm thấy trong một https://wikipedia.org/wiki/Data_breach[data breach].

Để hỗ trợ việc đó, Spring Security cung cấp tích hợp với https://haveibeenpwned.com/API/v3#PwnedPasswords[Have I Been Pwned API] thông qua implementation javadoc:org.springframework.security.web.authentication.password.HaveIBeenPwnedRestApiPasswordChecker[] của interface javadoc:org.springframework.security.authentication.password.CompromisedPasswordChecker[].

Bạn có thể tự sử dụng API `CompromisedPasswordChecker` hoặc, nếu đang sử dụng xref:servlet/authentication/passwords/dao-authentication-provider.adoc[các `DaoAuthenticationProvider`] thông qua xref:servlet/authentication/passwords/index.adoc[các cơ chế authentication của Spring Security], bạn có thể cung cấp một bean `CompromisedPasswordChecker`, và cấu hình Spring Security sẽ tự động nhận bean đó.

Khi làm như vậy, nếu bạn thử authentication qua Form Login bằng một password yếu, chẳng hạn `123456`, bạn sẽ nhận được 401 hoặc được redirect tới trang `/login?error` (tùy thuộc vào user-agent của bạn).
Tuy nhiên, chỉ trả về 401 hoặc redirect trong trường hợp này không hữu ích lắm và sẽ gây nhầm lẫn vì user đã cung cấp đúng password nhưng vẫn không được phép đăng nhập.
Trong những trường hợp như vậy, bạn có thể xử lý `CompromisedPasswordException` thông qua `AuthenticationFailureHandler` để thực hiện logic mong muốn, chẳng hạn redirect user-agent tới `/reset-password`:
